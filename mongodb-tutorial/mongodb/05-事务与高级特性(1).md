# 第五章：事务与高级特性

## 5.1 事务基础

MongoDB 4.0+ 支持多文档事务，确保 ACID 特性。

### ACID 特性

- **Atomicity（原子性）**：事务中的所有操作要么全部成功，要么全部失败
- **Consistency（一致性）**：事务前后数据保持一致
- **Isolation（隔离性）**：并发事务之间相互隔离
- **Durability（持久性）**：事务提交后数据永久保存

## 5.2 事务使用

### 基本语法

```javascript
const session = client.startSession();

try {
  session.startTransaction();
  
  // 执行操作
  await db.collection1.insertOne({ ... }, { session });
  await db.collection2.updateOne({ ... }, { ... }, { session });
  
  await session.commitTransaction();
} catch (error) {
  await session.abortTransaction();
  throw error;
} finally {
  session.endSession();
}
```

### Node.js 示例（Mongoose）

```javascript
const mongoose = require('mongoose');

async function transferMoney(fromUserId, toUserId, amount) {
  const session = await mongoose.startSession();
  session.startTransaction();
  
  try {
    // 扣除转出账户
    await User.updateOne(
      { _id: fromUserId },
      { $inc: { balance: -amount } },
      { session }
    );
    
    // 检查余额
    const fromUser = await User.findById(fromUserId).session(session);
    if (fromUser.balance < 0) {
      throw new Error('余额不足');
    }
    
    // 增加转入账户
    await User.updateOne(
      { _id: toUserId },
      { $inc: { balance: amount } },
      { session }
    );
    
    // 记录交易
    await Transaction.create([{
      fromUserId,
      toUserId,
      amount,
      type: 'transfer'
    }], { session });
    
    await session.commitTransaction();
    console.log('转账成功');
  } catch (error) {
    await session.abortTransaction();
    console.error('转账失败:', error);
    throw error;
  } finally {
    session.endSession();
  }
}
```

### TypeScript + Typegoose 示例

```typescript
import { InjectEntityModel } from "@midwayjs/typegoose";
import { ReturnModelType } from "@typegoose/typegoose";
import { Connection } from "mongoose";

@Provide()
export class TransactionService {
  @InjectEntityModel(User)
  userModel: ReturnModelType<typeof User>;
  
  @InjectEntityModel(Transaction)
  transactionModel: ReturnModelType<typeof Transaction>;
  
  @Inject()
  connection: Connection;
  
  async transferMoney(fromUserId: string, toUserId: string, amount: number) {
    const session = await this.connection.startSession();
    
    try {
      await session.withTransaction(async () => {
        // 扣除转出账户
        await this.userModel.updateOne(
          { _id: fromUserId },
          { $inc: { balance: -amount } },
          { session }
        );
        
        // 检查余额
        const fromUser = await this.userModel
          .findById(fromUserId)
          .session(session)
          .lean();
        
        if (fromUser.balance < 0) {
          throw new Error('余额不足');
        }
        
        // 增加转入账户
        await this.userModel.updateOne(
          { _id: toUserId },
          { $inc: { balance: amount } },
          { session }
        );
        
        // 记录交易
        await this.transactionModel.create([{
          fromUserId,
          toUserId,
          amount,
          type: 'transfer',
          createdAt: new Date()
        }], { session });
      });
      
      console.log('转账成功');
    } catch (error) {
      console.error('转账失败:', error);
      throw error;
    } finally {
      await session.endSession();
    }
  }
}
```

## 5.3 事务实现原理

理解MongoDB事务的底层实现机制，有助于更好地使用事务和解决相关问题。

### 5.3.1 副本集架构基础

在了解事务实现之前，需要先理解MongoDB的副本集架构：

**副本集（Replica Set）组成**：
- **主节点（Primary）**：唯一可以接收写操作的节点，所有写操作都先写入主节点
- **从节点（Secondary）**：复制主节点的数据，可以接收读操作（取决于读关注设置）
- **仲裁节点（Arbiter）**：不存储数据，只参与选举，帮助副本集在偶数个节点时选出主节点

**副本集架构示例**：

```text
┌─────────────┐
│  客户端应用  │
└──────┬──────┘
       │
       ├─────────────────┐
       │                 │
       ▼                 ▼
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  主节点     │──▶│  从节点1    │   │  从节点2    │
│ (Primary)   │   │ (Secondary) │   │ (Secondary) │
│             │   │             │   │             │
│ 写操作      │   │ 只读        │   │ 只读        │
│ 读操作      │   │             │   │             │
└─────────────┘   └─────────────┘   └─────────────┘
```

**主节点的作用**：
1. **唯一写入口**：所有写操作（insert、update、delete）必须通过主节点
2. **事务协调**：多文档事务由主节点协调执行
3. **数据同步**：将操作记录到oplog（操作日志），从节点通过oplog同步数据

**从节点的作用**：
1. **数据冗余**：存储主节点的数据副本，提供高可用性
2. **读扩展**：可以分担读操作（需要配置合适的读关注）
3. **故障转移**：主节点故障时，从节点可以选举成为新的主节点

### 5.3.2 事务的协调机制

MongoDB事务采用**两阶段提交（Two-Phase Commit, 2PC）**机制来保证ACID特性。

**事务执行流程**：

```text
阶段1：准备阶段（Prepare Phase）
┌─────────────────────────────────────────┐
│ 1. 客户端发起事务                        │
│ 2. 主节点分配事务ID（txnNumber）         │
│ 3. 主节点记录事务操作到事务日志           │
│ 4. 主节点锁定相关文档（WiredTiger层）    │
│ 5. 主节点准备提交，等待从节点确认         │
└─────────────────────────────────────────┘
              │
              ▼
阶段2：提交阶段（Commit Phase）
┌─────────────────────────────────────────┐
│ 6. 主节点将事务操作写入oplog             │
│ 7. 从节点复制oplog并应用事务操作         │
│ 8. 达到写关注要求后，主节点确认提交      │
│ 9. 释放锁，事务完成                      │
└─────────────────────────────────────────┘
```

**详细步骤说明**：

1. **事务开始**：
   ```javascript
   const session = client.startSession();
   session.startTransaction();
   ```
   - 客户端创建会话（Session）
   - 主节点分配唯一的事务ID（txnNumber）
   - 事务ID用于标识和追踪事务

2. **操作执行**：
   ```javascript
   await db.collection1.insertOne({ ... }, { session });
   await db.collection2.updateOne({ ... }, { ... }, { session });
   ```
   - 所有操作都携带`session`参数
   - 主节点将操作记录到事务日志（transaction log）
   - WiredTiger存储引擎在文档级别加锁
   - **此时数据尚未提交，其他事务看不到这些修改**

3. **准备提交**：
   ```javascript
   await session.commitTransaction();
   ```
   - 主节点将事务操作写入oplog（操作日志）
   - oplog是MongoDB复制机制的核心，记录所有写操作
   - 主节点等待从节点复制oplog（取决于写关注设置）

4. **从节点同步**：
   - 从节点定期拉取主节点的oplog
   - 从节点应用事务操作到本地数据
   - 从节点确认已应用操作

5. **提交确认**：
   - 当达到写关注要求（如`w: 'majority'`）时
   - 主节点确认事务已提交
   - 释放文档锁
   - 其他事务现在可以看到这些修改

### 5.3.3 WiredTiger存储引擎的事务支持

MongoDB使用WiredTiger作为默认存储引擎，它提供了事务的底层支持：

**WiredTiger的事务特性**：

1. **文档级锁**：
   - WiredTiger使用文档级（document-level）锁，而不是集合级锁
   - 多个事务可以并发修改不同文档
   - 只有修改同一文档的事务才会互斥

2. **快照隔离（Snapshot Isolation）**：
   - 每个事务看到数据的一致快照
   - 事务开始时获取快照时间戳
   - 事务中的所有读操作都基于这个快照

3. **MVCC（多版本并发控制）**：
   - WiredTiger维护文档的多个版本
   - 读操作读取快照版本，写操作创建新版本
   - 提交时，新版本变为可见版本

**锁竞争示例**：

```javascript
// 事务1：修改文档A
const session1 = client.startSession();
session1.startTransaction();
await db.users.updateOne({ _id: 'user1' }, { $set: { balance: 100 } }, { session: session1 });
// 事务1持有 user1 的锁

// 事务2：修改文档B（可以并发执行）
const session2 = client.startSession();
session2.startTransaction();
await db.users.updateOne({ _id: 'user2' }, { $set: { balance: 200 } }, { session: session2 });
// 事务2持有 user2 的锁，与事务1不冲突

// 事务3：修改文档A（必须等待事务1完成）
const session3 = client.startSession();
session3.startTransaction();
await db.users.updateOne({ _id: 'user1' }, { $set: { balance: 300 } }, { session: session3 });
// 事务3必须等待事务1释放 user1 的锁
```

### 5.3.4 事务日志（Transaction Log）

MongoDB使用事务日志来保证事务的持久性和可恢复性：

**事务日志的作用**：

1. **持久性保证**：事务提交前，操作先写入事务日志
2. **故障恢复**：MongoDB重启后，从未提交的事务日志恢复
3. **复制基础**：oplog基于事务日志生成

**事务日志流程**：

```text
写操作
  │
  ▼
WiredTiger事务日志（本地）
  │
  ▼
oplog（操作日志，用于复制）
  │
  ├──▶ 从节点1复制
  ├──▶ 从节点2复制
  └──▶ ...
```

### 5.3.5 副本集中的事务实现

在副本集中，事务的实现涉及主节点和从节点的协调：

**单副本集事务流程**：

```javascript
// 客户端发起事务
const session = client.startSession();
session.startTransaction({
  readConcern: { level: 'majority' },
  writeConcern: { w: 'majority' }
});

try {
  // 1. 操作发送到主节点
  await db.accounts.updateOne(
    { userId: 'user1' },
    { $inc: { balance: -100 } },
    { session }
  );
  
  // 2. 主节点记录到事务日志
  // 3. 主节点锁定文档
  
  await db.accounts.updateOne(
    { userId: 'user2' },
    { $inc: { balance: 100 } },
    { session }
  );
  
  // 4. 提交事务
  await session.commitTransaction();
  // 5. 主节点写入oplog
  // 6. 从节点复制oplog
  // 7. 达到写关注要求（w: 'majority'）后确认提交
} catch (error) {
  await session.abortTransaction();
  // 回滚：主节点丢弃事务日志中的操作
}
```

**主节点故障时的处理**：

1. **事务进行中主节点故障**：
   - 事务自动回滚
   - 从节点选举新的主节点
   - 客户端需要重试事务

2. **事务提交中主节点故障**：
   - 如果oplog已写入，从节点可以继续提交
   - 如果oplog未写入，事务回滚
   - 客户端可能收到`UnknownTransactionCommitResult`错误，需要检查事务状态

### 5.3.6 分片集群中的事务实现

分片集群中的事务实现更复杂，因为数据分布在多个分片上：

**分片事务限制**：

1. **单分片事务**：事务只能操作单个分片的数据（MongoDB 4.0+）
2. **跨分片事务**：事务可以操作多个分片的数据（MongoDB 4.2+）

**跨分片事务流程**：

```text
客户端
  │
  ▼
协调节点（mongos）
  │
  ├──▶ 分片1（主节点）──▶ 分片1（从节点）
  ├──▶ 分片2（主节点）──▶ 分片2（从节点）
  └──▶ 分片3（主节点）──▶ 分片3（从节点）
```

**跨分片事务的两阶段提交**：

1. **准备阶段**：
   - mongos协调节点向所有涉及的分片发送准备命令
   - 每个分片的主节点准备事务，记录到事务日志
   - 每个分片等待从节点确认

2. **提交阶段**：
   - 所有分片准备完成后，mongos发送提交命令
   - 每个分片的主节点写入oplog
   - 所有分片达到写关注要求后，事务提交

**分片事务示例**：

```javascript
// 跨分片事务（MongoDB 4.2+）
const session = client.startSession();
session.startTransaction({
  readConcern: { level: 'snapshot' },
  writeConcern: { w: 'majority' }
});

try {
  // 这些操作可能涉及不同的分片
  await db.orders.insertOne({ userId: 'user1', amount: 100 }, { session });
  await db.payments.insertOne({ userId: 'user1', amount: 100 }, { session });
  await db.inventory.updateOne({ productId: 'prod1' }, { $inc: { stock: -1 } }, { session });
  
  await session.commitTransaction();
  // mongos协调所有分片的两阶段提交
} catch (error) {
  await session.abortTransaction();
  // 所有分片回滚
}
```

### 5.3.7 事务性能考虑

理解事务实现有助于优化性能：

**性能影响因素**：

1. **锁竞争**：
   - 文档级锁减少了锁竞争
   - 但热点文档（频繁修改的文档）仍可能成为瓶颈
   - 解决方案：减少事务持续时间，避免长时间持有锁

2. **写关注级别**：
   - `w: 1`：只等待主节点确认，最快
   - `w: 'majority'`：等待大多数节点确认，更安全但更慢
   - 根据业务需求选择平衡点

3. **读关注级别**：
   - `local`：从本地节点读取，最快但可能读到未提交数据
   - `majority`：从大多数节点读取，保证一致性但可能延迟
   - `snapshot`：读取快照，最高一致性但性能开销最大

4. **事务持续时间**：
   - 事务持续时间越长，锁持有时间越长
   - 锁持有时间越长，其他事务等待时间越长
   - **最佳实践**：尽快提交或回滚事务

**性能优化建议**：

```javascript
// ❌ 不好：事务中包含慢操作
const session = client.startSession();
session.startTransaction();
await db.users.updateOne({ ... }, { ... }, { session });
await slowNetworkCall(); // 慢操作，长时间持有锁
await db.orders.insertOne({ ... }, { session });
await session.commitTransaction();

// ✅ 好：先完成慢操作，再开始事务
await slowNetworkCall(); // 在事务外完成
const session = client.startSession();
session.startTransaction();
await db.users.updateOne({ ... }, { ... }, { session });
await db.orders.insertOne({ ... }, { session });
await session.commitTransaction(); // 快速提交
```

### 5.3.8 事务错误处理

理解事务实现有助于正确处理错误：

**常见错误类型**：

1. **WriteConflict（写冲突）**：
   - 多个事务同时修改同一文档
   - 解决方案：重试事务

2. **TransientTransactionError（临时事务错误）**：
   - 主节点选举、网络问题等临时错误
   - 解决方案：重试事务

3. **UnknownTransactionCommitResult（未知提交结果）**：
   - 提交过程中网络中断
   - 解决方案：检查事务状态，必要时重试

**错误处理示例**：

```javascript
async function executeWithRetry(operation, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    const session = client.startSession();
    
    try {
      await session.withTransaction(async () => {
        await operation(session);
      }, {
        readConcern: { level: 'majority' },
        writeConcern: { w: 'majority' }
      });
      
      return; // 成功
    } catch (error) {
      if (error.hasErrorLabel('TransientTransactionError') ||
          error.hasErrorLabel('UnknownTransactionCommitResult')) {
        // 临时错误，可以重试
        await new Promise(resolve => setTimeout(resolve, 100 * Math.pow(2, i)));
        continue;
      } else {
        // 非临时错误，不重试
        throw error;
      }
    } finally {
      session.endSession();
    }
  }
  
  throw new Error('Transaction failed after retries');
}
```

## 5.4 事务选项

### 读写关注（Read/Write Concern）

**读关注（Read Concern）**：控制读取操作从哪些节点读取数据。

```javascript
// 读关注级别
const session = client.startSession({
  defaultTransactionOptions: {
    // local: 从本地节点读取（最快，但可能读到未提交的数据）
    readConcern: { level: 'local' },
    
    // majority: 从大多数节点读取（保证读到已提交的数据）
    readConcern: { level: 'majority' },
    
    // snapshot: 读取快照数据（最高一致性）
    readConcern: { level: 'snapshot' }
  }
});
```

**写关注（Write Concern）**：控制写入操作需要多少个节点确认。

```javascript
session.startTransaction({
  // w: 1 - 等待主节点确认（默认，最快）
  writeConcern: { w: 1 },
  
  // w: 'majority' - 等待大多数节点确认（更高一致性）
  writeConcern: { w: 'majority' },
  
  // w: 2 - 等待 2 个节点确认
  writeConcern: { w: 2 },
  
  // wtimeout: 超时时间（毫秒）
  writeConcern: { w: 'majority', wtimeout: 5000 }
});
```

**读写关注组合**：

```javascript
// 高性能配置（适合读多写少）
session.startTransaction({
  readConcern: { level: 'local' },
  writeConcern: { w: 1 }
});

// 高一致性配置（适合金融交易）
session.startTransaction({
  readConcern: { level: 'majority' },
  writeConcern: { w: 'majority' }
});
```

### 5.4.1 事务隔离级别

MongoDB 支持快照隔离（Snapshot Isolation），这是默认的隔离级别。

**快照隔离特点**：
- ✅ 事务看到一致的数据快照
- ✅ 避免脏读（Dirty Read）
- ✅ 避免不可重复读（Non-repeatable Read）
- ⚠️ 可能出现幻读（Phantom Read）

**隔离级别示例**：

```javascript
// 事务1：转账操作
const session1 = client.startSession();
session1.startTransaction({
  readConcern: { level: 'snapshot' },
  writeConcern: { w: 'majority' }
});

try {
  // 读取账户余额（快照）
  const account1 = await Account.findOne({ userId: 'user1' }).session(session1);
  const account2 = await Account.findOne({ userId: 'user2' }).session(session1);
  
  // 执行转账
  await Account.updateOne(
    { userId: 'user1' },
    { $inc: { balance: -100 } },
    { session: session1 }
  );
  
  await Account.updateOne(
    { userId: 'user2' },
    { $inc: { balance: 100 } },
    { session: session1 }
  );
  
  await session1.commitTransaction();
} catch (error) {
  await session1.abortTransaction();
  throw error;
} finally {
  session1.endSession();
}
```

**并发控制**：

```javascript
// 使用写冲突检测
const session = client.startSession();
session.startTransaction();

try {
  // 读取文档
  const doc = await Collection.findOne({ _id: id }).session(session);
  
  // 修改文档
  await Collection.updateOne(
    { _id: id, version: doc.version },  // 版本号检查
    { $set: { ... }, $inc: { version: 1 } },
    { session }
  );
  
  await session.commitTransaction();
} catch (error) {
  if (error.code === 11000) {  // 写冲突
    await session.abortTransaction();
    // 重试逻辑
  }
} finally {
  session.endSession();
}
```

### 5.4.2 事务超时和重试

```javascript
// 事务超时
session.startTransaction({
  maxTimeMS: 5000  // 5 秒超时
});

// 事务重试逻辑
async function transferWithRetry(fromUserId, toUserId, amount, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    const session = client.startSession();
    
    try {
      await session.withTransaction(async () => {
        // 转账操作
        await transferMoney(fromUserId, toUserId, amount, session);
      }, {
        maxTimeMS: 5000,
        readConcern: { level: 'majority' },
        writeConcern: { w: 'majority' }
      });
      
      return;  // 成功，退出
    } catch (error) {
      if (error.hasErrorLabel('TransientTransactionError')) {
        //  transient 错误，可以重试
        await new Promise(resolve => setTimeout(resolve, 100 * (i + 1)));  // 指数退避
        continue;
      } else {
        // 非 transient 错误，不重试
        throw error;
      }
    } finally {
      session.endSession();
    }
  }
  
  throw new Error('Transaction failed after retries');
}
```

**事务错误类型**：

- **TransientTransactionError**：临时错误，可以重试
- **UnknownTransactionCommitResult**：提交结果未知，需要检查
- **WriteConflict**：写冲突，需要重试

## 5.5 变更流（Change Streams）

变更流可以实时监听集合的变化。

### 基本使用

```javascript
// 监听集合变化
const changeStream = db.collection('users').watch();

changeStream.on('change', (change) => {
  console.log('变化:', change);
  
  switch (change.operationType) {
    case 'insert':
      console.log('插入:', change.fullDocument);
      break;
    case 'update':
      console.log('更新:', change.updateDescription);
      break;
    case 'delete':
      console.log('删除:', change.documentKey);
      break;
    case 'replace':
      console.log('替换:', change.fullDocument);
      break;
  }
});

// 监听特定条件的变化
const changeStream = db.collection('users').watch([
  { $match: { 'fullDocument.status': 'active' } }
]);
```

### Node.js 示例

```typescript
import { ChangeStream } from 'mongodb';

async function watchLotteryResources() {
  const changeStream = this.lotteryResourceDao.watch([
    { $match: { 'fullDocument.tag': 2 } }  // 只监听审核通过的
  ]);
  
  changeStream.on('change', (change) => {
    console.log('抽奖资源变化:', change);
    
    // 处理变化，例如发送通知
    if (change.operationType === 'insert') {
      this.notifyNewResource(change.fullDocument);
    }
  });
  
  changeStream.on('error', (error) => {
    console.error('变更流错误:', error);
  });
}
```
