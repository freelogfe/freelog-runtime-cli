# 运行时与 CLI：主题、插件的本地开发

状态：讨论稿，2026-10-14。只做分析和产品设计，尚未实现新的预览命令或 mock 协议。

本轮已按节点产品文档与 Console 实际代码修正业务层次。平台测试节点及其规则明确排除；“本地插件预览宿主”是正式节点页面内的临时挂载工具，两者无关。

目标：开发者或 AI 在真实节点页面里开发主题、插件，修改代码、属性、可选配置和依赖时不用反复发行版本；完成后再走真实发行与节点签约。

## 先记住这个最小模型

**开发中的应用 = 本地代码 + 开发上下文 + 一个挂载它的宿主。**

- 主题的宿主是节点运行时；节点已有可用主题时，可以替换其代码入口。
- 插件的宿主是一个会调用挂载 API 的主题或父插件。给出插件地址，并不会让主题自动挂载它。
- 本地代码替换不等于属性、配置和依赖也被替换；这些需要统一的开发上下文。

因此插件首发前的推荐入口是“本地插件预览宿主”：在用户提供的正式节点里，用一个轻量本地主题挂载本地插件。它不是要发行的业务主题，也不是用假 ID 直接访问平台资源。

## 推荐先讨论的两个结论

1. 建议让插件先在本地预览宿主单独调试，再进入真实主题联调，不要求先发行插件或改节点主题的真实依赖；需要运行时新能力配套。
2. mock 只改变当前开发页面的执行视图；不能把它当作真实授权、真实节点签约或线上发行成功。

目标是两仓都修改，以运行时接管 mock 为核心；CLI 组织候选、关系和场景，不重做运行时响应投影。新应用可纯本地编辑开发候选，不要求先建线上壳；决定发行才接入正式稿。

本轮产物是可审阅设计，不是“功能已经可用”。03 补了真实 CLI 初始化/只读数据/节点门禁与未来能力场景推演；完整 mock 仍待实现和实测。证据缺口与验收门槛集中在 02。
