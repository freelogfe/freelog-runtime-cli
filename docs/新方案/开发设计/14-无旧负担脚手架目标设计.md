# 无旧负担脚手架目标设计

## 1. 结论

本设计按“新脚手架开发、没有旧代码负担”处理：不兼容旧 `freelog.resource.config.*` / `freelog.version.config.*` / `freelog.collection.config.*`，不保留 `jiti` 执行用户配置的能力，不做旧 config 迁移层。

最终形态：

1. 用户发布意图只存在于 `freelog.manifest.json`。
2. CLI 运行状态只存在于 `.freelog/state.json`。
3. 工程模板的元数据仍叫 `template.manifest.json`，但它只描述模板包，不参与资源发布。
4. CLI 对齐 Console 的平台请求契约，不复刻 Console 的 React 页面、弹窗、自动保存节奏。
5. `@freelog/tools-lib2/node` 是 CLI 唯一平台 SDK 入口；浏览器端继续走默认导出，不需要改。

这意味着实现阶段应删除旧配置层，而不是在旧 config 上继续补字段。

## 2. 证据清单

### 2.1 当前 CLI 的结构性问题

| 证据 | 说明 |
|---|---|
| `packages/cli/src/config/read.ts` | 当前通过 `jiti` 加载 `freelog.*.config.ts/js`，会执行用户配置代码。 |
| `packages/cli/src/config/writeShell.ts` | `ResourceShell` / `VersionShell` / `CollectionShell` 同时包含用户意图和 CLI 状态，例如 `resourceId`、`userId`、`draftSync` 与 `dependencies`、`filePath` 混在一起。 |
| `packages/cli/src/services/scaffold.ts` | `init` 复制模板后写 `freelog.resource.config`、`freelog.version.config`，另写 `.freelog/scaffold-meta.json`。 |
| `packages/cli/src/services/publishService.ts` | `publish` 读取 version config，并把 `fileSha1`、`filename`、owner 信息写回同一个 config。 |
| `packages/cli/src/services/syncService.ts` | `ensureOwner` / `pull` 会把平台 owner 和资源信息写回 config。 |
| `packages/cli/src/services/draftService.ts` | 草稿冲突指纹 `draftSync` 写在 version config。 |

推论：继续修补旧 config 会把“用户希望发布什么”和“CLI 最近同步到了什么”越缠越紧；这是脚手架设计层面的错误边界。

### 2.2 Console 需要对齐的平台契约

| 证据 | 说明 |
|---|---|
| `packages/console/src/models/resourceCreatorPage/step1Effects.ts` | 创建资源时先用 `username/name` 预查重，但 `Resource.create` 只提交短 `name`、`resourceTypeCode`、`resourceTitle`。 |
| `packages/console/src/models/resourceCreatorPage/step2Effects.ts` | `createVersion` payload 包含 `resourceId`、`version`、`fileSha1`、`filename`、`dependencies`、`baseUpcastResources`、`authExcludedItems`、`inputAttrs`、`customPropertyDescriptors`、`description`。 |
| `packages/console/src/models/collectionManager/versionEffects.ts` | 合集发版通过 `Resource.updateCollection`，payload 包含目录合并、展示属性、依赖、授权排除、输入属性、自定义属性。 |
| `packages/console/src/pages/resource/sidebar/Sider/index.tsx` | `resourceOnline` 是 Console helper：读取资源信息和策略后调用 `Resource.update({ status: 1 })`，不是平台 endpoint。 |
| `packages/@freelog/tools-lib/src/service-API/resources.ts` | 平台 API 是 `Resource.create`、`createVersion`、`update`、`updateCollection` 等请求函数。 |

推论：CLI 应对齐请求字段、状态门禁和错误语义；交互应 CLI 化、声明式、可 CI 执行。

### 2.3 旧脚手架可借鉴但不能继承

| 可借鉴 | 不继承 |
|---|---|
| 字段枚举较全，尤其 version 的依赖、上抛、授权排除、自定义属性，collection 的展示字段。 | 可执行 TS/JS 配置、`userId: 0` 占位、批量 temp config、inquirer-only 流程、把平台缓存和发布意图写在同一个文件。 |

## 3. 目标文件结构

### 3.1 单品项目

```text
my-theme/
├── freelog.manifest.json        # 用户拥有，提交 git
├── .freelog/
│   └── state.json               # CLI 拥有，不提交 git
├── src/
└── dist/                        # manifest.version.filePath
```

`.gitignore` 应由 `init` 自动补齐：

```gitignore
.freelog/state.json
.freelog/cache/
.freelog/tmp/
```

### 3.2 合集项目

```text
my-collection/
├── freelog.manifest.json        # subject = "collection"
├── .freelog/state.json
└── chapters/
    ├── 01-intro/
    │   ├── freelog.manifest.json
    │   └── .freelog/state.json
    └── 02-chapter/
        ├── freelog.manifest.json
        └── .freelog/state.json
```

合集根只管理合集壳、目录草稿、合集发版表单；单品子目录仍按单品流程管理。

## 4. 用户 Manifest

### 4.1 设计原则

1. 只用数据格式，不执行用户代码。
2. 只放用户意图，不放平台同步状态。
3. 用 Zod 校验，错误要带 JSON path。
4. 带 `$schema`，方便 IDE 校验。
5. `resourceName` 在 manifest 中永远是短授权标识，不含 `username/`；完整名来自平台返回并存在 state。
6. `resourceId`、`userId`、`username`、`fileSha1`、`filename`、`draftSync` 不允许出现在 manifest。

### 4.2 单品 Manifest v1

```json
{
  "$schema": "https://freelog-cli.dev/schemas/freelog-manifest.schema.json",
  "schemaVersion": 1,
  "subject": "resource",
  "identity": {
    "name": "my-theme",
    "title": "my-theme",
    "resourceTypeCode": "theme"
  },
  "listing": {
    "intro": "",
    "coverImages": [],
    "tags": []
  },
  "version": {
    "version": "1.0.0",
    "description": "",
    "filePath": "dist",
    "runtimeVersion": "0.5",
    "dependencies": [],
    "baseUpcastResources": [],
    "authExcludedItems": [],
    "inputAttrs": [],
    "customPropertyDescriptors": []
  },
  "policies": []
}
```

### 4.3 合集 Manifest v1

```json

  "schemaVersion": 1,

    "version": "1.0.0",
    "description": "",

    "customPropertyDescriptors": []
  },
  "policies": []

```

### 4.4 字段归属

| 字段 | Manifest | State | 说明 |
|---|---:|---:|---|
| 短授权名、标题、类型 code | 是 | 否 | 用户创建意图 |
| listing intro / cover / tags | 是 | 可缓存平台快照 | manifest 是目标值，state 只记录上次平台快照 |
| version / description / filePath / runtimeVersion | 是 | 否 | 发版意图 |
| dependencies / baseUpcastResources | 是 | 可缓存解析结果 | publish payload 来源是 manifest |
| authExcludedItems / inputAttrs / customPropertyDescriptors | 是 | 否 | 嵌套字段必须走 schema |
| policies | 是 | 可缓存 policyId 映射 | policy text/status 是用户意图，policyId 是平台状态 |
| resourceId / full resourceName / owner | 否 | 是 | 平台事实 |
| fileSha1 / filename / lastPublishedVersion | 否 | 是 | CLI 计算或平台返回 |
| draftSync | 否 | 是 | 冲突检测状态 |

## 6. 命令设计

### 6.1 初始化

`init` 是脚手架命令，不调用平台创建 API。

```bash
freelog-cli init my-theme --scaffold runtime --template vite-vue-ts --resource-type <typeCode> --runtime 0.5 --pm pnpm --yes
freelog-cli init . --scaffold none --resource-type <typeCode>
freelog-cli init my-file --scaffold none --resource-type <typeCode>
freelog-cli init my-collection --scaffold collection --resource-type <typeCode>
```

职责：

1. 复制工程模板。
2. 渲染 EJS。
3. 写 `freelog.manifest.json`。
4. 写 `.freelog/state.json` 的空 state 与 scaffold 信息。
5. 写 `.gitignore`。
6. 可选安装依赖。

`init <name>` 创建新目录；`init .` 在已有项目或空目录中初始化 Freelog manifest/state，不复制工程模板，除非显式传 `--scaffold runtime|package` 且目标目录为空或可安全合并。

资源类型不应该要求普通使用者先去 Console 查 code。命令规则：

1. 传了 `--resource-type <code>`：直接校验 code 并写入 manifest。
2. 没传 `--resource-type` 且是交互终端：调用平台资源类型列表，让用户搜索/选择资源类型。
3. 没传 `--resource-type` 且是非交互终端或 `--yes`：exit 4，并提示 `type search` 或 `type list --json`。
4. `--scaffold collection` 只展示合集类型；`--scaffold runtime` 优先展示主题/插件等运行时类型；`--scaffold none` 展示可本地上传的单品类型。
5. 用户选择自定义类型时，若平台要求 `resourceTypeName`，CLI 继续询问或要求 `--type-name`。

### 6.2 单品主流程

```bash
freelog-cli login
freelog-cli create
freelog-cli publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

其中 `publish` 的语义是“创建正式版本”，对应 Console Step2 的 `Resource.createVersion`。它不要求资源已经有策略；策略只影响资源是否可以被授权/访问，以及后续 `online` 能否通过门禁。

`create`：

1. 读 manifest.identity。
2. 按 Console 规则净化短名。
3. 用当前登录 `username/name` 预查重。
4. 调 `Resource.create({ name, resourceTypeCode, resourceTypeName, resourceTitle })`。
5. 写 state.resource。

`publish`：

1. 读 manifest.version。
2. 从 state 取 resourceId。
3. 计算 SHA1，按资源类型决定是否打 zip。
4. 上传 storage。
5. 构造与 Console `createVersion` 同形 payload。
6. 调 `Resource.createVersion`。
7. 写 state.version。

`publish` 不检查策略数量，也不自动创建策略。若存在依赖，仍需按 Console 契约校验依赖授权；依赖授权失败可以阻断发版，但“本资源未配置策略”不能阻断发版。

`policy apply --from-file`：

1. 读用户显式指定的 policy.json。
2. 对每条策略调用 `Resource.update({ addPolicies })`。
3. 平台成功后刷新 `state.resource.policies`。
4. CLI 不内置策略 Builder，也不自动从 manifest.policies 提交。

`online`：

1. `Resource.info({ isLoadPolicyInfo: 1, isLoadLatestVersionInfo: 1 })`。
2. 无 latestVersion 直接失败。
3. 无启用策略直接失败，并提示 `policy apply --from-file` 或 Console。
4. 门禁通过后 `Resource.update({ status: 1 })`。

### 6.3 合集主流程

```bash
freelog-cli collection create
freelog-cli collection item add ./chapters/01-intro
freelog-cli collection item reorder --order-file order.json
freelog-cli collection publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

合集同理：`collection publish` 是提交合集版本/目录变更，对应 `Resource.updateCollection`，不因为合集自身没有策略而失败；合集上架才要求 latestVersion 与至少一条启用策略。

合集与单品共用 `create` / `policy` / `online` 的资源状态模型；区别在于：

1. `subject = "collection"`。
2. 目录草稿命令调用 catalogue draft API。
3. 发版调用 `Resource.updateCollection`。
4. 合集发版 payload 使用 manifest.collection 与 manifest.version 组合生成。

### 6.4 草稿

```bash
freelog-cli draft push
freelog-cli draft pull
freelog-cli draft discard --yes
freelog-cli draft push --collection
```

草稿冲突依据仍是规范化 draftData 指纹，但 `draftSync` 只写 `.freelog/state.json`。

`draft pull` 可以改 manifest，因为它是把平台草稿转成本地用户意图；但必须保留 `filePath`，并只覆盖 draftData 对应字段，不覆盖 state。

### 6.5 环境选择

CLI 只发布一个 npm 包。环境不是打包产物差异，而是运行时配置：

1. 默认 production。
2. `--test` / `--env test` 选择测试环境。
3. `--env dev` 只允许本地调试或内部使用，不应作为 npm 用户默认路径。
4. token 与 endpoint 写在用户级配置，不写入项目 manifest。

因此“发布线上交给测试使用”的方式是发布同一个 CLI 包，测试人员用 `freelog-cli --env test` 或用户级配置切到测试环境。

### 6.6 使用者视角的端到端流程

这一节是新脚手架的真实验收场景。目标用户不是在“配置 API”，而是在自己的电脑上把已有产物发布成 Freelog 资源。

#### 6.6.1 React 主题项目

用户已有 React 主题工程，CLI 负责创建 Freelog 资源、压缩构建产物目录、上传并发版。

```bash
cd my-react-theme
pnpm build
freelog-cli init . --scaffold none --resource-type <themeTypeCode> --runtime 0.5
freelog-cli create
freelog-cli publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

若用户从零创建工程：

```bash
freelog-cli init my-react-theme --scaffold runtime --template vite-react-ts --resource-type <themeTypeCode> --runtime 0.5
cd my-react-theme
pnpm build
freelog-cli create
freelog-cli publish
```

规则：

1. `manifest.version.filePath` 指向 `dist` 等构建产物目录。
2. `publish` 检测到资源类型需要目录包时，压缩 `filePath` 目录内容为临时 zip。
3. zip 文件名由短资源名和版本生成，例如 `my-react-theme-1.0.0.zip`。
4. 临时 zip 上传并计算 SHA1 后必须清理。
5. `publish` 不运行 `pnpm build`，构建职责留给项目脚本；后续可加显式 `publish --build`，但 P0 不做隐式构建。

#### 6.6.2 Vue 插件项目

Vue 插件与 React 主题使用同一套 runtime 模板池；差异只在平台 `resourceTypeCode` 和用户工程技术栈。

```bash
cd my-vue-widget
pnpm build
freelog-cli init . --scaffold none --resource-type <widgetTypeCode> --runtime 0.5
freelog-cli create
freelog-cli publish
```

规则同主题：运行时类资源必须有 `runtimeVersion`，否则 `publish` exit 4；非运行时资源不得误传 runtimeVersion。

#### 6.6.3 单个图片资源

```bash
mkdir cover-resource && cd cover-resource
freelog-cli init . --scaffold none --resource-type <imageTypeCode>
# 编辑 freelog.manifest.json: version.filePath = "../cover.png"
freelog-cli create
freelog-cli publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

规则：

1. 图片不是运行时目录包，`filePath` 必须指向具体文件。
2. `publish` 直接计算图片文件 SHA1、上传原文件、调用 `createVersion`。
3. CLI 应通过 `getResourceTypeInfoByCode` 校验资源类型支持本地上传、文件格式和大小。

#### 6.6.4 单个视频资源

```bash
mkdir video-resource && cd video-resource
freelog-cli init . --scaffold none --resource-type <videoTypeCode>
# 编辑 freelog.manifest.json: version.filePath = "../movie.mp4"
freelog-cli create
freelog-cli publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

规则：

1. 视频同样上传原文件，不压缩。
2. 文件大小、格式、是否支持下载/可选配置等以平台资源类型配置为准。
3. Console 目前存在视频封面上传入口，但 `createVersion` 中视频封面字段仍是 TODO；CLI P0 不伪造该字段，只支持 listing cover。

#### 6.6.5 图片文件夹用于合集

用户有一个扁平图片目录，希望每张图片成为一个单品，再组合成一个合集。

推荐命令面：

```bash
freelog-cli init photo-album --scaffold collection --resource-type <collectionTypeCode>
cd photo-album
freelog-cli collection create
freelog-cli collection item import-dir ../photos --resource-type <imageTypeCode> --title-prefix "照片 " --item-policy-file ./item-policy.json
freelog-cli collection publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

`collection item import-dir` 是一个组合命令，应等价于：

1. 读取 `../photos` 的扁平文件列表。
2. 对每个文件生成子资源 manifest/state。
3. 为每个文件创建资源壳并创建 `1.0.0` 正式版本。
4. 把成功创建的子资源加入合集目录草稿。
5. 汇总成功/失败；成功项保留，失败项可重试。

不推荐让用户手动循环几十次 `init/create/publish/item add`。那是实现细节，不是好用的脚手架体验。

这里的产品语义必须明确：图片文件夹不是作为一个 zip 文件发布成合集；文件夹中的每个图片文件都是一个独立单品资源，合集资源只保存目录关系和展示设置。

#### 6.6.6 视频文件夹用于合集

视频文件夹与图片文件夹同一模型：

```bash
freelog-cli init video-album --scaffold collection --resource-type <collectionTypeCode>
cd video-album
freelog-cli collection create
freelog-cli collection item import-dir ../videos --resource-type <videoTypeCode> --title-prefix "视频 " --item-policy-file ./item-policy.json
freelog-cli collection publish
freelog-cli policy apply --from-file ./policy.json
freelog-cli online
```

区别：

1. 单个视频文件大小限制通常高于图片，应完全以平台 `resourceConfig.fileMaxSize` / `fileMaxSizeUnit` 为准。
2. 视频文件上传耗时较长，命令必须输出进度或阶段状态；`--json` 下输出结构化 item 状态。
3. 部分失败时，不回滚已创建的资源和已加入的目录项，返回失败清单供用户重试。

视频文件夹同样不是整体打包上传；每个视频文件是一个独立视频资源，合集收录这些视频资源。

### 6.7 文件处理与资源类型校验

CLI 发布文件前必须读取平台资源类型配置：

```ts
FServiceAPI.Resource.getResourceTypeInfoByCode({ code: resourceTypeCode })
```

校验规则：

1. `fileCommitMode` 是官方 bit 能力，必须包含本地上传位 `1`；不支持本地上传的类型，CLI 拒绝 `publish` 或 `collection item import-dir`。
2. `formats` 存在时，`filePath` 后缀必须匹配。
3. `fileMaxSize` / `fileMaxSizeUnit` 存在时，文件大小必须小于等于平台限制。
4. 是否打 zip 不能只靠中文类型名长期硬编码；P0 可保留 `主题/插件/软件库/theme/widget/plugin` 兜底，但最终应由平台类型配置或 CLI 类型能力表决定。
5. `supportOptionalConfig` 是官方 `1/2` 枚举，只有 `2` 表示支持；不支持时 manifest 中不得声明自定义属性配置，否则应 exit 4 并指出 JSON path。

### 6.8 交互与非交互命令规则

CLI 的默认体验应是“人能顺着提示走，脚本能完全靠 flags 跑”。同一个命令不得在 CI 里突然等待用户输入。

#### 6.8.1 资源类型发现命令

新增类型发现命令：

```bash
freelog-cli type list
freelog-cli type search 图片
freelog-cli type list --subject resource --json
freelog-cli type list --subject collection --json
freelog-cli type info <resourceTypeCode> --json
```

输出字段至少包含：

```json
{
  "code": "image",
  "name": "图片",
  "labels": ["图片"],
  "subjectType": 1,
  "fileCommitMode": 3,
  "formats": [".jpg", ".jpeg", ".png"],
  "fileMaxSize": 200,
  "fileMaxSizeUnit": 1,
  "supportDownload": true,
  "supportEdit": false,
  "supportOptionalConfig": 2
}
```

#### 6.8.2 `init` 交互流

当用户执行：

```bash
freelog-cli init my-resource
```

交互顺序：

1. 选择脚手架类型：runtime / package / none / collection。
2. 若 runtime 或 package：选择工程模板。
3. 选择平台资源类型。
4. 若 runtime：选择运行时档位，默认 CLI 支持的最新稳定档。
5. 输入或确认资源标题，默认目录名。
6. 输入或确认短授权名，默认按 Console 规则净化目录名。
7. 确认生成 `freelog.manifest.json` 与 `.freelog/state.json`。

非交互规则：

```bash
freelog-cli init my-theme --scaffold runtime --template vite-react-ts --resource-type <code> --runtime 0.5 --yes
```

`--yes` 表示接受默认值，但不能替用户猜资源类型、模板或运行时档位。缺少这些关键字段时必须失败。

#### 6.8.3 `create` 交互流

`create` 优先读 manifest。manifest 中缺 `identity.resourceTypeCode` 时：

1. 交互终端：进入资源类型选择。
2. 非交互：exit 4。

创建前必须展示将提交的平台请求摘要：

```text
资源名: alice/my-theme
标题: my-theme
类型: 主题 (theme)
```

交互终端可确认；`--yes` 或非交互直接执行。

#### 6.8.4 `collection item import-dir` 交互流

当用户执行：

```bash
freelog-cli collection item import-dir ../photos
```

交互顺序：

1. 选择文件夹内单品资源类型，例如图片或视频。
2. 显示文件数量、总大小、平台大小/格式限制。
3. 显示将创建的前 5 个资源标题和短授权名预览。
4. 用户确认后批量创建、上传、发布、加入目录草稿。

非交互必须传：

```bash
freelog-cli collection item import-dir ../photos --resource-type <imageTypeCode> --item-policy-file ./item-policy.json --yes
```

#### 6.8.5 交互边界

| 场景 | 交互终端 | 非交互 / `--yes` |
|---|---|---|
| 缺资源类型 | 可选择 | exit 4 |
| 缺模板 | 可选择 | exit 4 |
| 缺 runtimeVersion 且类型需要运行时 | 可选择 | exit 4 |
| 短授权名冲突 | 可重新输入 | exit 4 |
| publish 缺 filePath | 可输入并写 manifest | exit 4 |
| online 缺策略 | 不自动创建，提示 `policy apply` | exit 4 |
| 删除草稿/覆盖草稿 | 需要确认 | 需要 `--yes` 或 `--force --yes` |

## 7. 模板设计

模板包仍保留当前结构：

```text
packages/templates/<id>/
├── package.json
├── template.manifest.json
└── template/
```

但 `template.manifest.json` 只服务 CLI 选模板：

```json
{
  "id": "vite-vue-ts",
  "npmName": "@freelog-cli/template-vite-vue-ts",
  "title": "Vite Vue TS",
  "tags": ["runtime", "theme", "widget"],
  "version": "0.5.2",
  "runtimeVersions": ["0.5"],
  "freelogRuntimeRange": "^5.0.7",
  "filePath": "dist",
  "startCommand": "pnpm start",
  "ejsIgnore": ["**/public/**"]
}
```

模板不携带 `freelog.resource.config.*`。`init` 根据模板 manifest + 用户 flags 生成 `freelog.manifest.json`。

## 9. 验收矩阵

| 验收项 | 标准 |
|---|---|
| 不执行用户代码 | `init` 后项目内没有 `freelog.*.config.ts/js`；CLI 不依赖 `jiti` 加载用户配置。 |
| Manifest / State 分离 | manifest 不含 `resourceId`、`userId`、`username`、`fileSha1`、`filename`、`draftSync`；state 不含用户描述性发布意图。 |
| create 对齐 Console | 查重用 `username/name`，创建只传短 `name`。 |
| init 当前目录 | 已有 React/Vue 项目和单文件目录可通过 `init .` 接入 Freelog，不强制搬目录。 |
| publish 对齐 Console | createVersion payload 字段与 Console step2 同形。 |
| collection publish 对齐 Console | updateCollection payload 字段与 Console collection version 同形。 |
| publish 不绑定策略 | 单品/合集没有策略时仍可发布正式版本；缺策略只阻断 `online`。 |
| online 对齐 Console | 必须检查 latestVersion 与启用策略；通过后只调用 `Resource.update({ status: 1 })`。 |
| 资源类型校验 | 主题/插件发布目录 zip；图片/视频发布原文件；格式与大小按平台资源类型配置校验。 |
| 文件夹合集 | 图片/视频文件夹能用一条 `collection item import-dir` 批量创建单品、发布首版并加入合集，再 `collection publish`。 |
| 资源类型选择 | 用户可交互选择资源类型；CI 可通过 `type list --json` 获取 code 后全 flags 执行。 |
| 浏览器端无改造 | console/components 等浏览器 workspace 不需要改。 |
| 单 npm 包可测 | 同一个 CLI 包支持 `production` 与 `test` 运行时环境选择。 |
| 测试覆盖 | manifest schema、state 写回、create、publish、draft push/pull、policy apply、online gate、collection publish 均有单测。 |

## 10. 推荐执行顺序

1. 先落 `manifest/state` schema 与读写层。
2. 改 `init`，让新项目只生成 `freelog.manifest.json` + `.freelog/state.json`。
3. 改 `create` / `pull` / `ensureOwner`，把平台事实写 state。
4. 改 `publish` / `draft` / `dep`，所有发布意图从 manifest 读写。
5. 改 `collection`，确保合集目录草稿、发版表单、策略都走新上下文。
6. 删除旧 config 层、旧文档口径和 `jiti` 依赖。
7. 跑 `pnpm test`、`pnpm exec tsc --noEmit -p tsconfig.json`、`pnpm build`。

## 11. ADR

**Decision**：采用 `freelog.manifest.json` + `.freelog/state.json`，删除旧 config 兼容。

**Drivers**：

1. 新脚手架没有旧项目兼容负担。
2. CLI 必须可 CI 执行、可审计、可复现。
3. Console 对齐点是平台请求契约，不是 UI 状态机。

**Alternatives considered**：

| 方案 | 结论 |
|---|---|
| 继续修补 `freelog.*.config.ts/js` | 否决。会继续执行用户代码，并混淆意图与状态。 |
| 双读旧 config + 新 manifest | 否决。适合迁移旧用户，不适合无旧负担的新脚手架。 |
| YAML 作为主格式 | 暂缓。可读性好，但 JSON + `$schema` + Zod 对 CLI、CI、IDE 更稳定。 |

**Consequences**：

1. 代码改动会大，但边界更清晰。
2. 文档必须统一删除旧 config 口径。
3. 现有围绕 `writeShell/read.ts` 的测试要重写为 manifest/state 测试。

**Follow-ups**：

1. 可后续增加 `freelog-cli manifest validate`。
2. 可后续增加 `freelog-cli plan` 输出 manifest 与平台差异。
3. 可后续增加 `freelog.workspace.json` 支持多资源批量编排。
