# 资源生命周期拓扑设计

## 1. 目的

本文用拓扑方式定义新 CLI 的资源生命周期：哪些实体是节点，哪些命令是边，哪些字段能改，哪些字段只能新建，哪些状态写 manifest，哪些状态写 state。

原则：

1. `manifest` 是用户意图。
2. `state` 是 CLI 对平台事实的本地镜像。
3. `platform` 是最终权威。
4. `create`、`publish`、`update`、`draft`、`online` 是不同边，不能互相代替。
5. 单品与合集共用资源壳、策略、上下架模型；版本与目录模型不同。

## 2. 拓扑节点

```text
User Workspace
  ├─ source/build files
  ├─ freelog.manifest.json
  └─ .freelog/state.json

CLI Runtime
  ├─ auth/env
  ├─ resource type cache
  ├─ file processor
  ├─ payload builders
  └─ conflict detector

Freelog Platform
  ├─ Resource Shell
  ├─ Resource Listing
  ├─ Resource Version
  ├─ Version Draft
  ├─ Policy
  ├─ Dependency/Auth Tree
  ├─ Contract
  ├─ Collection Catalogue Draft
  ├─ Collection Version/Form
  ├─ Collect Rules
  └─ Storage Object
```

## 3. 不可变与可变边界

| 字段/实体 | 新建后是否可改 | 修改入口 | 说明 |
|---|---:|---|---|
| 短授权名 `identity.name` | 否 | 仅 create 前 | create 后平台返回完整 `resourceName`，写 state。 |
| `resourceTypeCode` | 否 | 仅 create 前 | 类型决定文件能力和版本 payload，创建后不可变。 |
| `resourceTitle` | 是 | `update` / `collection update` | create 时初值，后续 listing 更新。 |
| `intro` / `coverImages` / `tags` | 是 | `update` / `collection update` | listing 字段。 |
| resource status | 是 | `online` / `offline` | 不允许普通 `update` 直接改 status。 |
| 策略新增与启停 | 是 | `policy apply` / `policy set` | `policy apply` 通过 `addPolicies` 新增；`policy set` 通过 `updatePolicies(policyId,status)` 启停。 |
| 正式版本号 | 否 | `publish` 新增 | 已发布版本不能换文件，只能新增版本或编辑元数据。 |
| 已发布版本描述 | 是 | `version edit` | `updateResourceVersionInfo`，不改文件 SHA1。 |
| 发版意图 | 是 | 编辑 manifest / `version set` | 未发布前本地意图可改。 |
| 平台发版草稿 | 是 | `draft push/pull/discard` | 与正式版本分离。 |
| 依赖声明 | 是 | manifest / `dep add/remove/update` | 随下一次 publish 生效。 |
| 依赖合约 | 是 | `dep auth` / Console | 授权结果是平台事实。 |
| 合集目录草稿 | 是 | `collection item *` | 独立于合集发版表单草稿。 |
| 合集正式目录/版本 | 是 | `collection publish` 新增/合并 | `updateCollection`。 |
| 自动收录规则 | 是 | `collection collect-rules set` | 不等同目录草稿。 |

## 4. 单品拓扑

### 4.1 初始化边

```text
source/build files + user input
  -- init -->
freelog.manifest.json + .freelog/state.json(empty)
```

输入：

1. `--scaffold`
2. `--template`
3. `--resource-type`
4. `--runtime`
5. `--resource-name` / 目录名默认

输出：

1. `manifest.identity`
2. `manifest.version`
3. `.freelog/state.json` 空壳
4. `.gitignore`

规则：

1. 不调用平台 create。
2. 不写 resourceId。
3. TTY 可选择资源类型；非交互必须给 `--resource-type`。

### 4.2 创建资源壳边

```text
manifest.identity + auth.username
  -- create -->
Platform Resource Shell
  -- write-back -->
state.resource
```

平台调用：

```text
Resource.info(username/name)   # 查重
Resource.create({ name, resourceTypeCode, resourceTypeName?, resourceTitle })
Resource.getResourceTypeInfoByCode({ code })
```

写入：

1. `state.resource.resourceId`
2. `state.resource.resourceName`
3. `state.resource.resourceType`
4. `state.resource.resourceTypeCode`
5. `state.resource.owner.userId`
6. `state.resource.owner.username`

不写入：

1. 不把 resourceId 写 manifest。
2. 不创建版本。
3. 不创建策略。
4. 不上架。

### 4.3 更新基础信息边

```text
manifest.listing + state.resource.resourceId
  -- update -->
Platform Resource Listing
  -- write-back -->
manifest.resource + state.resource/sync
```

命令：

```bash
freelog-cli update --title "新标题" --intro "..." --cover ./cover.png --tags "a,b"
```

平台调用：

```text
Resource.update({ resourceId, resourceTitle?, intro?, coverImages?, tags? })
```

规则：

1. 可只更新部分字段。
2. `cover` 本地文件先上传或解析为 URL，再转 `coverImages`。
3. 不允许通过此命令传 `status`。
4. 不触碰版本、策略、草稿。
5. 这是唯一会把本地 listing 意图推到平台并同步更新 manifest.resource 的命令。

### 4.4 更新本地发版意图边

```text
manifest.version
  -- version set / dep add / manifest edit -->
manifest.version'
```

命令：

```bash
freelog-cli version set --version 1.1.0 --description "..." --file ./dist
freelog-cli dep add <resourceId> --range "^1.0.0"
```

规则：

1. 只改 manifest。
2. 不调用平台草稿 API。
3. 不改 `state.version.draftSync`。
4. 不上传文件。
5. 依赖变更只随下一次 `publish` 或 `draft push` 生效。

说明：现有命令名 `updateVersion` 容易误解为“更新平台版本”，新命令面建议改为 `version set`；若保留别名，只作为兼容内部开发期别名，不作为最终文档主命令。

### 4.5 发布正式版本边

```text
manifest.version + state.resource + local file
  -- publish -->
Storage Object + Platform Resource Version
  -- write-back -->
state.version
```

平台调用：

```text
Resource.getResourceTypeInfoByCode({ code })
Storage.fileIsExist / Storage.uploadFile
Resource.authTree({ resourceId, version })    # 有 dependencies 时
Resource.createVersion(payload)
```

payload 对齐 Console `createVersion`：

```json
{
  "resourceId": "...",
  "version": "1.1.0",
  "fileSha1": "...",
  "filename": "...",
  "description": "...",
  "dependencies": [],
  "baseUpcastResources": [],
  "authExcludedItems": [],
  "inputAttrs": [],
  "customPropertyDescriptors": [],
  "runtimeVersion": "0.5"
}
```

规则：

1. 版本必须大于平台 latestVersion。
2. 本资源没有策略不能阻断 publish。
3. 依赖授权未完成可以阻断 publish，exit 5。
4. 主题/插件/软件库等目录包需要 zip；图片/视频/普通文件上传原文件。
5. 文件能力、格式、大小以平台资源类型配置校验。
6. 成功后写 `state.version.fileSha1`、`filename`、`versionId`、`lastPublishedVersion`。

### 4.6 编辑已发布版本元数据边

```text
state.resource.resourceId + version + description
  -- version edit -->
Platform Resource Version metadata
```

平台调用：

```text
Resource.updateResourceVersionInfo({ resourceId, version, description })
```

规则：

1. 不改文件。
2. 不改 SHA1。
3. 不改依赖。
4. 只允许平台支持的元数据字段。

### 4.7 发版草稿边

```text
manifest.version
  -- draft push -->
Platform Version Draft

Platform Version Draft
  -- draft pull -->
manifest.version

Platform Version Draft
  -- draft discard -->
state.version.draftSync cleared
```

规则：

1. `draft push` 把本地发版意图转换为 Console 同形 draftData。
2. `draft pull` 用平台草稿更新 manifest.version，但保留本地 `filePath`。
3. `state.version.draftSync` 记录 fingerprint 与远端 updateDate。
4. `version set` / `dep add` 不改 `draftSync`，以便发现本地未 push 变更。
5. 冲突时 exit 3，除非 `--force`。

### 4.8 策略边

```text
policy.json / manifest.policies
  -- policy apply -->
Platform Policies
  -- write-back -->
state.resource.policies
```

平台调用：

```text
Resource.update({ resourceId, addPolicies })
Resource.update({ resourceId, updatePolicies })
```

规则：

1. `publish` 不依赖本资源策略。
2. `online` 依赖至少一条启用策略。
3. 已上架资源不允许关闭最后一条启用策略。
4. `policy apply --from-file` 调 `addPolicies` 新增策略；`policy set` 调 `updatePolicies(policyId,status)` 启停策略。
5. Console/tools-lib 稳定契约没有“通过 Resource.update 修改策略正文/名称”的入口，CLI 不伪造该能力；需要改正文时回 Console 或新增策略。
6. CLI 不实现策略 Builder；manifest.policies 只作为可选声明模型保留，不自动提交。

### 4.9 上下架边

```text
state.resource.resourceId
  -- online -->
Resource.info(gates) -> Resource.update({ status: 1 })

state.resource.resourceId
  -- offline -->
Resource.update({ status: 4 })
```

online 门禁：

1. 有 latestVersion。
2. 至少一条启用策略。
3. 非冻结。

规则：

1. `resourceOnline` 是 Console helper，不是平台 endpoint。
2. CLI 不在 online 时自动生成策略。
3. soft status update 不暴露给普通 `update`。

## 5. 合集拓扑

### 5.1 创建合集壳边

```text
manifest(subject=collection).identity + auth.username
  -- collection create -->
Platform Resource Shell(subjectType=4)
  -- write-back -->
state.resource
```

规则同单品 create，但 subject 是合集。

### 5.2 更新合集基础信息边

```text
manifest.listing + manifest.collection.display
  -- collection update -->
Platform Resource Listing + catalogueProperty
```

平台调用：

```text
Resource.update({ resourceId, resourceTitle?, intro?, coverImages?, tags? })
Resource.updateCollection({ resourceId, catalogueProperty? })
```

规则：

1. listing 和展示设置可以同一命令提交。
2. 不合并目录草稿。
3. 不发布合集版本。
4. 不上下架。

### 5.3 合集目录草稿边

```text
item resourceId/path
  -- collection item add/remove/update/reorder -->
Platform Collection Catalogue Draft
  -- write-back -->
state.collection.catalogueDraftSnapshot
```

平台调用：

```text
Resource.addResourceItems_Draft
Resource.deleteCollectionItems_Draft
Resource.updateCollectionItemsInfo_Draft
Resource.setCollectionItemsSortID_Draft / reorderCollectionItems_Draft
```

规则：

1. `collection item add <path>` 读取子项目 state.resource.resourceId。
2. `collection item add <resourceId>` 允许加入已发布平台资源。
3. 目录草稿不是发版表单草稿。
4. 目录草稿必须通过 `collection publish` 合并到正式合集。

### 5.4 文件夹导入合集边

```text
folder files
  -- collection item import-dir -->
many Resource Shells + many Resource Versions + Collection Catalogue Draft
```

组合边：

1. 对每个文件执行单品 create。
2. 对每个文件执行单品 publish 首版。
3. 对成功项执行 collection item add。

规则：

1. 文件夹不作为一个 zip 发布。
2. 每个文件是独立单品资源。
3. 图片文件夹和视频文件夹只是同一拓扑的不同 item type。
4. 部分失败不回滚成功项。

### 5.5 合集发布边

```text
manifest.collection.description + catalogue draft
  -- collection publish -->
Platform Collection Version/Form
  -- write-back -->
state.resource.latestVersion + state.collection.catalogueDraft
```

平台调用：

```text
Resource.getCollectionItemsAuth_Draft
Resource.updateCollection(payload)
```

payload 对齐 Console `updateCollection`：

```json
{
  "resourceId": "...",
  "description": "...",
  "catalogueProperty": {},
  "dependencies": [],
  "baseUpcastResources": [],
  "authExcludedItems": [],
  "inputAttrs": [],
  "customPropertyDescriptors": [],
  "isMergeCatalogueDraft": 1
}
```

规则：

1. 合集没有策略不能阻断 `collection publish`。
2. 合集 item 授权缺口可以阻断 publish，exit 5。
3. `isMergeCatalogueDraft` 只在明确发布目录变更时传 1。

### 5.6 合集发版表单草稿边

```text
manifest.collection + manifest.version
  -- draft push --collection -->
Platform Version Draft(collection form)
```

规则：

1. 这是发版表单草稿，不是目录草稿。
2. 与 `collection item *` 的 catalogue draft 分离。
3. 冲突检测写 `state.collection.draftSync`，但 subject=collection。

### 5.7 自动收录 / RSS 边

```text
rules/rss input
  -- collection collect-rules / rss -->
Platform Collect Rules / RSS Binding
```

平台调用：

```text
Resource.setCollectRules
Resource.getCollectionCollectRules
Rss.sendVerificationCode
Rss.bindRssFeed
Rss.syncBinding
```

规则：

1. 自动收录规则不等同手动目录草稿。
2. RSS 验证码来自邮箱，不能纯自动化。
3. RSS 同步可能改变目录，应通过 status/pull 反映平台事实。

## 6. Pull / Status 拓扑

### 6.1 Pull

```text
Platform Resource/Version/Collection facts
  -- pull -->
state + explicit manifest fields
```

规则：

1. 平台 owner、resourceId、完整 resourceName 写 state。
2. 默认只刷新 state，不覆盖 manifest.resource。
3. `pull --apply-listing` 才把平台 listing 写回 manifest，作为用户当前意图基线。
4. latestVersion / status / policies 映射写 state。
5. `draft pull` 才写 version draft 字段；普通 pull 不把正式版文件路径乱写成本地 filePath。
6. 不用远端整对象覆盖 manifest。
7. `ensureSynced` 只能自动刷新 state；不能因为平台 listing drift 就静默改 manifest。
8. `pull --apply-listing` 使用三方判断：`state.sync.listingFingerprint` 是上次平台 listing 基线；若 manifest 相对基线未改动，可直接采用平台 listing；若 manifest 和平台都改过同字段，exit 3，除非 `--force`。

### 6.2 Status

```text
manifest + state + Platform info + drafts
  -- status -->
human/json report
```

必须报告：

1. 登录账号与 owner 是否匹配。
2. manifest 是否通过 schema。
3. state 是否绑定 resourceId。
4. 平台 latestVersion / status。
5. 本地发版意图是否高于 latest。
6. 平台发版草稿是否存在。
7. `draftSync` 是否对齐。
8. online 门禁是否满足。
9. 合集目录草稿是否存在未发布变更。

|---|---|---|---|---|

| `type list/search/info` | 类型发现 | platform types | 可缓存 | resourceTypes / getInfoByCode |
| `create` | 创建资源壳 | manifest.identity + auth | state.resource | info + create + getTypeInfo |

| `dep auth` | 依赖签约 | manifest.dependencies + policy map | 平台合约事实；本地不维护 contract state | batchCreateContracts + authTree |
| `publish` | 发布正式版本 | manifest.version + state + files | state.version | upload + createVersion |
| `version edit` | 编辑已发布版 | state + flags | state snapshot | updateResourceVersionInfo |
| `draft push` | 推发版草稿 | manifest.version + state | state.version.draftSync | saveVersionsDraft |

| `collection create` | 创建合集壳 | manifest.identity + auth | state.resource | info + create |
| `collection update` | 更新合集信息/展示 | manifest/listing/display | manifest + state snapshot | update + updateCollection |
| `collection version set` | 更新合集发布说明意图 | flags + manifest.collection | manifest.collection.description | 无 |

| `collection rss` | RSS | feed/code + state | state.rss snapshot | rss APIs |

## 8. 新建与更新分层

### 8.1 新建类命令

| 命令 | 创建什么 | 不创建什么 |
|---|---|---|
| `init` | 本地 manifest/state | 平台资源 |
| `create` | 平台资源壳 | 版本、策略、上架 |
| `publish` | 正式版本 | 策略、上架 |
| `policy apply` | 策略 | 版本 |
| `collection create` | 合集壳 | 目录、版本、策略 |
| `collection item import-dir` | 多个单品资源和版本、目录草稿项 | 合集正式发布、合集策略、合集上架 |
| `collection publish` | 合集版本/正式目录 | 合集策略、合集上架 |

### 8.2 更新类命令

| 命令 | 更新什么 | 不更新什么 |
|---|---|---|
| `update` | resource listing | version / policy / status |
| `version set` | 本地下一版意图 | 平台正式版 |
| `version edit` | 已发布版本描述等元数据 | 文件 SHA1 / 依赖 |
| `dep add/remove/update` | 下一版依赖意图 | 当前正式版本 |
| `draft push/pull` | 平台草稿 / manifest version | 正式版本 |
| `policy set` | 策略启停 | listing / version |
| `online/offline` | status | listing / version |
| `collection update` | 合集 listing/display | 目录草稿合并 |
| `collection item *` | 目录草稿 | 合集正式版本 |
| `collection collect-rules` | 自动收录规则 | 手动目录项 |

## 9. 关键拓扑约束

1. `resourceTypeCode` 是创建壳前的必需节点；创建后只能作为平台事实读取。
2. `publish` 依赖 `state.resource.resourceId`，因此不能跳过 create，除非先 `pull` 绑定已有资源。
3. `publish` 依赖本地文件和 storage，但不依赖本资源策略。
4. `online` 依赖 latestVersion 和启用策略，但不创建版本。
5. `collection publish` 依赖合集壳和目录草稿/manifest，但不依赖合集策略。
6. `collection item import-dir` 是组合边，必须可恢复、可重试、可报告部分失败。
7. `pull` 不得覆盖用户未发布意图；只能写 state 和明确选择的 manifest 基线字段。
8. `draftSync` 只属于 state，不能出现在 manifest。
9. 所有平台写命令必须先校验 owner；加入他人已发布资源到合集是例外，因为那是引用，不是修改他人资源。

## 10. 验收

| 场景 | 验收标准 |
|---|---|
| 新建主题 | `init -> build -> create -> publish` 生成 zip 并 createVersion；无策略也可 publish。 |
| 更新主题基础信息 | `update --title/intro/cover/tags` 只调用 Resource.update listing 字段。 |
| 发主题新版本 | `version set -> publish` 新增正式版本，不改变 listing/status。 |
| 编辑已发布版本说明 | `version edit` 调 updateResourceVersionInfo，不上传文件。 |
| 单图片 | 原文件上传，格式/大小按资源类型校验。 |
| 单视频 | 原文件上传，支持大文件进度，格式/大小按资源类型校验。 |
| 图片文件夹合集 | `collection item import-dir` 创建多个图片单品、发布首版、加入目录草稿；`collection publish` 后合集有正式目录。 |
| 视频文件夹合集 | 同图片文件夹，但大文件进度和部分失败报告必须可用。 |
| 合集基础信息更新 | `collection update` 不触碰目录草稿发布状态。 |
| 合集目录更新 | `collection item add/remove/reorder -> collection publish` 才进入正式合集。 |
| 策略与上架 | 无策略可 publish；无启用策略不可 online。 |
| Console 交替 | Console 草稿存在时 `status` 可见，`draft pull/push --force/discard` 决策明确。 |
