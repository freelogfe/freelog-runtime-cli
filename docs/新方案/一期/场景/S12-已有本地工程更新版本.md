# S12 · 已有本地工程更新版本

> **文档角色：** 已绑定本地工程日常更新、发新版、release 的体验设计。总规则见 [../02-CLI体验拓扑设计.md](../02-CLI体验拓扑设计.md)。

最后更新：2026-08-28

---

## 1. 用户目标

用户已经有 `freelog.manifest.json` 和 `.freelog/state.json`。他修改了文件或代码，希望安全发布新版本，或只维护已发版说明。

---

## 2. 启动时应展示

`freelog-cli start` 或 `status` 在已有工程中必须先告诉用户：

- 当前 env、账号、凭据来源；
- resourceId / resourceName / owner；
- 平台 latestVersion；
- manifest 当前 version；
- filePath 是否存在；
- listing 是否与平台漂移；
- 是否有未发布草稿、依赖未授权、策略/online 问题。

Console 对齐来自 sidebar 与 versionCreator：listing 维护、已发版信息维护、发新版、策略和上下架是不同入口。CLI 向导必须把这些入口解释成用户动作，不得把“改已发版说明”和“重新发布文件”混为一个 publish。

---

## 3. TTY 连续向导

| checkpoint | 用户看到 | 输入 | 副作用 | 失败处理 |
|---|---|---|---|---|
| U1 识别工程 | 当前资源摘要 | 继续/退出 | 无 | manifest 损坏给修复位置 |
| U2 选择动作 | 发新版、改已发版说明、改 listing、策略/上下架 | 选择 | 无 | 不确定时给解释 |
| U3 版本计划 | 当前 latest vs manifest version | bump/手填/保持 | 写 manifest | 同版本冲突需解释 |
| U4 构建 | build 命令/产物路径 | build/跳过 | 本地 build | 失败不写平台 |
| U5 预检 | 完整发布意图指纹 | confirm | 无 | listing/依赖/版本失败先处理 |
| U6 发版 | upload/createVersion | 等待 | 写平台/state | 同版本同意图恢复；不同意图冲突 |
| U7 续接 | online/加入合集/结束 | 选择 | 确认后写 | 给命令 |

---

## 4. 关键分叉

| 用户想法 | CLI 应引导 |
|---|---|
| “我改了代码，要发新版” | build → publish/release |
| “我只改版本说明” | `version edit`，不重新发文件 |
| “我只改封面/简介/标签” | `update`，不是 publish |
| “我想上线” | 策略模板/启用策略/online 检查 |
| “平台被别人改了” | diff/pull/apply-listing，而不是覆盖 |

---

## 5. AI/CI 等价命令

```bash
freelog-cli status --json --env <env>
freelog-cli validate --for publish --json --env <env>
freelog-cli release --build-cmd "pnpm build" --bump patch --yes --json --env <env>
freelog-cli online --yes --json --env <env>
```

---

## 6. 回归到总设计

已有工程更新场景要求：

- `status` 不是调试命令，而是用户继续工作的入口；
- `release` 要把 build/package/upload/platform write 阶段说清；
- 版本恢复必须比较完整发布意图，不只看 SHA。
