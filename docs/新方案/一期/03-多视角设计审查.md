## 1. 当前结论

当前设计已经完成“总拓扑 + S01–S14 场景分册”的基础拆分，能进入多视角评审；但不能因为有了目录就说已经完美。CLI 脚手架体验要达到最佳实践，必须每次按本文从多个角度回扫：

```text
单场景可走通
  ≠ 普通用户舒服

  ≠ 开发人员能稳定实现
  ≠ 与 Console 业务细节完全对齐
```

因此重构前的设计完成标准是：每个场景都通过 §3 的视角审查，并且所有重复问题已经回收到 [02-CLI体验拓扑设计](./02-CLI体验拓扑设计.md)。

## 3. 多视角审查矩阵

### 3.1 AI / CI 视角

AI/CI 不读人类长文案，也不能卡在交互里。每个场景必须回答：

| 审查问题 | 通过标准 |
|---|---|
| 非 TTY 缺参数会怎样？ | code 4 + hint；不进入 prompt |
| 写操作是否需要显式 env / yes？ | 必须；production fallback 不发请求 |
| 输出能否机器判断？ | `--json` stdout 只有 envelope；长任务 NDJSON |
| 失败能否自动处理？ | code 2/3/4/5 语义稳定；details 可解析 |
| 重试会不会重复创建远端？ | 幂等恢复或明确冲突；unknown 停止 |
| 需要浏览器动作时怎么办？ | code 5 + `actionUrl/contractsUrl/nextCommand` |

重点回扫场景：S07、S10、S12、S13、S14。

### 3.2 产品经理视角

产品视角不只看“功能有无”，而是看用户心智是否被正确组织。

| 审查问题 | 通过标准 |
|---|---|
| 用户第一屏是否按“我手里有什么”组织？ | 主题、插件、package、普通文件、目录、批量、合集、已有资源、session/studio 都可发现 |
| 是否把 Console 业务和 CLI 体验分开？ | 结果、字段、流程对齐；交互可以 CLI 化 |
| 是否解释清楚 CLI 的独有价值？ | 模板、build、压缩、batch report、AI/CI、恢复是一等能力 |
| 是否避免错误模型？ | 目录整体 zip / 批量拆资源 / 合集策展必须分清 |
| 是否避免宣传未签字能力？ | ENV 证据缺口只写验证报告，不削弱设计 |

重点回扫场景：S01–S05、S08、S09。

### 3.3 普通用户视角

普通用户不应先学内部 API。

| 审查问题 | 通过标准 |
|---|---|
| 能否输入一个入口命令开始？ | `freelog-cli` / `freelog-cli start` 是目标主入口 |
| 是否必须记住命令链？ | 不必须；显式命令只是 checkpoint |
| 类型选择是否能一级级浏览？ | 默认逐级，搜索只是快捷入口 |
| 每一步是否知道会不会写平台？ | 写前 preflight；取消不写平台 |
| 成功后是否知道下一步？ | 下一步命令在成功摘要里 |
| 失败时是否能继续？ | 错误说明原因、当前状态和恢复路径 |

重点回扫场景：S01、S02、S04、S05、S08、S13、S14。

### 3.4 前端/工程型资源开发者视角

主题、插件、package 是脚手架体验的核心，不是模板小功能。

| 审查问题 | 通过标准 |
|---|---|
| 主题和插件是否有独立入口？ | 第一屏分别出现；文案不混用 |
| 技术模板和平台资源类型是否区分？ | runtime/package 模板只是本地工程；平台 leaf 单独确认 |
| build 失败是否停在本地？ | 不进入 upload/createVersion |
| dist zip 是否可预期？ | ignore、zip 文件名、SHA、大小可见 |
| package 是否有 namespace 和 leaf 映射？ | package-js → JS工具包；React/Vue → 组件库 |

重点回扫场景：S01、S02、S03、S12。

### 3.5 策展/运营用户视角

合集和批量最容易被做成“看起来能用，实际很坑”的功能。

| 审查问题 | 通过标准 |
|---|---|
| 批量是否先预览？ | 展示处理/跳过/拒绝数量、分批、report |
| 批量失败状态是否分清？ | failed/resume/unknown/skipped 不混 |
| 合集四层模型是否讲清？ | 合集壳、子资源、目录草稿、合集版本 |
| 添加本地目录到合集是否安全？ | 子资源先创建/发布；成功项才进入目录草稿 |
| RSS 锁定字段是否硬拦？ | 不因 CLI 无 UI 而放开 |

重点回扫场景：S07、S08、S09。

### 3.6 测试人员视角

测试人员需要可执行、可观察、可判断，不需要猜产品意图。

| 审查问题 | 通过标准 |
|---|---|
| 每个场景是否有手测目标？ | 场景文档能直接变成测试脚本/手测步骤 |
| 是否能观察副作用？ | 标明本地写、平台写、report、state |
| 是否有负向场景？ | 缺 env、缺 yes、父类型、超大小、owner 不符、paid handoff |
| 是否能区分设计/代码/ENV？ | 设计不写运行数字；ENV 结果进 reports |
| 是否有验收 ID？ | 02 的 UX-* 与 FORM-* 能定位 |

重点回扫全部 S01–S14。

### 3.7 开发人员视角

研发需要知道拆在哪、边界是什么、不要把体验逻辑散到命令里。

| 审查问题 | 通过标准 |
|---|---|
| 场景是否能映射到模块？ | command 只做入口；service 做业务；store 做持久化；prompt 做交互 |
| 是否有共享交互组件？ | 类型选择、preflight、成功续接、handoff、错误渲染复用 |
| 是否避免魔法判断？ | 类型、artifactMode、RSS lock 来自平台/manifest 明确能力 |
| 是否可测试？ | 每个 checkpoint 可单测或契约测试 |
| 是否可维护？ | 重复规则回收到 02 或共享模块，不散落 Sxx |

重点回扫 S01–S05 的 init/publish，S07/S08 的批量与合集，S10 的输出协议。

### 3.8 安全/支持视角

CLI 会写本地、写平台、处理凭据，安全不是后补。

| 审查问题 | 通过标准 |
|---|---|
| 凭据是否不进项目和日志？ | auth 不落 public docs；debug 脱敏 |
| env 是否明确？ | 写操作不走 production fallback |
| owner 是否可见？ | 写前展示账号和 owner |
| 敏感文件是否会被候选/打包/上传？ | `.freelog-auth`、`.freelog/`、VCS 强排 |
| 支付/验证码是否越权？ | 只 handoff，不伪造完成 |

重点回扫 S05、S07、S09、S11、S13。

## 4. 当前审查发现

| 发现 | 影响 | 已回归到哪里 |
|---|---|---|
| 主题/插件此前只在矩阵里提到，不足以指导体验实现 | 容易被做成搜索型入口或复用错误文案 | S01、S02 已单独成文；02 §1.2/§1.3 索引 |
| package 既是模板又是平台资源类型，容易混淆 | namespace、leaf 类型、runtimeVersion 会错 | S03 单独定义模板到 leaf 映射 |
| “文件夹”至少有三种模型 | 用户可能把目录 zip、批量、合集走错 | S05、S07、S08 分开定义 |
| 02 原本混入大量场景正文 | 总设计和场景细节职责混乱 | 02 改为总拓扑 + 场景索引；细节进 `场景/` |
| AI/CI 和 TTY 都要覆盖，但不能互相污染 | 可能出现 JSON stdout 混人类文案或 TTY 难用 | S10 + 02 §0.2 |
| 策略此前受旧命令影响写成文件优先 | 普通用户被迫猜 policy DSL，无法对齐 Console Builder | S14 单独定义模板列表 → 参数 → 预览 → 应用；02 §9 回收总规则 |

## 5. 本轮多视角审查结果（2026-08-28）

| 视角 | 结论 | 还要继续盯的点 |
|---|---|---|
| AI / CI | 基础设计已覆盖：S10 单独成文，所有场景都有等价命令或机器限制 | 后续实现时逐命令核 stdout/stderr、schemaVersion、exit code |
| 产品经理 | 主入口和场景拆分已清楚：从“我手里有什么”进入，而不是命令树；策略已修正为模板 Builder 主路径 | 第一屏最终文案、默认推荐路径仍需 UX 文案评审 |
| 普通用户 | 已明确 TTY 连续向导优先，显式命令是 checkpoint | 需要在下一轮把每个 checkpoint 的具体 prompt 文案写到实现规格 |
| 前端/工程型资源开发者 | 主题、插件、package 已拆成 S01/S02/S03，资源类型定稿规则明确 | 需要确保模板列表和最终生成文案不混用主题/插件/package |
| 批量/策展用户 | 批量、合集、RSS 已分为 S07/S08/S09，模型边界清楚 | 合集 item import-dir 的手测路径要单独验收 |
| 测试人员 | 场景能转成手测用例，02 保留 UX-* 总矩阵 | 需要从 S01–S14 派生正式手测脚本/清单 |
| 开发人员 | 已有 checkpoint、模块边界和回归规则；策略需要新增模板服务/渲染服务而不是继续扩大文件 apply | 需要下一步把 prompt/preflight/renderer 抽为共享实现，不要散在命令里 |
| 安全/支持 | env、owner、auth、敏感文件、handoff 已纳入场景 | 需要手测凭据不落盘和敏感文件扫描排除 |

审查结论：

- **可以进入下一轮“屏幕文案 + 实现结构规划”设计**：总拓扑和场景分册已经能承载讨论。
- **还不建议直接开始大规模代码重构**：因为每个场景的具体 prompt 文案、preflight 字段顺序、成功续接菜单还需要再细化一轮。
- **不能再回到单文件大杂烩**：后续任何体验问题先落到 Sxx 场景，再回归 02 总规则。

## 6. 设计完成门槛

只有同时满足以下条件，才可以说“一期 CLI 脚手架体验设计足够进入实现重构”：

- [ ] S01–S14 每个场景都有：用户目标、Console 对齐、资源类型或对象模型、TTY checkpoint、副作用、失败处理、AI/CI 等价或明确不适用、回归总设计。
- [ ] 02 只保留跨场景规则，不重新堆场景正文。
- [ ] 主题、插件、package 都有独立入口和资源类型定稿规则。
- [ ] 策略新增的普通 TTY 主路径为模板 Builder；`--from-file` 仅为 advanced/AI/CI fallback。
- [ ] 普通文件、目录整体 zip、批量、合集的模型差异在第一屏可解释。
- [ ] Console FORM 约束能落到每个相关场景。
- [ ] 测试人员能把每个场景转换成手测脚本，不需要询问产品意图。
- [ ] 开发人员能把每个 checkpoint 映射到 command / prompt / service / store / renderer。
- [ ] AI/CI 所有写路径都有非交互失败和结构化输出策略。

未勾完时，不建议开始大规模代码重构；可以只做不改变体验结构的底层清理。
