# 一期产品设计总纲

> **文档角色：** 一期资源发行脚手架的产品总纲。本文回答“为什么做、为谁做、做哪些、不做哪些、CLI 应该按什么信息架构组织”。Console 事实见 [对齐/Console业务流程字段接口总账.md](./对齐/Console业务流程字段接口总账.md)，具体流程拓扑见 [02-CLI体验拓扑设计.md](./02-CLI体验拓扑设计.md)。

最后更新：2026-08-31

## 1. 产品目标

Freelog Console 适合在浏览器中逐步创建、编辑、确认资源；CLI 的价值不是复制页面，而是把资源发行和维护变成本地工作台。

一期 CLI 要让用户或 AI 能够：

- 管理本地电脑、Git 仓库、构建产物里的资源。
- 发布或更新主题、插件、前端库、普通文件、普通目录资源。
- 批量处理本地素材目录。
- 创建和维护合集、RSS 合集、自动收集规则。
- 管理线上资源的策略、依赖授权、上架和下架。
- 在 AI/CI 中用稳定参数、JSON/NDJSON、退出码和报告恢复完成同一业务。

一句话目标：

```text
输入一个入口命令，用户可以按清晰提示完成一次资源发行或维护；专家和 AI 可以用显式命令完成同一件事。
```

## 2. 设计顺序

设计和实现必须按这个顺序推进：

```text
Console 常规业务流程
  → Console 字段约束 / 接口 / 状态门禁
  → CLI 环境差异
  → CLI 主流程设计
  → 具体场景校验
  → 代码结构和命令实现
```

不能从旧 CLI 命令倒推产品，也不能因为旧实现缺失就删除 Console 能力。

## 3. Console 常规业务流程

CLI 首先对齐业务结果，不复制浏览器 UI。

### 3.1 独立资源首次发行

```text
选择资源类型 leaf
  → 填标题和资源名
  → 创建资源壳
  → 选择文件 / 构建产物
  → 创建版本
  → 选择策略模板并应用
  → 填封面 / 标签 / 简介
  → 上线
```

### 3.2 独立资源维护

```text
读取线上资源
  → 改 listing
  → 发新版本，或编辑已发布版本可编辑字段
  → 管理依赖授权
  → 新增或启停策略
  → 上线 / 下线
```

### 3.3 批量发行

```text
选择支持批量的资源类型
  → 选择最多 20 个文件一批
  → 为每项生成标题、资源名、属性、策略
  → createBatch
  → 输出逐项结果
```

CLI 可以把大目录自动拆成多批，但每批写平台时必须遵守 Console 约束。

### 3.4 合集

```text
创建合集壳
  → 添加条目或绑定 RSS
  → 编辑目录草稿 / 展示设置 / 授权
  → 发布合集版本
  → 添加策略
  → 设置 collect-rules
  → 上线
```

合集不是“上传一个 zip”。它有合集壳、目录草稿、子资源、合集版本四层。

### 3.5 策略

策略新增的主流程是：

```text
看可用策略模板
  → 选择模板
  → 填模板参数
  → 编译策略
  → 翻译预览
  → 确认应用
```

手写 policy 文件只属于专家、迁移、AI/CI fallback，不能作为普通 TTY 主路径。

## 4. CLI 环境差异

Console 用 UI 约束用户；CLI 必须把这些约束显式化。

| Console 中的隐性保障 | CLI 中的产品设计 |
|---|---|
| 页面上下文 | 每一步显示 env、账号、资源、下一步 |
| 按钮禁用 | 写平台前 preflight |
| 表单校验 | prompt 校验 + 非交互错误码 |
| 文件选择器 | 本地扫描、ignore、大小、sha1、敏感文件排除 |
| 弹窗确认 | 明确风险摘要和 confirm |
| 浏览器支付 / 签约 / 验证码 | handoff URL + nextCommand |
| 页面成功页 | 下一步菜单 + 可复制命令 + report |

## 5. 目标用户和任务

| 用户 | 任务 | CLI 要解决 |
|---|---|---|
| 普通作者 | 发布图片、视频、文档 | 不懂类型 code、API、策略 DSL 也能完成 |
| 主题开发者 | 初始化、构建、打包、发版、上架主题 | 不把主题藏进搜索框 |
| 插件开发者 | 发布插件资源 | 不复用主题文案误导 |
| 前端库开发者 | 发布 package / 软件库 | 明确 package 模板和构建产物 |
| 策展人 | 创建合集、维护目录、RSS、收集规则 | 分清合集和目录 zip |
| 批量运营 | 处理一批素材 | 可预览、可中断、可恢复 |
| 线上维护者 | 只改策略、上下架、listing | 不被迫创建本地工程 |
| AI/CI | 自动化发布和维护 | 无 prompt、稳定 JSON、可恢复 |
| QA/研发 | 验证 Console parity 和 CLI 体验 | 有场景、有门禁、有证据 |

## 6. 产品信息架构

CLI 按用户目标组织，不按 API 名组织。

### 6.1 第一屏

```text
你要做什么？
  1. 发布一个新资源
  2. 更新当前本地工程
  3. 维护一个已有线上资源
  4. 批量发布一个本地文件夹
  5. 创建或维护合集
  6. 只管理策略 / 依赖 / 上下架
  7. 进入 session / studio 临时工作
```

### 6.2 资源类型是一等入口

发布新资源时先问产品语义，再落到平台类型 leaf：

```text
主题
插件
前端库 / 软件库 package
普通单文件
普通目录 zip
批量本地目录
合集
RSS 合集
```

类型选择必须同时支持：

- 逐级浏览资源类型树。
- 搜索 leaf。
- 显示完整路径、code、格式限制、大小限制、支持能力。

只做搜索、不做逐级选择，是不合格设计。

### 6.3 本地目录有三种含义

| 用户手上的目录 | 应走流程 | 平台结果 |
|---|---|---|
| 目录整体就是一个作品 | 普通目录 zip | 一个资源版本文件 |
| 目录里每个文件都是作品 | 批量发行 | 多个独立资源 |
| 目录要组成相册/专辑/合集 | 合集 | 子资源 + 合集版本 |

第一屏必须帮用户分清这三件事。

## 7. 运行表面

同一套业务规则，需要支持不同使用表面。

| 表面 | 入口 | Store | 适合 | 硬规则 |
|---|---|---|---|---|
| 工程模式 | `freelog-cli start` / 显式命令 | manifest + state + report | 长期维护、Git、CI | 本地意图和平台事实分层 |
| 单命令会话 | `--session --resource-id` | 内存 | 临时维护线上资源一次动作 | 命令结束不记忆 |
| session 壳 | `freelog-cli session` | 内存 | 一个终端内临时连续完成事项 | 退出前提示导出 |
| studio | `freelog-cli studio` | 子工程 + 临时凭据 | 多账号、多文件工作台 | 不读取磁盘 auth，不串账号 |
| AI/CI | `--json --yes --env` | 工程/report | 自动化 | 禁止 prompt，stdout 稳定 |

这些表面只改变 Auth/Store/输出方式，不改变字段约束、策略门禁、版本规则和上线规则。

## 8. 能力边界

### 8.1 一期必须覆盖

| 域 | 能力 |
|---|---|
| 资源类型 | 主题、插件、package、普通文件、普通目录 |
| 本地能力 | 模板、构建、压缩、ignore、sha1、report |
| 资源发行 | create、publish/version、listing、policy、online/offline |
| 批量 | scan、preview、分批、retry/resume、NDJSON |
| 合集 | create、item、display、collect-rules、publish、online |
| RSS | inspect、send-code、verify、bind、status、sync、锁字段 |
| 会话 | `--session`、`session`、`studio` |
| 自动化 | JSON、NDJSON、退出码、report |

### 8.2 一期只做 handoff 或边界记录

| 域 | 一期处理 |
|---|---|
| 支付 / 结算 | 给原因、Console 链接、nextCommand |
| 浏览器签约 | 可 CLI 判断则处理；需要浏览器则 handoff |
| 节点 / 展品 / 主题激活 | 资源发布后提示或跳转；完整节点管理另开事实总账 |
| Console 裁剪 UI | CLI 接收合规图片或提示去 Console 裁剪 |

## 9. 合格标准

产品设计进入代码实现前，必须能回答：

1. Console 常规业务流程是什么？
2. 每个字段限制和状态门禁来自哪里？
3. CLI 为什么这样分流，而不是照搬页面？
4. 主题、插件、package 是否是清楚的一等入口？
5. 单文件、目录 zip、批量、合集是否不会混淆？
6. 策略是否默认先选模板再应用？
7. RSS 和 collect-rules 是否有完整流程和锁字段？
8. session、studio、AI/CI 是否只改变运行表面，不改变业务规则？
9. 每次平台写入前是否有 preflight？
10. 失败后是否有 nextCommand、report 或 handoff？
11. 场景分册是否能反推出主设计，而不是复制一堆规则？
12. 代码结构是否能按流程阅读，而不是命令文件拼 API？
