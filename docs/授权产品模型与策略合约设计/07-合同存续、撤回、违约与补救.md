# 合同存续、撤回、违约与补救

状态：**待定稿的产品规则。**本文记录平台应有的用户权益、资源管理和合同处理规则；不代表现有接口或 CLI 已实现。多合同、升级与续费的一般规则见 [06-多合同、升级与续费](./06-多合同、升级与续费.md)。

## 1. 先确立的判断方法

“资源下架”不能直接等同于“已有授权失效”，也不能笼统等同于“发了一个新版本”。它实际可能涉及四件互不相同的事：

| 业务动作 | 对新用户 | 对已有合同 | 典型目的 |
|---|---|---|---|
| 停止新签约 | 不可再签 | 继续履约 | 作者不想再卖，但愿意履行已卖出的承诺 |
| 暂时不可交付 | 不可再签 | 按合同进入暂停/补救流程 | 临时版权争议、技术故障、合规审核 |
| 变更后续内容 | 取决于新版本规则 | 取决于合同固定的版本范围 | 修复文件、追加内容、替换主题版本 |
| 彻底撤回 | 不可再签 | 不能继续按原承诺履约，必须进入解除或补救 | 权利失效、内容必须移除、作者主动终止供给 |

因此，平台至少要分别管理**可发现性**、**能否新签约**、**能否继续交付**和**合同补救**，不能只用一个资源状态字段决定全部结果。

```text
资源对外可见 / 可新签约
            ↓ 停止新签约
履约中但不再销售 ─────────→ 已有合同继续可查、可使用
            ↓ 无法继续交付
合同补救中 ───────────────→ 恢复履约 / 解除并补偿 / 平台裁决
            ↓ 已无有效合同
归档
```

## 2. 资源下架、合集移除单品与版本更新

### 2.1 推荐的默认规则

**推荐默认规则：有有效合同的内容，只能先进入“停止新签约、继续履约”。**

此时它不再出现在面向新用户的检索、推荐和新签约入口；但已签约使用方仍应能在“我的合同 / 我的已授权内容”中找到它，并经合同校验后访问应有范围。不能仅因它不在公共资源列表中，就让已有合同失去交付入口。

这需要平台查询层区分两种视图：

- 公共视图：只返回可发现、可新签约的资源。
- 合同视图：只对合同当事人返回与该合同有关、仍在履约或补救中的资源，并明确标示状态。

直接通过资源 ID 查询也不能绕过这个边界：平台应先判断来访者是否有有效合同或管理权限，再决定返回何种元数据和是否允许取得内容。

### 2.2 “完全下架”不是普通状态切换

如果内容无法继续提供，而又存在有效合同，这不是普通的资源下架，而是**履约无法继续**。推荐把它设计为受约束的合同事件：

1. 授权方提出撤回理由、拟生效时间和补救方案。
2. 平台找出所有受影响合同及其当前剩余承诺。
3. 按合同中预先约定、且平台可执行的规则继续交付、替代交付、补偿或解除。
4. 每份合同保留结论、计算依据和资金/通知结果，完成后资源才可彻底归档或撤回。

**没有预先约定且没有平台强制规则时，不应允许授权方直接彻底下架。**它最多可以停止新签约。这样不会让“付款 10 元获得 30 天授权”的承诺因作者点击下架而无声消失。

对付费、按期授权，授权发布或平台标准条款至少需要能声明：

- 可否提前终止交付；
- 提前终止时采用继续可用、替代内容、按未履行期间退款、固定补偿或其他方案；
- 退款/补偿如何计算、由谁确认、失败时如何处理；
- 内容因法律、侵权或平台安全原因必须立即移除时，使用方获得什么解释与补救。

其中“退款”应由平台的结算能力执行和留痕，不能只是一句条款文本；平台可以支持授权方选择触发条件和计算方式，但不能自行扣款或假定退款成功。

### 2.3 合集移除单品：先冻结合同范围

合集的成员变化尤其不能回头改变历史合同。推荐规则：

- 新签约只面向合集当前成员和当前授权范围。
- 已签约合同保留其签约时被授权的单品集合或明确分段，不能因单品后来被移出合集而自动缩小。
- 如果被授权单品本身仍可交付，合同继续履约，即使它不再属于合集的当前公开成员。
- 如果该单品本身也无法交付，按“完全下架”的合同补救规则处理，而不是把问题伪装成一次合集编辑。

这也是“合同范围应以不可变单品身份锁定”的原因；合集标题、排序和当前列表都是可变展示信息，不能作为合同范围的唯一证据。

### 2.4 版本更新必须先明确授权版本范围

“发布新版本”与“下架”不同：前者通常是继续提供同一资源，后者是减少或终止交付。新版本是否允许旧合同取得，不能凭直觉决定，必须检查合同固定的**版本范围**。

推荐默认是“全部版本（含合同有效期内后续发布的版本）”；授权方也可选择有界范围或指定版本。范围一经合同接受即固定，作者不能通过发布新版本或改写范围，间接改变旧合同实际可取得的版本。若某个版本在范围内却无法继续交付，问题属于履约与补救，而不是范围失效。

## 3. 同一使用方存在多份合同

### 3.1 不能只比较“范围是否更大”

你的判断是正确方向：如果使用方已有合同，新合同的有效权利完全被已有合同覆盖，通常不应再让用户无意义地签一遍。

但“被覆盖”必须同时比较：内容目标、能力、范围、有效期、使用限制、额度/次数、价格与未履行义务。只比较单品范围会误判，例如同样可下载但一次是 30 天、一次是永久；同样覆盖全集但一次包含商业使用、一次不包含。

### 3.2 推荐的四类处理结果

| 新合同与有效合同的关系 | 推荐用户动作 | 授权结果 |
|---|---|---|
| 语义完全相同 | 拒绝重复签约，直接指向现有合同 | 不创建重复合同 |
| 新合同的实际权利被现有合同完全覆盖 | 提示“你已拥有不弱于此的授权”，默认不再签 | 保留现有合同 |
| 新合同提供更广权利或更长期间 | 走明确的“升级 / 续期”流程，并关联原合同 | 新合同与旧合同的关系明确记录 |
| 两份合同各有一部分独立权利 | 允许并存，但在签约前展示叠加后的效果和各自义务 | 分别保存，按明确聚合规则生效 |

### 3.3 聚合规则：权利可并集，义务不能被静默覆盖

推荐的默认解释是：**只要任一有效合同明确授予某项权利，使用方即可在该合同的范围和限制内行使它。**因此，访问能力通常按可满足的合同并集判断。

但这不代表“所有字段简单取最大值”：下载次数、并发设备数、商业用途、地域、有效期等限制必须仍归属到产生它的那份合同；付款、结算、署名等义务也分别存在。

“优先级覆盖”不应是默认机制。只有使用方明确选择“替换 / 升级”且新合同声明替代范围时，才允许新合同终止、迁移或覆盖旧合同的特定效果；否则会产生用户不知情地失去旧权利、或授权方借新条款规避旧承诺的问题。

## 4. 授权规则下线、资源停止签约与合同违约

三者应当有清晰边界：

| 动作 | 新签约 | 已成立合同 | 推荐限制 |
|---|---|---|---|
| 授权规则下线 | 不可再选择或签约 | 不受影响 | 下线不能改写历史合同 |
| 资源停止新签约 | 不可签 | 继续履约 | 必须保留合同视图和交付入口 |
| 资源完全撤回 | 不可签 | 进入补救/解除流程 | 有有效合同时不得直接完成撤回 |
| 合同到期 | 不可再依该合同使用 | 结束，但历史可查 | 续费另建周期合同 |
| 条件暂不满足 | 取决于合同约定 | 暂停或降级 | 条件、恢复方式和通知必须明确 |

对于你提出的“资源下架若仍有合同，规则要写好违约说明”，推荐分层处理：

- 平台提供不可绕过的最低保护：不能无补救地彻底撤回仍有有效合同的内容。
- 授权方可在这个底线内选择更具体的提前终止、退款或替代交付规则。
- 平台因法律、侵权、安全等原因强制处理时，仍走可追溯的合同补救路径，而不是假装合同从未存在。

这样既不把所有复杂退款逻辑写死在每一份授权规则里，也不会留下“作者没有写退款条款就可以直接违约”的漏洞。

## 5. 续费：新周期合同，而不是修改旧合同

推荐确认你的判断：续费创建一个**新的合同周期**，并关联上一个周期，但不改写旧周期。

这允许授权方设计：

- 首期价与续费价不同；
- 连续续费折扣或权益；
- 续费资格依赖上一个周期是否正常结束；
- 新周期采用当时接受的新授权发布，还是沿用原授权发布。

需要另行定稿的一点是：续费时默认锁定原授权发布，还是允许用户重新接受新版条款。推荐在产品上显式选择并展示差异；不能把“自动续费”变成无提示接受新条款。

## 6. 平台资格：可被授权规则使用，但必须有来源与影响规则

平台的用户资料、认证、会员、渠道身份等可以成为授权规则可判断和可监听的资格事实。建议把它们视为平台提供的、带有效期和来源的资格，而不是授权方自行维护的标签。

每一项资格在被授权规则使用前，应明确：

1. 谁产生和撤销该资格；
2. 签约时只检查一次，还是合同期间持续检查；
3. 资格变化影响新签约、已有合同，还是两者；
4. 失效后是暂停、降级、给宽限期，还是终止；
5. 使用方如何知道被哪个资格影响，并能否申诉或纠正。

推荐默认：资格变化不应隐式地把既有合同永久删除；它只能按合同中已展示的规则引发暂停、恢复或后续周期不再续签。

## 7. 当前必须定稿的决策清单

以下问题是合同服务、资源查询、支付结算、管理后台和 CLI 都必须共同遵守的业务前提：

- [ ] 各内容类型支持哪些版本范围（全部、有界、指定）？默认“全部版本”是否明确包含合同期内后续版本？
- [ ] 有效合同下，作者申请完全撤回时允许哪些补救方案？哪些内容或合同类型必须限制为“停止新签约”？
- [ ] 合集单品移除后，合同范围如何保存和查询；单品被强制下架时如何批量进入补救？
- [ ] “已有授权覆盖新授权”的精确比较维度与用户提示文案是什么？
- [ ] 升级、替换、叠加、续费分别如何创建和关联合同？
- [ ] 多合同的下载次数、设备数、地域、商业用途等限制如何聚合或选择？
- [ ] 平台资格的来源、监听范围、宽限期和申诉机制是什么？
- [ ] 合同补救中的退款、替代交付、通知、失败重试和人工裁决分别由哪个平台能力负责？

在这份清单没有明确前，平台不应承诺这些复杂场景已经被正确支持。
