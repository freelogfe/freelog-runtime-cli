# 治理、运营与平台能力

状态：**历史专题草案，不作为当前产品规则**。平台能力、权限与最低保护仍须产品决策；本文的能力清单和状态建议仅用于回溯问题，不代表现行或已批准的方案。

## 目标

授权产品不能只设计创作者和使用方的正常路径。内容类型、模板、审核、支付、客服、风控与各端接口必须围绕同一份合同事实协作，否则产品会在异常场景中各说各话。

## 1. 内容类型治理

内容类型是平台的产品能力开关，不只是分类标签。运营后台应为每个叶子类型明确配置：

- 可发行的内容形态与交付要求；
- 可用属性和可选配置，以及哪些是必填；
- 可提供的权利和可使用的授权发布类型；
- 是否允许下载、全部版本/有界版本范围/指定版本、合集单品选择或持续更新目录；
- 对封面、简介、标签、文件解析、版权证明和审核的要求；
- 可使用的平台资格、地域、年龄与风控限制；
- 允许的撤回、替代交付与补偿方案。

配置变更必须版本化。新配置影响新内容和新授权发布；对于已经签约的合同，只能在合同已经公开接受的平台强制规则范围内生效，不能借后台改配置倒改历史权益。

## 2. 授权发布与模板治理

平台可以提供授权模板帮助创作者快速发布，但模板的角色是降低创建成本，不是隐藏关键承诺。

模板上架前，运营应审查其是否明确覆盖：权利、内容/单品/版本范围、条件、价格、期限、续费、暂停、提前终止与补救。模板更新后应形成新版本；旧模板产生的授权发布和合同不受影响。

模板列表、内容类型和合集/单资源适用范围，都应由平台返回并可审计。客户端只负责展示和收集选择，不得自行猜测模板适用性。

## 3. 审核、风控与强制处理

平台需要区分三类运营动作：

| 动作 | 适用情况 | 对合同的产品后果 |
|---|---|---|
| 预防性审核 | 内容或授权发布尚未公开 | 阻止开放市场，不产生用户合同损失 |
| 风险限制 | 可疑欺诈、支付风险、资格异常 | 限制新签约或暂停高风险操作，并通知当事人 |
| 强制处理 | 侵权、违法、安全事故、法院/监管要求 | 可能中断交付，但必须进入合同补救、证据保全与申诉流程 |

强制处理不能被包装成普通“作者下架”。平台应显示处理主体、依据类别、影响范围、临时措施、复核入口与受影响合同的补救状态；对外披露应满足隐私与法律要求。

## 4. 争议与人工裁决

自动状态无法覆盖所有争议。平台应有统一案件对象，至少可关联内容、授权发布、合同、支付记录、使用记录和相关通知。

| 阶段 | 用户能力 | 平台能力 |
|---|---|---|
| 发起 | 选择争议类型、提交最小必要材料 | 校验时效、冻结必要证据 |
| 处理 | 查看受理、补件、临时保护和预计时间 | 分派、补件、风险控制、查看完整历史 |
| 裁决 | 查看理由、补偿、恢复或解除结果 | 作出有权限的决定并生成可审计记录 |
| 复核 | 在规则允许期限内申诉 | 二次审核、纠正或维持，并保留两个结论 |

人工裁决可以改变合同的后续履约结果，但不能抹掉原始合同和历史事实。所有例外动作都应说明授权人、原因和影响。

## 5. 通知与知情权

以下事件应通知合同当事人，并在通知中心可追溯：合同生效、待付款、付款成功/失败、即将到期、自动续费提醒、资格变化、暂停/恢复、停止新签约、交付受限、撤回补救、退款/替代交付、争议受理与裁决。

通知应区分“信息提醒”和“需要用户行动”。对于会降低或终止权益的事件，通知必须包含生效时间、影响范围、补救/申诉入口；仅发一条泛化消息不足以满足产品责任。

## 6. 产品端的职责划分

| 产品端 | 核心职责 | 不应承担 |
|---|---|---|
| 市场/详情页 | 展示可签约授权发布、对比权益、发起签约 | 自行判断合同或支付成功 |
| 创作者管理台 | 管理内容、版本、授权发布、市场状态和撤回申请 | 直接改写已成立合同 |
| 使用方内容库 | 展示有效权利、合同依据、续费和异常处理 | 依赖公共搜索作为唯一入口 |
| 支付与结算 | 收款、退款、对账和结果确认 | 单独决定内容权利 |
| Console / CLI | 收集操作意图、调用平台能力、展示平台结果 | 保存会与线上合同分叉的本地真相 |
| API / 节点 | 按统一的合同与交付结论提供能力 | 各自定义不同的状态或权益规则 |
| 运营后台 | 配置、审核、风控、案件与审计 | 绕过留痕任意修改用户权益 |

## 7. 审计、隐私与数据留存

平台至少要保留合同成立、条件确认、状态迁移、付款/退款、授权范围、交付受限、通知与人工处理的必要证据。用户应能查看与自己有关的解释和历史；授权方只能查看自己合同所必需的信息；运营人员按角色和案件范围访问。

资格信息、支付信息和使用记录应遵循最小化原则：只为合同履约、风控、争议和法定义务收集与保存；展示时脱敏；超过必要期限后按规则删除、匿名化或限制访问。

## 8. 平台级可靠性要求

- 同一支付回调、签约确认、撤回申请或退款结果重复到达，不得重复创建合同、扣款或补偿。
- 市场、详情、内容库、API、节点和 CLI 对同一合同应得出一致的可用权利结论。
- 任何关键状态变化都应可重试、可恢复、可人工介入；失败不能停在用户无法理解的中间状态。
- 平台应区分“暂时无法查询”与“合同没有权利”，避免系统故障被误判为用户无授权。
- 对不可逆动作，例如完全撤回、解除合同、退款结算，应提供预览、确认、影响范围和事后审计。
