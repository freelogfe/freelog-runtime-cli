# 授权与合约核心抽象设计

状态：**已归档的历史讨论材料，不作为当前规则。**对象变化事件、合同流程与场景覆盖的当前主模型见[策略合约核心抽象与场景覆盖](../12-策略合约核心抽象与场景覆盖.md)。

本文原本讨论授权平台最小、稳定、可扩展的业务抽象，不讨论策略语言、接口、数据库或执行代码。

## 一、先回答授权系统到底在判断什么

授权系统最核心的问题不是“合同现在处于哪个状态”，也不是“最近收到了什么事件”，而是：

> 某个使用主体，在某个具体情境下，是否可以依据一份或多份合同，对某项内容的某个范围执行某种行为？

一次完整判断至少包含：

```text
谁
  + 对什么内容、哪个单品、哪个版本
  + 想做什么
  + 在什么时间、地域、设备与用途下
  + 依据哪份有效合同
  + 合同要求的事实是否成立
  = 本次行为是否落入授权范围，以及依据和原因
```

这意味着产品必须把三件事严格分开：

1. **合同是否存在并具有约束力**；
2. **合同承诺的权利范围是什么**；
3. **本次请求是否落在这份范围内**。

用户到了另一个国家、请求了范围外版本、改成商业用途，都不会自动改变合同本身。它们只改变本次请求是否适用。合同状态不应该成为所有判断结果的垃圾桶。

## 二、最小授权内核

无论以后接入支付、广告、会员、地域、设备、外部认证或新的内容类型，授权判断都可以归结为七个稳定对象。

| 核心对象 | 它回答的问题 | 例子 |
|---|---|---|
| **当事人** | 谁作出承诺、谁接受承诺、谁实际使用权利？ | 授权方、签约方、企业成员、节点 |
| **授权标的** | 权利针对什么？ | 单资源、合集、合集单品、资源版本 |
| **行为能力** | 被允许做什么？ | 浏览、下载、安装、播放、分享、商用 |
| **适用范围** | 该能力在哪些边界内有效？ | 版本、单品、时间、地域、用途、设备、次数 |
| **授权承诺** | 授权方愿意以什么条件提供什么权利？ | 一条公开可签约的授权发布 |
| **授权合同** | 哪个使用方接受了哪项承诺和哪些选择？ | 固定双方、内容、范围、价格、期限与补救安排 |
| **可信凭据** | 判断所依赖的事实从何而来？ | 支付确认、广告完成、用户资格、请求地域、版本已发布 |

最终产品输出不是一个模糊的“授权状态”，而是一次有依据的结论：

- 本次行为在授权范围内；
- 本次行为不在授权范围内；
- 必要条件尚未满足；
- 由于可信凭据不可用，暂时无法判断；
- 内容无法交付，需要进入履约或补救流程。

这些结果对用户的含义完全不同，不能统一显示为“无权限”或“合同暂停”。

## 三、用“合约关心项”统一扩展入口，但不抹平语义

平台未来会不断增加可以被授权规则使用的能力。为了扩展，它们需要一个统一入口；为了正确，它们又不能被强行当成同一种东西。

因此建议使用上位概念：**合约关心项**。它表示“合同形成、履行或授权判断可以引用的一项平台能力”。合约关心项有四种基本形态：

| 形态 | 业务语义 | 时间特征 | 例子 |
|---|---|---|---|
| **对象引用** | 指向一个稳定存在的人、内容或交易对象 | 身份稳定，可长期引用 | 用户、资源、版本、合集、支付单、广告活动 |
| **事实观察** | 某对象在某一时点被可信来源确认为什么样 | 有观察时间与有效期 | 会员有效、支付已完成、版本已发布、内容可交付 |
| **发生记录** | 某件事情在某时确实发生过 | 不可变、不可重复消费 | 广告观看完成、付款确认、退款完成、版本发布 |
| **请求情境** | 只描述本次行为发生时的环境 | 短暂，仅服务本次判断 | 当前地域、当前时间、设备、请求版本、使用目的 |

它们可以共享“来源、时间、可信程度、可见范围、证据”这些共同属性，但不能混为一类：

- 对象引用解决“究竟是哪一个”；
- 事实观察解决“此刻被确认为什么样”；
- 发生记录解决“某件事是否已经发生过”；
- 请求情境解决“本次行为处在什么边界内”。

### 为什么事件不能简单视为可变化对象

从存储角度，事件记录当然也可以有 ID、时间和字段；但从业务语义看，事件不是“一个会继续变化的对象”，而是对一次发生事实的不可变证明。

支付单是对象；“支付成功”是该支付单的一次发生记录。广告活动是对象；“用户完成了这条广告”是发生记录。资源版本是对象；“该版本已经发布”既可表现为发布事实，也可产生一次发布记录。

保留这个区别，才能正确处理重复通知、发生顺序、撤销、更正和审计。否则“重复收到支付成功”可能被误认为发生了两次付款，“当前未查到广告完成”也可能错误覆盖历史上已经完成的事实。

## 四、同一个对象可以被合同以四种方式关心

对象本身是稳定的；合同如何使用它，是另一层关系。

| 关心方式 | 含义 | 是否写入合同 | 示例 |
|---|---|---|---|
| **绑定** | 签约时选中并固定，之后不能悄悄替换 | 是 | 使用方、资源、广告活动、版本范围、所选单品 |
| **取样** | 在某个关键时点读取事实，并把当时结果固定 | 视产品规则 | 签约时的会员等级、签约时已有版本清单 |
| **持续观察** | 合同存续期内持续关心某项可靠事实或发生记录 | 保存影响合同的变化 | 付款完成、资格撤销、内容恢复交付 |
| **按请求判断** | 每次使用内容时重新取得本次情境 | 通常不改变合同 | 当前地域、请求版本、设备、用途、服务时段 |

“固定对象”和“可以监听的对象”因此不是对象分类，而是合同对对象的使用方式。平台用户既可以被绑定为合同当事人，也可以持续观察其资格；资源既可以被绑定为授权标的，也可以观察它是否发布新版本；当前地域只适合按请求判断，通常没有必要持续监听。

## 五、适用范围是授权模型的中心，而不是附加条件

行为能力必须与适用范围一起存在。单独说“可下载”是不完整的；完整表达应是“谁可下载什么内容的哪些版本，在什么时间、地域、用途、设备与额度内”。

适用范围至少有以下维度：

| 范围维度 | 回答的问题 | 示例 |
|---|---|---|
| 内容范围 | 哪些内容属于授权标的？ | 整个资源、合集中的 10 个指定单品 |
| 版本范围 | 哪些版本被覆盖？ | 全部版本、`1.x`、指定版本 |
| 时间范围 | 在什么时间内适用？ | 30 天、某日之前、每天 08:00–22:00 |
| 地域范围 | 在哪些区域内适用？ | 中国大陆、指定国家列表 |
| 用途范围 | 允许以何种目的使用？ | 个人使用、教育使用、商业使用 |
| 主体范围 | 谁可以实际使用？ | 签约账户、企业指定成员、某个节点 |
| 设备与渠道范围 | 通过什么设备或渠道使用？ | 最多 3 台设备、仅受信任节点 |
| 数量范围 | 可使用多少次或多少额度？ | 下载 10 次、调用 1000 次 |

这些范围在合同中被承诺，本次请求只是在其中取一个具体点进行匹配：

```text
合同地域范围 = 中国大陆
本次请求地域 = 日本
结论 = 本次请求不在地域范围内
合同 = 仍然存在且有效
```

同理，请求 `2.0.0` 而合同只覆盖 `1.x`，结论是该版本请求不适用，不是合同暂停、失效或违约。

## 六、合同条件与适用范围不能混用

范围回答“权利覆盖到哪里”；条件回答“权利何时产生或某项承诺何时履行”。两者在用户体验和合同后果上不同。

| 类型 | 不满足时发生什么 | 示例 |
|---|---|---|
| 范围 | 本次行为不属于合同授权 | 地域不符、版本不符、用途不符、次数已用尽 |
| 形成条件 | 合同尚未成立或尚未完成确认 | 用户未接受条款、必要选择未完成 |
| 生效条件 | 合同存在，但相应权利尚未产生 | 首次付款未确认、指定广告尚未完成 |
| 持续事实 | 根据承诺决定权利是否继续产生 | 会员资格必须持续有效、上游许可必须持续存在 |
| 履约义务 | 某方需要完成动作；失败可能产生违约或补救 | 付款、交付、通知、退款、结算 |

平台不应看到任何动态信息就尝试修改合同状态。例如会员资格失效，可以有三种完全不同的产品设计：

- 只影响下一周期续费资格；
- 当前合同继续有效，但会员折扣不再适用于下一次购买；
- 合同明确约定资格必须持续有效，因此相应权利暂时不产生。

只有授权承诺提前说明并由使用方接受，平台才能选择其中一种。即使相应权利暂时不产生，也不应默认把合同整体称为“暂停”。

## 七、两种完全不同的运行过程

授权系统有两条运行主线，必须分开设计。

### 7.1 合同演进

合同演进处理会留下持久历史的业务变化：

```text
授权承诺被接受
  → 合同形成
  → 发生记录或可靠事实满足某项条件
  → 形成新的履约记录、权利期间或待办事项
  → 到期、续费、解除、补救或结算
```

典型输入包括付款确认、广告完成、退款完成、人工裁决和内容无法交付。每次处理都应可去重、可追溯，并产生新的历史记录，不能覆盖旧事实。

### 7.2 本次授权判断

本次授权判断只回答当前行为是否被已有合同覆盖：

```text
本次请求
  + 已形成的合同及其权利范围
  + 必要的当前事实
  → 找出能够覆盖本次行为的合同
  → 返回适用或不适用，以及依据
```

请求地域、请求版本、用途、设备和服务时段通常只参与这条主线。它们不会反复驱动合同生命周期，也不应产生大量无意义的合同状态变化。

## 八、能力提供方只提供可信凭据，不能直接授予权利

平台模块可以扩展授权系统，但必须遵循职责边界：

```text
能力提供方提供对象、事实或发生记录
        ↓
授权承诺规定这些凭据能产生什么合同效果
        ↓
合同固定双方选择和承诺
        ↓
平台依据合同作出授权判断或履约处理
```

例如：

- 广告平台只能证明“某用户完成了某广告”，不能直接给用户增加某资源的下载权；
- 支付平台只能确认“某订单付款成功”，不能自行决定合同授予哪些版本；
- 地域服务只能判断“本次请求来自哪个地区”，不能自行终止合同；
- 资源服务只能证明“某版本已发布且可交付”，不能扩大合同原本的版本范围；
- 用户中心只能提供“某资格当前有效或发生变化”，不能绕过合同直接授予内容权利。

这是整个扩展体系最重要的隔离：**提供事实的人不能同时决定事实产生什么授权后果。**

## 九、平台能力如何逐层扩展

### 第一层：授权内核

只包含不会随业务插件变化的概念：当事人、标的、行为能力、适用范围、授权承诺、合同、可信凭据和授权结论。

### 第二层：平台基础关心项

由平台核心业务长期提供：

- 用户与组织身份；
- 单资源、版本、合集和单品；
- 授权发布与合同；
- 时间、地域和请求环境；
- 支付、退款与结算；
- 内容交付、合规和争议状态。

### 第三层：可插拔业务能力

由独立平台模块提供：

- 广告活动与完成记录；
- 会员、认证、企业资质；
- 设备信任、节点状态；
- 外部许可证、第三方合同；
- 活动任务、积分、票券或其他履约能力。

### 第四层：授权产品

授权方或平台模板从前述能力中选择：绑定哪些对象、读取哪些事实、接受哪些发生记录、使用哪些范围，以及它们产生什么权利、义务和补救。

### 第五层：合同与实际使用

用户接受具体授权产品后形成合同；平台随后分别处理合同演进与每次授权判断。

这种分层保证新增“看广告获得授权”时，不需要修改授权内核：新增的是广告对象和可信完成记录，再由授权产品选择如何使用它。

## 十、每种新增能力必须提交的产品契约

平台要开放一种新的合约关心项，必须先定义以下产品内容：

1. **对象定义**：它是什么，谁拥有，如何唯一识别。
2. **可信来源**：谁可以提供或更正它的事实与发生记录。
3. **可绑定内容**：哪些选择可以固定进合同。
4. **可观察事实**：哪些事实可在签约、履约或请求时读取。
5. **可接受发生记录**：哪些变化可被合同演进消费，如何防重复和乱序。
6. **允许用途**：可用于范围、条件、价格、合同演进、授权判断还是待办事项。
7. **有效时间**：事实何时生效、何时过期、历史是否可追溯。
8. **不可用处理**：能力提供方故障时，是无法判断、维持既有结果，还是进入人工处理。
9. **用户知情**：签约前怎样展示，变化后怎样解释，用户怎样申诉或纠正。
10. **隐私与权限**：谁可以读取、保存多久、是否需要用户同意。

未完成这份产品契约的能力，不应直接暴露给授权产品使用。

## 十一、三个场景验证核心抽象

### 场景一：看指定广告获得 24 小时浏览权

- 绑定：使用方、资源、指定广告活动、浏览能力；
- 发生记录：广告平台确认该使用方完成该广告；
- 合同演进：平台记录完成事实并产生一个 24 小时权利期间；
- 本次判断：请求在该期间、内容范围和其他适用范围内时允许浏览；
- 重复通知：不得重复产生多个权利期间，除非授权承诺明确允许重复完成。

### 场景二：主题插件仅授权 `1.x` 且限中国大陆使用

- 绑定：资源、`1.x` 版本范围、中国大陆地域范围、使用方；
- 当前事实：请求版本已发布且可交付；
- 请求情境：请求 `1.5.0`、地域为中国大陆；
- 结论：本次请求落入授权范围；
- 如果请求 `2.0.0` 或来自日本：只是不适用于该次请求，合同不发生变化。

### 场景三：会员身份影响续费价格

- 绑定：使用方、资源、当前合同周期；
- 取样：续费报价时读取会员等级；
- 计算：根据当时会员等级得到续费价格；
- 合同演进：用户接受报价并付款后，形成关联上一周期的新合同；
- 后续会员变化：不倒改已经形成的新合同价格。

这三个场景分别验证了发生记录、请求范围和时点取样，说明“动态能力”不只有监听事件这一种使用方式。

## 十二、需要坚持的设计原则

1. **合同是承诺记录，不是实时环境状态容器。**
2. **权利必须同时包含行为能力和适用范围。**
3. **本次请求不适用，不等于合同无效、暂停或违约。**
4. **事件是一次发生的证明，不是可以任意覆盖的当前值。**
5. **当前事实与历史发生记录不能互相替代。**
6. **能力提供方只提供可信凭据，不直接授予或撤销内容权利。**
7. **影响合同历史的变化必须可去重、可追溯、可解释。**
8. **只影响本次请求的情境，不应制造合同状态变化。**
9. **新增能力先定义产品契约，再允许授权产品使用。**
10. **语言、接口和代码都应服从该模型，而不是反过来塑造业务。**

## 十三、仍需继续定稿的问题

- 持续资格不满足时，平台统一使用什么产品表述：相应权利暂不产生、条件未满足，还是允许授权发布选择正式的合同中止机制？
- 次数、额度等消耗型范围在多合同并存时，使用方是否可以选择消耗哪份合同，平台默认选择规则是什么？
- “全部版本”是否覆盖合同成立前已发布的历史版本；历史版本的保存义务如何与版本授权范围分开？
- 发生记录被可信来源撤销或纠正时，已产生的合同效果怎样处理，是否需要人工裁决？
- 外部能力不可用时，哪些场景应保守拒绝，哪些应延续最近一次可信事实，哪些必须进入无法判断状态？
- 合同解释页如何同时展示合同本身、当前产生的权利以及某次请求不适用的具体范围原因？

这些问题属于平台产品规则，必须在进入策略表达或实现设计前逐项决定。
