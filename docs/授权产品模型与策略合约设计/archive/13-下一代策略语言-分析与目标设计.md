# 下一代策略语言：现状分析与目标设计（归档草稿）

当前讨论请先读[最小流程与对象全景](../12-策略合约核心抽象与场景覆盖.md)，再读[下一代策略语言业务语义设计](../13-策略产品规则与能力边界.md)。此稿仅供追溯讨论，不再作为目标模型依据。

状态：**产品语义设计草案，供讨论；不是现行语言规范、编译器计划或 CLI 实施承诺。**

本文先分析现有状态机语言和平台产品目标之间的距离，再提出策略语言应表达的业务语义。本文的“语言”是授权方能够作出何种承诺、平台能够依据承诺作出何种判断；具体关键字、语法、存储和执行器均可后定。不得用本文推断线上服务或当前 CLI 已支持这些能力。

## 1. 问题从哪里来

一个用户已经付款，获得“资源 R 的 1.x 版本可在中国大陆下载 10 次”的授权。今天他在中国请求 1.2 版本，平台允许；同一时刻他在美国的另一台设备请求同一版本，平台拒绝。两次结果不同，但付款、合约、已取得的下载权都没有改变。

如果语言只有“当前合约状态 → 一组权利”，就容易把“中国有权、美国无权”设计成两个状态，并在 IP 变化时反复迁移。这样既无法自然表达同一时刻两个不同请求，也会把地域、版本、设备、时间、用途和剩余额度的组合推成状态爆炸。问题不在于状态机技术不好，而在于**把逐次访问结论误当成合约全局状态**。

授权产品实际上要分别回答：

1. 用户接受了什么承诺，双方分别是谁？
2. 付款、广告完成等事实是否使某项权利形成，是否产生履约义务？
3. 已形成的权利覆盖什么行为、内容、版本、期间、地域和额度？
4. 这一次具体使用是否落入范围，能否实际交付，成功后如何计量？
5. 无法履约、退款、续约或争议时，原承诺如何处理？

语言首先要能分别表达这些问题，再决定哪些部分适合编译成状态机。

## 2. 现状证据与分析边界

### 2.1 已观察到的现状

| 证据 | 能确认什么 | 不能据此宣称什么 |
|---|---|---|
| 本仓库[第一版语言接入设计](../../一期/产品方案/脚手架设计/ARCHITECTURE/10-策略语言接入.md) | 当前在线手写策略有签约声明、状态机、函数事件；CLI 接入仍是未来设计 | 本文的新语义已经被在线编译接口支持 |
| 邻近研究仓库的 docs/prototype-v0.md、examples/periodic-streaming.authz 与 ContractEvaluator.kt | 研究原型 0.2 以事件驱动 Process State 迁移；当前状态内嵌 entitlement，echo 返回该状态的权利集合 | 原型已经支持签约、持久化、访问请求的地域/版本判断或额度结算 |
| 邻近研究仓库的 docs/architecture-v0.md | 早期语义基线规定“只有事件启动迁移”，状态指定权利集合 | 这种约束是平台授权产品不可改变的业务要求 |
| 本仓库[合同生命周期](./03-授权发布与合同生命周期.md)、[核心抽象](./11-授权与合约核心抽象设计.md)与[事实分类](./12-平台业务、策略合约与对象生命周期.md) | 产品目标已区分合约存续、权利范围、逐次使用、可信事实和内容交付 | 这些目标规则已全部由现行服务实现 |

这里“现行线上语言”“研究原型 0.2”和“目标产品模型”是三个不同层次。本文评估研究原型的语义方向，不要求当前 CLI 兼容新语言，也不修改邻近研究仓库。

研究原型另有 customer-classification.authz：分类值也可以是某份合约状态的输出。产品上，这类值最多是另一份内容合约可按约定读取的**资格事实来源**，不能因持有“premium”等标签便自动流入内容授权；还需要确定绑定的用户、读取时点、可信来源及原合约承诺。

### 2.2 不应让一个“状态”回答四类问题

| 问题 | 合适的业务表达 | 地域从中国变为美国时 |
|---|---|---|
| 合约是否成立、终止或进入补救？ | 合约履约历程 | 通常不变 |
| 是否已因付款、广告等取得权利？ | 权利形成依据与期间 | 通常不变 |
| 本次请求是否属于权利范围？ | 主体、行为、标的与本次情境的判断 | 可能从允许变为不适用 |
| 内容此刻能否交付？ | 资源供给和交付判断 | 需独立核验，不能用授权结论代替 |

合约可以同时有浏览权和下载权，两项权利可以有不同期间、地域和额度；多份合约还可以同时覆盖一个请求。因此单一的“当前授权状态”甚至不足以概括同一用户当前拥有的权利，更不能代表未来每一次请求的结果。

### 2.3 三种路线的取舍

| 路线 | 擅长 | 无法单独承担的部分 | 判断 |
|---|---|---|---|
| 以状态机为全部语义 | 描述付款、取消、退款、争议等离散流程 | 地域、版本、设备、用途等逐次判断；多权利和多合约组合 | 不宜作为唯一核心 |
| 只做逐次访问规则 | 根据主体、行为、资源和情境给出一次允许/拒绝 | 签约承诺、付款后取得权利、额度结算、续约、补救 | 同样不够 |
| 声明式承诺与权利范围，辅以履约流程和逐次判断 | 把承诺、事实、权利、访问与补救各放在正确位置 | 需要明确跨层时间、证据和计量规则 | 推荐的产品语义 |

属性和环境参与逐次判断并非新发明：NIST 的[属性访问控制指南](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-162.pdf)将主体、对象与环境条件纳入访问决策；[Cedar 授权模型](https://docs.cedarpolicy.com/auth/authorization.html)也按主体、行为、资源和请求情境提出一次请求。它们可启发“逐次判断”这一层，但不能代替 Freelog 的签约、履约、额度和补救产品语义。

## 3. 设计原则：以承诺为核心，不以迁移为核心

下一代策略语言的首要产物应是一项**可被接受的授权承诺**。授权方声明什么条件下授予什么权利，使用方接受时固定具体版本、选择和双方身份；平台随后凭可信事实解释承诺，并在每次使用时作判断。策略下线或改版，不倒改已经接受的承诺。

语言至少要区分九个概念：

| 概念 | 回答的问题 |
|---|---|
| 授权发布 | 哪一项可供接受的承诺被用于哪个内容？ |
| 接受与绑定 | 谁接受了哪个不可变承诺版本，签约时固定了哪些选择？ |
| 可信事实 | 平台依据谁的确认，知道何事在何时发生或何种状态成立？ |
| 履约义务 | 哪一方必须付款、交付、通知或补救？ |
| 权利取得 | 什么事实使哪项具体权利形成，期间从何时计算？ |
| 行为与标的 | 允许谁对哪个资源、单品和版本做什么？ |
| 适用范围 | 时间、地域、用途、设备、主体、次数等边界是什么？ |
| 本次决定与计量 | 此请求为何适用或不适用；成功使用后如何记账？ |
| 续约与补救 | 新周期如何形成；无法履约时双方如何处理？ |

这九个概念不是九种技术对象，更不是要求语法各写九个关键字。它们是对语言表达能力的检查表。尤其要把**取得权利的条件**与**行使权利的范围**分开：付款确认可以使下载权形成；请求地域不符只是这一次下载不在范围内。若持续资格是签约价格依据，之后变化不倒改价格；若资格是使用范围，才在每次使用时核对。

## 4. 推荐的语言语义结构

### 4.1 承诺与签约

策略要声明授权方、标的、允许提供的权利及签约资格。签约时固定策略的精确版本、当事人、所选单品或合集成员规则、版本范围、价格与补救条款。签约前检查的事实必须标明**在接受时取样**；不能以后用用户当前会员级别回写当时价格。

### 4.2 可信事实与履约

策略只能引用平台正式开放的事实能力：例如绑定本合约的订单付款成功、指定广告由指定用户完成、资格在某时点有效。每项能力须说明提供者、相关对象、发生时间、确认时间、有效范围、撤销或更正路径。用户“点击支付”和支付服务“确认收款”不能互换。

付款、完成广告、时间到期、平台治理决定可能产生持续的履约结果；同一事实重复送达不能重复授予权利。权利取得是否可重复、可累计或互斥，应在承诺中明确，不靠事件到达次数猜测。

### 4.3 权利、范围与逐次判断

一项权利应能表达：**使用主体 + 行为 + 内容及版本/单品范围 + 有效期间 + 其他适用范围 + 可用额度**。是否允许某次使用，至少依赖该权利、请求和必要的当前事实。地域、请求版本、用途、设备和服务时段通常在每次请求时核对，不触发合约迁移。

版本和合集范围也必须有明确语义：指定版本、1.x 或“含后续发布版本的全部版本”不是同一个承诺；“签约时选定单品”与“按明确规则纳入后续新增单品”也不同。语言不能仅引用当前合集页面或当前版本列表，导致作者日后编辑目录时静默改变旧合约。

权利范围与内容可交付性分开。用户可能有权取得 1.x，但该版本已因故无法交付；此时不能谎称用户“没有授权”，应显示授权依据及交付/补救问题。

### 4.4 使用计量

次数、时长、流量或金额不是一个笼统的“状态”。语言应声明**计量对象、计量单位、成功点、扣减归属及是否可重复**。请求被拒绝、下载/播放失败或重复收到交付通知，不能自动扣减。并发占额和事后纠错需要平台统一规则，不能交给每条策略随意编程。

### 4.5 续约、终止与补救

续约形成关联上期的新合约；报价时哪些资格参与折扣，是否沿用旧条款，必须显式可见。策略下线只停止新签，不影响旧合约。内容无法交付、提前撤回、退款或争议，应引用平台不可绕过的最低保护及允许的补救选项，授权方不能写出“已付费但随时无补救下架”的规则。

## 5. 一份概念性策略长什么样

下面只展示**人能够审阅的语义骨架**，不是建议立即实现的具体 DSL 语法：

~~~text
授权发布：视频 R 的个人下载许可

签约对象：个人账户；绑定资源 R 和本次接受的条款版本
签约时：选择版本范围 1.x；确认价格 30 元

履约：
  与本合约绑定的订单由支付服务确认收款 30 元后，
  为该使用方取得一项下载权

下载权：
  标的：资源 R 的 1.x 版本
  期间：付款确认起 30 天
  地域：每次下载请求须来自中国大陆
  额度：最多 10 次成功交付

计量：只有本次下载实际成功交付，才对所依据的这份合约扣 1 次
续约：发起新周期报价并形成关联的新合约，不修改本期
补救：范围内版本无法交付时，进入平台规定的通知与补救流程
~~~

这个例子故意没有“在中国 → active、在美国 → inactive”的迁移。付款确认使权利形成；时间、地域、版本与余额在本次下载时参与判断；交付成功后才结算额度。相同合约在中国请求可允许、在美国请求可拒绝，两次结果互不改写合约。

再看“完成指定广告得 24 小时浏览权”：策略需要绑定广告活动，明确完成记录对应同一使用方、一次完成可奖励几次、完成时需满足哪些资格，以及 24 小时从何时算起；后续浏览仍按请求地域、版本等范围判断。仅写“收到广告事件就进入有权状态”会遗漏这些承诺。

## 6. 一次使用应怎样得出结论

~~~text
本次主体、行为、资源/版本、用途和情境
  → 找出该主体可能依据的合同
  → 对每份合同独立确认承诺版本、已形成权利及其范围
  → 核对本次时间、地域、版本、资格与可用额度
  → 若多份合同可用，确定本次依据及额度归属
  → 输出允许/不适用/条件未满足/事实暂不可核验及解释
  → 获准后再核对内容交付；实际使用成功后结算
~~~

多份合同的权利可以提供不同依据，但不能把 A 合同的下载次数与 B 合同的地域范围拼出一项任何合同都未承诺的“超级权利”。一次有额度的使用必须能归属到具体合同或权利。平台强制治理限制属于单独的受控覆盖层，不能伪装成授权方修改旧合同。

“事实暂不可核验”不等于“不满足条件”：平台在无法确认地域或付款时不得凭猜测放行，但应向用户区分未知、范围不符和确实未付款。授权决定与实际交付结果也要分开记录。

## 7. 状态机保留在哪里

状态机仍适合**边界清楚、会留下持续结果的具体流程**：支付订单待付/已付/退款，广告任务开始/完成，退款申请受理/结案，合同成立/解除/补救。它也可以成为某些履约条款的执行方式或编译目标。

但状态机不应成为“当前是否有授权”的唯一权威：

- 当前 IP 国家、设备、请求版本和用途是一次请求的输入，不是合约全局状态；
- 到期判断可以直接比较约定期间与本次时间；定时任务可负责通知或结算，不必为了拒绝过期请求制造一次迁移；
- 一份合约可有多项不同的权利、额度和义务，不能靠单个 Process State 概括；
- 多份合同可同时适用，合约间权利不能压扁成用户的一个全局状态。

因此不必先决定“要不要删掉 PS/ES”。先把产品语义定清，再决定现有 PS/ES 如何映射履约过程与权利集合；如果它无法表达请求范围，也应增加独立的逐次判断语义，而非堆叠更多地域/时间状态。这是对研究原型的设计建议，不是已验证的迁移方案。

## 8. 语言必须提供的可验证保障

授权方写策略时，平台至少应在**发布前**检查：

- 事实能力已注册，来源、主体关联、类型、时间语义和隐私权限明确；不能引用任意外部变量。
- 标的、行为能力、版本/单品、时间、地域和额度的单位与范围有效；默认值不会意外造成永久或无限授权。
- 签约取样、行为完成时检查、逐次使用检查和事后计量的时点不混淆。
- 同一策略的重叠规则不会对同一事实给出自相矛盾的权利结果。
- 退款、撤回、不可交付等情形不绕过平台最低补救规则。
- 用户能在签约前读懂权利、限制、付款/广告条件、续约与补救；运行时能看到结论依据。

**运行时**还必须保证重复付款/广告完成通知不重复授予，重复交付通知不重复扣额，额度并发使用有一致的结算依据，事实更正留有历史，无法核验时不凭猜测放行。这些不能靠发布前静态检查代替。

这些保障也不是都要在 DSL 中暴露成可编程选项。尤其并发计量、事实更正、可信来源不可用和平台最低保护，应由平台统一定义安全语义，作者只在允许的产品选项内选择。

## 9. 仍需先定稿的产品问题

1. 同一请求有多份可用合同时，默认选择哪份作为依据并扣减额度？用户能否选择？
2. 事实的实际发生时间、平台确认时间、对权利生效时间不一致时，以哪个为准？
3. 外部事实撤销或迟到时，已经取得或消耗的权利如何更正，何时进入人工争议？
4. 请求地域、设备和资格无法可靠核验时，哪些结论显示“待核验”，哪些受平台强制限制？
5. “全部版本”是否覆盖合同期间后来发布的版本，以及历史版本无法交付的补救规则，以已接受承诺为准如何展示？
6. 哪些资格是签约时一次性定价依据，哪些可以是持续使用条件？持续条件变化是否还触发额外通知或补救？
7. 策略可以选择哪些补救安排，哪些最低保护不能由授权方排除？

这些问题没有结论前，不宜冻结表层关键字或以研究原型的状态图反推业务答案。

## 10. 结论与后续顺序

推荐的语义内核是：**不可倒改的授权承诺 + 可核验的业务事实 + 权利取得与义务履行 + 有范围的权利 + 每次请求独立判断 + 使用结算与补救**。状态机服务其中明确的履约流程，不充当所有授权结论的容器。

后续先用付款、广告、地域、会员、版本、次数、合集、多合同、续费和下架补救组成产品样例集，逐个写清“签约前看到什么、事实何时成立、产生何种权利、一次使用怎样判断、异常怎样解释”；再讨论正式句式、编译校验和对现有系统的渐进接入。语言应接受这些样例的检验，而不是要求样例适应既有语法。
