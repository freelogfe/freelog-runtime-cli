# 多合同、升级与续费

## 目标

同一使用方可能多次获得同一内容的授权：重复点击、购买更长周期、升级为商业用途、从合集取得单品后又单独购买、或进行续费。产品需要防止无意义的重复签约，同时允许真实的扩展交易，并让用户明白最终拥有什么。

## 1. 签约前先比较“实际权益”

不能只比较内容相同或范围大小。平台应比较：内容、能力、单品范围、版本范围、用途、地域、次数/额度、有效期、价格、待履行义务与解除安排。

| 与当前有效合同的关系 | 默认产品动作 |
|---|---|
| 完全相同 | 不创建重复合同，直接展示现有合同 |
| 新合同的实际权益完全被覆盖 | 提示“你已拥有不弱于此的授权”，默认不再签约 |
| 新合同更广、更久或增加能力 | 进入升级或续期流程，清楚说明新增权益和与旧合同的关系 |
| 彼此独立、各有价值 | 允许并存，签约前展示叠加效果与各自义务 |
| 存在冲突 | 阻止直接签约，要求选择替换、等待旧合同结束或联系支持 |

比较结果要可解释。用户不能只看到“不可签约”，而应看到是哪份现有合同覆盖了什么权益、何时到期，以及为何新合同没有额外收益。

## 2. 多合同的默认聚合规则

推荐规则是“**权利按合同来源分别存在，使用时选择能够支持该动作的有效合同**”。

- 对浏览、下载、使用等可独立判断的能力，只要任一有效合同在相应范围内授予，即可行使。
- 次数、额度、设备数、地域、用途等限制不应简单取最大值；平台必须知道本次使用消耗或依据的是哪一份合同。
- 付款、署名、分成、通知等义务仍归属于产生它的合同，不能因另一份合同存在而自动消失。
- 用户页面应给出“当前使用依据哪份合同”的解释，并允许在多份都可用时查看选择逻辑。

这比“全部取并集”更安全，也避免低价合同和高价合同的限制被错误混合。

## 3. 升级与替换

升级不是悄悄让新合同覆盖旧合同，而是一项明确交易。升级页应显示：

- 旧合同与新合同各自的权利和限制；
- 新增、减少和保持不变的权益；
- 旧合同是否继续有效、是否按比例抵扣、是否提前结束；
- 支付差额、退款或不可退款条款；
- 发生失败时恢复到哪个合同状态。

推荐默认：新合同只增加新权益，旧合同继续保留。只有使用方显式确认“替换”且授权发布允许时，平台才可结束或迁移旧合同的指定部分。替换不会抹去旧合同历史。

## 4. 续费：新的周期合同

续费应创建新的合同周期并关联上一周期，而不是修改旧合同。这样可保留每一期的价格、资格、付款和实际条款，也可支持首期优惠、连续续费折扣和恢复订阅。

续费产品需要明确：

| 决策 | 推荐规则 |
|---|---|
| 何时可续 | 在到期前的续费窗口内；到期后可转为重新签约 |
| 续费内容范围 | 默认沿用上一周期的单品范围和版本范围；若任一范围会变，必须显式确认 |
| 续费条款 | 默认沿用上一期已接受条款；采用新版时必须展示差异并重新确认 |
| 续费价格 | 显示原价、续费价、折扣依据与下次价格规则 |
| 自动续费 | 必须单独授权、可随时关闭，并在扣款前提供提醒和取消窗口 |
| 付款失败 | 不倒改旧周期；按宽限期或到期规则进入暂停/结束 |

## 5. 合集与单资源合同重叠

用户可以通过合集合同取得某个单品，也可以单独签约该单品。平台不应假定两者必然重复：合集可能只授予浏览，单品可能授予下载；合集可能只有 30 天，单品可能永久。

签约前比较仍按实际权益进行。详情页与已授权内容库应把“来自合集的权利”和“来自单品的权利”分别解释，避免用户误以为移除合集成员会让自己丢失独立购买的单品合同。
