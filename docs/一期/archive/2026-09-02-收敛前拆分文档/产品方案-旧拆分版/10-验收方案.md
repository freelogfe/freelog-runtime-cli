# 10 · 验收方案

> **文档角色：** 定义一期 CLI 产品和实现的验收方式。本文面向产品、测试、开发和 AI/CI，确保不是“文档写了很多但不能判断完成”。

最后更新：2026-09-01

## 1. 验收原则

每项能力必须同时回答：

1. 用户能不能顺畅完成？
2. 字段和流程是否对齐 Console？
3. CLI 特殊场景是否处理？
4. 失败后是否可理解、可恢复？
5. AI/CI 是否能判断结果？
6. 是否有本地和目标环境证据？

## 2. 验收层级

| 层级 | 目的 | 通过标准 |
|---|---|---|
| L0 文档治理 | 防止方案散乱、旧命令回流 | 主线文档完整，链接可解析，无过期命令 |
| L1 纯本地契约 | 字段、payload、状态机、错误码 | 单元和契约测试通过 |
| L2 本地集成 | 多步骤命令组合、manifest/state/report | 不依赖真实平台或少依赖平台 |
| L3 dev/test 真实环境 | 平台接口真实可用 | 使用授权账号完成关键路径 |
| L4 production 签字 | 正式环境可交付 | production 开放后专项签字 |

## 3. 产品验收矩阵

| 流程 | 必须证明 |
|---|---|
| start 主入口 | 新用户能从一个命令进入正确流程 |
| 类型选择 | 可逐级选择，也可搜索；主题/插件/package 可发现 |
| 单资源发行 | 从本地文件到 create/version/policy/online 完整走通 |
| 主题发行 | 主题入口、模板、构建、目录 zip、策略、上线 |
| 插件发行 | 插件入口独立，不混主题文案 |
| package 发行 | namespace、模板、leaf 类型映射清楚 |
| 目录 zip | 不与批量/合集混淆 |
| 维护已有资源 | bind/pull/update/version edit/publish 边界清楚 |
| 策略模板 | 先选模板、填变量、预览、应用 |
| 上下架 | latestVersion、启用策略、owner、frozen 门禁有效 |
| 依赖授权 | 免费可处理，付费/复杂签约可 handoff |
| 批量 | 预览、20 个一批、report、resume、unknown 对账 |
| 合集 | 合集壳、目录草稿、合集版本、策略、上线边界清楚 |
| RSS | preview、验证码、1000 条限制、sync、failed-items、锁字段 |
| collect-rules | 条件字段、操作符、值、语义预览完整 |
| session | 临时维护不落 manifest/state |
| studio | 多账号凭据不落盘，子工程可恢复 |
| AI/CI | 无 prompt，JSON/NDJSON/exit code/report 稳定 |

## 4. 字段验收矩阵

| 字段组 | 必测 |
|---|---|
| resource | type leaf、title、name、custom type |
| listing | intro、cover、tags、RSS lock |
| file | path、format、size、sha1、directory-zip ignore |
| version | first 1.0.0、semver递增、reuse、version edit 边界 |
| properties | 文本/整数/小数/日期/枚举/只读属性 |
| custom descriptors | name/key/description/options |
| policy | template、policyName、variables、translation、duplicate |
| online | version/policy/owner/frozen |
| dependency | versionRange、auth tree、paid handoff |
| batch | item count、item name、item title、report |
| collection | itemTitle、display、sort、merge flag |
| RSS | feedUrl、ownerEmail、code、date range、lock |
| collect-rules | status、serializeStatus、conditionType、field/operator/value |

## 5. 场景验收

### 5.1 普通作者

```text
start
  → 发布单文件图片
  → 逐级选择图片类型
  → 填 title/name
  → publish
  → 选择免费策略模板
  → online
```

通过：用户不需要知道 type code、不需要手写 policy、不需要猜下一步。

### 5.2 主题开发者

```text
start
  → 发布主题
  → 选择主题模板和 runtime
  → build
  → directory-zip publish
  → policy template
  → online
```

通过：主题类型、runtime、构建目录、策略、上线都明确。

### 5.3 插件开发者

通过标准：

- 插件入口独立；
- 插件 leaf 类型可选；
- 文案不出现主题误导；
- 构建失败不会上传。

### 5.4 package 开发者

通过标准：

- package 模板可选；
- namespace 必填；
- leaf 类型无法唯一映射时要求确认；
- 不和插件/主题混淆。

### 5.5 批量运营

通过标准：

- 预览候选/跳过/拒绝；
- 超过 20 自动拆批；
- 部分失败有 report；
- unknown 不自动重试。

### 5.6 策展人

通过标准：

- 创建合集壳；
- 添加已有资源；
- 从本地目录导入子资源；
- 编辑排序和展示；
- collection publish；
- 策略和 online。

### 5.7 RSS 维护者

通过标准：

- inspect/preview；
- ownerEmail 处理；
- 验证码；
- 1000 条日期范围；
- sync/status/failed-items；
- 锁字段阻断。

### 5.8 AI/CI

通过标准：

- 缺参数 code 4；
- 无 prompt；
- stdout JSON；
- 长任务 NDJSON；
- report 可恢复；
- handoff code 5。

## 6. 负向验收

必须覆盖：

- 未登录；
- auth 损坏；
- env 不一致；
- owner 不符；
- 选中父类型；
- 类型不支持上传；
- 文件不存在；
- 文件超大小；
- sha1 被他人发行；
- version 不递增；
- 无策略上架；
- 停用最后启用策略；
- 付费策略；
- 批量 unknown；
- RSS 无 ownerEmail；
- RSS `matchedItemCount` 超过 1000；
- collect-rules 空条件；
- session 结束后状态不保存。

## 7. 手动测试标准

手测记录必须包含：

- 日期；
- CLI 版本；
- env；
- 测试账号标识，但不记录密码/token/cookie；
- 输入文件或 fixture；
- 执行命令或 TTY 路径；
- 平台结果；
- 本地 manifest/state/report；
- 失败和恢复路径；
- 是否与 Console 对齐；
- 遗留差异。

## 8. 文档验收

文档必须满足：

- 本目录本身能读通；
- 不依赖“去看旧文档才能知道流程”；
- 每条流程都写字段和异常；
- 实现方案不写具体代码文件名当作方案；
- 旧文档只能作为证据/历史材料；
- 文档链接可解析；
- 敏感账号密码不进入文档。

## 9. 实现验收

实现完成时必须证明：

- 架构分层符合 [09-实现解决方案.md](./09-实现解决方案.md)；
- 每个流程可追踪到 use case；
- 字段总账中的 HARD 约束都有校验；
- TTY 和 AI/CI 共用业务规则；
- session/studio 不降低门禁；
- 平台写入有 preflight 和对账；
- report 能恢复长任务；
- Console handoff 不伪造成功。

## 10. 完成判定

只有当产品、字段、流程、异常、实现架构、验收全部闭环，才可以说一期 CLI 产品方案完成。单独“代码能跑”或“文档很长”都不算完成。
