# 一期 CLI 产品与实现方案入口

> **文档角色：** 一期 Freelog Runtime CLI 的完整产品设计与实现解决方案入口。本目录是主线方案，不是材料索引；研发、测试、产品评审都应从这里开始。

最后更新：2026-09-01

## 1. 本目录解决什么问题

本目录要回答完整的一组问题：

1. CLI 的产品目标是什么，用户为什么用它？
2. Console 的资源发行、维护、策略、合集、RSS、collect-rules 等业务流程如何在 CLI 中对齐？
3. CLI 自己的终端体验、会话模式、多账号、AI/CI、模板、构建、压缩、批量、恢复怎么设计？
4. 每条流程有哪些字段约束、接口顺序、状态门禁、失败和恢复处理？
5. 实现时应该采用什么架构、状态机、数据契约和验收门禁？

## 2. 本目录的推导链路

```text
用户需求
  → Console 业务分析
  → CLI 环境差异分析
  → 产品原则
  → 业务对象和状态模型
  → 命令与交互方案
  → 分流程解决方案
  → 字段约束、异常恢复、实现和验收
```

读者不需要再去 `对齐/`、`开发/` 或 `场景/` 拼一套设计。那些目录只负责提供证据、实现细节和验收材料。

## 4. 方案和证据的关系

本目录必须自洽，可以直接指导实现。Console 源码证据、场景校验卡和现有代码只能作为核对材料：

| 材料 | 用途 |
|---|---|
| `../对齐/` | Console 事实证据：业务流程、字段限制、接口调用 |
| `../场景/` | 编号场景校验卡：用于挑战本方案是否遗漏 |
| `../开发/` | 旧实现规格和字段账本：用于核对，不作为产品真源 |
| `../使用/` | 编号最终用户手册：实现完成后从本方案同步 |
| `../验证/` | 手测和环境报告：记录某次版本、环境下的结果 |

如果本目录和参考材料冲突：

```text
先确认 Console 事实
  → 修正本目录方案
  → 再同步开发/使用/验证文档
  → 最后改代码
```

当前代码实现不得反向决定产品。

## 5. 完整性的最低标准

本目录中的每条主流程都必须包含：

- 用户目标；
- TTY 交互路径；
- 非交互 / AI / CI 等价路径；
- Console 业务对齐点；
- 平台接口顺序；
- 字段约束与提示；
- CLI 特殊体验处理；
- 本地写入与平台写入边界；
- 失败、取消、冲突、恢复和 Console 接力；
- 验收标准。

如果某条流程缺其中任一项，就不能说设计完成。
