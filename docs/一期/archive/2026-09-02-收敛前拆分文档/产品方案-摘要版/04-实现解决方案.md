# 04 · 实现解决方案

> **文档角色：** 定义一期 CLI 的实现边界、模块职责和验证策略；不绑定旧代码文件名，不把旧实现当成产品依据。

最后更新：2026-09-02

## 1. 实现分层

```text
CLI Entry
  → 解析命令、TTY/非 TTY、全局参数、环境

Interaction Layer
  → start/studio/session 向导、字段提示、确认、取消、Console 接力

Use Case Orchestrators
  → publish/update/policy/dependency/collection/rss/batch 的业务编排

Domain Services
  → 类型树、字段校验、策略模板、依赖授权树、RSS 差异、collect-rules

Artifact Layer
  → 本地文件扫描、ignore、build 编排、zip、SHA1、上传

State & Report Layer
  → manifest、state、auth、write lock、batch/studio report、resume/retry

Platform Adapter
  → Freelog API 调用、payload normalize、错误码映射、环境保护

Output Layer
  → 人类输出、JSON envelope、NDJSON events、exit code
```

实现时应先按职责重构，不按当前目录名倒推职责。如果旧文件结构阻碍职责清晰，可以移动或合并；没有旧代码负担时优先选择清楚的边界。

## 2. 核心状态机

### 单资源发行

```text
local_validated
  → artifact_ready
  → uploaded
  → resource_created 或 resource_bound
  → version_created
  → listing_updated
  → online_requested
  → state_written
```

任一平台写入后失败，都必须记录是否可安全重试。不能用“命令失败”掩盖平台可能已创建资源或版本。

### 批量发行

```text
run_created
  → scanned
  → item_planned
  → item_remote_started
  → item_remote_confirmed / remote_outcome_unknown
  → item_local_written / remote_succeeded_local_pending
  → run_done
```

### RSS/合集

```text
collection_selected
  → feed_compared / items_planned
  → user_confirmed
  → platform_updated
  → sync_state_written
```

## 3. 字段校验实现原则

- Console 字段限制应沉淀为统一 field registry，而不是散落在每个命令。
- TTY prompt、manifest validate、平台写入前 validate 必须复用同一校验器。
- 硬约束失败时停止；软提示只能 warning，不得改变 payload。
- 平台枚举、资源类型和策略模板优先运行时读取；无法读取时明确失败。
- 字段提示先说用户语言，再在 debug/JSON details 中给字段名。

## 4. 交互实现原则

TTY 主路径应是连续任务流：

```text
任务选择 → 类型/资源选择 → 字段补全 → 预检 → 写入 → 后续动作
```

每个 prompt 必须具备：

- 当前步骤目的。
- 输入约束。
- 默认值来源。
- 返回/取消方式。
- 写入前是否还会确认。

搜索只能作为加速能力；资源类型、策略模板、依赖授权树都必须保留可浏览路径。

## 5. 本地资源文件管理

- manifest 是长期意图，适合 Git。
- state 是平台事实，不适合 Git。
- reports 是恢复凭证，不应被用户手工编辑。
- auth 必须加密；凭据不得进入 manifest/state/report。
- 压缩产物默认临时化，不把 zip 当成长期源文件。
- dry-run 零持久副作用：不写本地、不上传、不创建平台对象。

## 6. 平台适配与错误

Platform Adapter 负责：

- 统一 env base URL 和 production 门禁。
- 统一认证头、刷新和脱敏。
- 统一 API payload normalize。
- 统一 Console/API 错误码映射，例如 RSS 验证码错误。
- 对非幂等创建提供对账入口。

业务层不得直接拼接平台 URL 或直接吞平台异常。

## 7. 输出契约

人类输出：

- 结果先行。
- 说明当前状态。
- 给下一步命令。
- 长列表分页或过滤，不刷屏。

JSON：

```json
{
  "schemaVersion": 1,
  "ok": true,
  "command": "publish",
  "data": {},
  "warnings": [],
  "meta": { "env": "dev" }
}
```

NDJSON：

- 每行一个事件。
- stdout 只放协议。
- stderr 放日志和诊断。
- 批量任务必须包含 `start`、`ok`、`fail`、`skip`、`done`。

## 8. 重构实施顺序

1. 先固定字段 registry、错误码、JSON/NDJSON envelope 和状态机测试。
2. 再整理 store/auth/report/write lock，确保本地资源和凭据边界清楚。
3. 再实现 start/studio/session 的连续交互体验。
4. 再对齐单资源、策略、依赖、上下架。
5. 再对齐合集、RSS、collect-rules。
6. 最后做批量和恢复能力的体验打磨。

每一步完成后都要保证现有可交付路径不退化，不能为了“架构漂亮”破坏用户主路径。
