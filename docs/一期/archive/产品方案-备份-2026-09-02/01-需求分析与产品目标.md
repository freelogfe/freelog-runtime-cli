# 01 · 需求分析与产品目标

> **文档角色：** 需求分析和产品目标。本文回答“为什么要做 CLI、用户要完成什么、哪些体验不能妥协”。

最后更新：2026-09-02

## 1. 背景问题

Console 适合人通过 UI 一步步创建和维护资源，但它天然不适合以下场景：

- 本地电脑上已有大量资源文件，需要快速发行或更新。
- 一个前端工程、主题工程、插件工程需要构建、压缩、打包后发布。
- 用户只想先创建一个可运行的主题/插件工程，或先把目录打成可检查、可复用的发行包，不一定马上写平台。
- 用户希望一次会话完成资源类型、版本、策略、listing、上架，而不是在多个页面来回跳。
- AI 或 CI 需要可预测的输入输出、结构化错误和可恢复报告。
- 多账号、临时会话、不同环境之间需要明确隔离，不能靠浏览器状态猜。

CLI 的价值不是复制 Console 页面，而是把 Console 业务规则转成终端里更高效、更清晰、更适合本地文件和自动化的流程。

## 2. 用户画像

| 用户 | 主要目标 | 典型上下文 | 不能接受 |
|---|---|---|---|
| 普通作者 / 普通资源发布者 | 把本地图片、音频、视频、Markdown、压缩包等发行成平台资源 | 终端不熟，依赖提示完成 | 一堆参数、字段含义不清、失败后从头再来 |
| 工程/主题/插件开发者 | 构建本地项目，发布主题/插件资源或更新版本 | 熟悉终端，需要模板、构建、压缩、版本号 | CLI 不懂工程结构、需要手动整理产物 |
| 主题开发者 | 构建并发行主题资源，再去 Console 完成节点主题激活 | 需要本地模板、构建、压缩、依赖插件检查 | CLI 漏掉主题资源类型，或把节点激活伪装成已闭环 |
| 插件开发者 | 构建并发行插件资源，供主题依赖或后续签约使用 | 需要插件模板、版本、策略、依赖检查 | 插件类型不可选，依赖/签约状态不可见 |
| 合集维护者 | 创建合集、添加资源、排序、维护 RSS 或自动收录 | 资源数量多，频繁维护 | 条目和资源本体混淆，误改线上 listing |
| 运营/内容管理员 | 批量发布、上下架、改标签、维护展示信息 | 需要审查和报告 | 没有预览、没有差异、没有恢复 |
| AI/CI 调用方 | 通过 manifest 或脚本稳定完成资源操作 | 无 TTY、需要 JSON/NDJSON | 输出不稳定、错误不可解析、需要人工接管 |

## 3. 核心用户任务

| 任务 | 用户语言 | 产品必须支持的结果 |
|---|---|---|
| 首次发行单资源 | “把这个文件发布成 Freelog 资源” | 创建资源壳、创建版本、选择策略模板、填写 listing、可选择上架 |
| 更新已有资源 | “这个资源发一个新版本” | 读取远端最新状态、继承可继承字段、创建新版本、保留恢复记录 |
| 维护线上资源 | “改封面/简介/标签/上下架/策略” | 展示当前值与 diff，只提交用户改过的字段 |
| 创建模板工程 | “给我建一个 React 主题/插件项目” | 选择模板、生成本地工程、写入可追溯模板信息、给出开发/构建/发布下一步 |
| 独立压缩打包 | “先把这个目录打成 Freelog 可发布包让我检查” | 扫描目录、应用 ignore、生成确定性压缩包、输出路径/大小/sha1，不写平台 |
| 本地工程发行 | “构建并发布这个项目” | 根据模板/manifest 执行构建、压缩、产物确认、再进入资源发布 |
| 批量发行 | “把这个目录里一批文件都发出去” | 扫描、命名模板、预览 create/update/skip/fail、分批写入、逐项报告 |
| 创建合集 | “把这些资源做成合集” | 创建合集资源、添加条目、排序、策略、listing、上架 |
| RSS 合集 | “绑定播客 RSS 并同步单集” | 检测 feed、验证码、数量限制、日期筛选、GUID 差异确认、锁定字段 |
| 自动收录 | “让合集自动收录符合条件的资源” | 条件构造器、字段/操作符/值联动、启用/停用、规则摘要 |
| 主题/插件资源 | “发布主题/插件并告诉我怎么去 Console 激活/签约” | CLI 完成资源发行，输出 Console 接力信息 |

## 4. 产品目标

1. 业务对齐：字段、接口、创建/更新顺序、禁用条件与 Console 对齐。
2. 体验重做：终端里必须有清晰的向导、预览、确认、撤销、恢复，而不是把 UI 表单硬搬成参数。
3. 本地优先：文件、目录、工程模板、构建、独立压缩、manifest、报告是 CLI 的一等能力，不只是发布流程内部步骤。
4. 自动化友好：同一套业务规则必须支持 TTY、非交互、AI/CI。
5. 安全明确：登录信息、会话、环境、账号、owner、写入副作用必须清楚可见。
6. 失败可行动：每个失败都告诉用户卡在哪个字段/步骤、当前状态是否已写远端、如何继续。

## 5. 非目标

- 不把 CLI 做成 Console 的低配页面。
- 不要求用户记住 Console 内部字段名才能完成发行。
- 不默认执行支付、签约、节点主题激活等强 UI/风控流程。
- 不在代码中偷偷补设计文档没有定义的规则。
- 不为旧实现保留错误交互兼容。

## 6. 成功标准

| 维度 | 成功表现 |
|---|---|
| 新用户 | 输入一条入口命令后，能通过提示完成首次资源发行 |
| 熟练用户 | 能用 manifest/参数/脚本稳定复现同一流程 |
| AI/CI | 能拿到机器可读的 plan、dry-run、result、error、resume 信息 |
| 业务一致性 | 同一字段在 Console 和 CLI 的必填、长度、枚举、禁用条件一致 |
| 本地体验 | 工程构建、压缩、模板、批量和恢复不需要用户手动拼流程 |
| 可维护性 | 新增资源类型、策略模板、collect-rules 操作符时，不需要改硬编码业务全集 |

## 7. 体验底线

- 用户永远能知道当前在哪一步、还缺什么、下一步会不会写远端。
- 搜索只能是加速入口，不能替代逐级浏览和可探索选择。
- 策略默认必须先看模板再应用，手写策略只能是高级能力。
- 模板创建可以独立完成，也可以在发布流程中作为内容来源；不能只有 `init` 或只有 `publish` 内部隐式模板。
- 压缩打包可以独立完成，也可以由发布流程调用；独立压缩不得上传或写平台。
- 批量不能是黑盒，必须逐项报告。
- RSS 和 collect-rules 必须是两个独立能力，不能混成一个“合集自动化”。
- 主题/插件必须作为资源类型进入发行流程，不能被遗漏。
