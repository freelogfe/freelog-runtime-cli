## 2. 逐项裁决

### 2.1 Q1 · sign 成功后如何得到 `presentableId`

**背景：** Console `FSignResourceToNodeDrawer` 在 `batchCreatePresentable` 成功后主要使用 per-resource `{ status: 1|2, data: string }`，UI 跳转节点管理页，**未稳定**将 `data` 当作 `presentableId` 写入状态。

**裁决：**

1. CLI **不得**假设 `batchCreatePresentable` 响应里 `data` 字段恒为 `presentableId`。
2. 每条资源 sign **成功**后，CLI **必须**调用 `Exhibit.presentableDetails({ resourceId, nodeId })` **反查** `presentableId`，并写入 JSON `data.presentableId`。
3. 批量 sign 时，JSON 返回 `results[]`：每项含 `resourceId`、`status`、`presentableId?`、`error?`；部分失败不整体假成功。
4. `--dry-run` **不**调用 create，但可调用 `presentableDetails` 做重复签约检查。

**可推翻条件：** 平台 API 文档或 Console 后续版本明确 `data` 即为 `presentableId` 且稳定；届时可简化为直接读取，仍保留反查作为兼容 fallback。

---

### 2.2 Q2 · `authException` 与 `ownerFreeze`

**背景：** Console Drawer `handleResource` 将 `batchAuth` 失败标为 `authException`、`batchUserList` 作者 `status===1` 标为 `ownerFreeze`，资源仍进入 **goodResources**（可签约列表），仅 UI warning。

**裁决：**

| 检查 | dry-run JSON | 默认 sign | `--strict` |
|---|---|---|---|
| `authException` | `checks.authChain: "warn"` | **允许** sign | **code 4**，禁止 sign |
| `ownerFreeze` | `checks.ownerFreeze: "warn"` | **允许** sign | **code 4**，禁止 sign |
| 资源未上架 / 已封禁 / 未发行 | `fail` | code 4 | code 4 |
| 重复签约 | `fail` | code 4 | code 4 |

**理由：** 与 Console Drawer 默认行为 **PARITY**；`--strict` 为 **CLI_ONLY** 增强，供 CI/Agent 保守编排。

**可推翻条件：** 产品要求 Agent 默认与 Console 硬门禁完全一致且 Console 改为 block — 届时同步改默认行为。

---

### 2.3 Q3 · 批量上架与 policy

**背景：** Console 展品 Tab 单条上架走 `onlineExhibit()`（policy 弹窗链）；批量上架直接 `batchUpdatePresentableStatus`，**不**逐条跑 policy builder，可能部分失败。

**裁决：**

| 能力 | 2.0 | 说明 |
|---|---|---|
| `node exhibit online <id>` | ✅ | 完整 preflight：至少一条 **status=1** policy；否则 code 4 + hint |
| `node exhibit offline <id>` | ✅ | 无 policy 前置 |
| 批量 online/offline | ⏭ 2.1（NM-18 相关） | 2.0 **不注册**；文档明示「不等价 Console 批量上架」 |

**理由：** Agent 首版求确定性与可解释失败；批量上架 policy 缺口在 Console 亦靠 ResultModal 事后展示，不适合 headless 默认路径。

---

### 2.4 Q4 · 付费 policy / 合约 handoff

**背景：** Console 签约 Drawer 对全局 `ret/errCode` 处理为主；付费策略可能需 Console 合约/收银，与一期 `dep auth` handoff 形态应对齐。

**裁决：**

1. 检测到需付费签约或平台返回合约/支付相关错误 → **exit code 5**。
2. JSON `error` 必含：`reason`（如 `payment_required`）、`contractsUrl` 或 `actionUrl`、`nextCommand`（人类/Agent 可重跑的完整 CLI 命令）。
3. TTY 可展示 URL；**非 TTY / `--json` 不自动打开浏览器**（与 DESIGN handoff 一致）。
4. `--dry-run` 在能静态判断时设 `checks.paymentRequired: true`，否则 sign 失败时再 handoff。

**可推翻条件：** 后端提供 headless 免费合约直签 API 且纳入 parity 范围。

---

### 2.5 Q5 · 主题类资源 sign vs activate

**背景：** Console 主题 Tab 用 `createPresentable` + `onlineExhibit` 激活 `nodeThemeId`；Drawer 路径 `batchCreatePresentable` 对「主题」类资源签约后可能跳转 theme Tab，但 **不** 等价于整站主题切换确认流。

**裁决：**

1. **`node exhibit sign` 允许**对「主题」类 **已上架** 资源创建 presentable（API 与 Drawer 一致）。
2. **`node theme activate` / 修改 `nodeThemeId` → OUT**（Console）。
3. sign 成功后 JSON 含 `resourceType`；若含「主题」，附加 `hint`：「整站主题激活请在 Console 完成」。
4. `exhibit list` 默认 `omitResourceType: 主题` 与 Console 展品 Tab 一致；主题列表不纳入 2.0 MVP。

---

### 2.6 Q6 · 市场 keywords / resourceType 筛选

**背景：** `discoverPage` model 已支持 `keywords`、`resourceType`；当前 market **页面 UI** 仅暴露分类 + operationTypes 排序。

**裁决：**

1. CLI `market search` **暴露** `--keywords`、`--type`（映射 `resourceType` / typeCode），与 model 能力 **EQUIVALENT**，优于当前 market UI 窄筛选。
2. 文档标注：Console UI 未暴露的筛选项，CLI 仍合法，以 `Resource.list` 契约为准。
3. 默认 `status: 1` 不可通过 flag 关闭（市场语义固定）。

---

### 2.7 Q7 · batchCreatePresentable 分项 status 与 data

**背景：** Drawer `onOk` 类型为 `{ [resourceId]: { status: 1 | 2; data: string } }`（L26–35、L313–316）。Console UI 不依赖 `data` 作为稳定 presentableId（见 Q1）。

**裁决：**

1. CLI **仍以 Q1 反查** 为 `presentableId` 真源；**不**解析 batch 响应 `data` 字符串。
2. 解析 `results[]` 时：`status` 成功项 → 反查；`status=2`（或平台失败码）→ 该项 `failed`，写入 `error`，不假装成功。
3. 全局 `ret !== 0 || errCode !== 0` → 整体失败；已发出请求但无响应 → [17 R3](./17-展品状态机与恢复模型.md#r3--反查-presentableid-失败) 停损。

**可推翻条件：** 平台 OpenAPI 明确 status/data 语义且与 Q1 反查一致。

---

### 2.8 Q8 · ownerFreeze 字段语义（照抄 Console）

**背景：** Drawer L181–184：`ownerFreeze := batchUserList.find(...)?.status === 1`。字段名像「作者冻结」，但实现为 **status===1 即 warning**。

**裁决：**

1. CLI JSON 使用 checks 字段名 **`ownerFreeze`**（与 Q2 一致），**语义 PARITY Console**，不在 CLI 层「修正」平台含义。
2. 文档与 hint 写：**「与 Console Drawer 作者状态 warning 一致」**，避免读者按字面理解 status 枚举。
3. 测试并排：对照 Console 黄标即可，不要求与业务词典一致。

---

### 2.9 Q9 · 市场合集（subjectType=4）与 sign

**背景：** `discoverPage.fetchDataSource` 对合集拉 `getVersionList`（L282–294）；市场可见合集条目。NM-19 合集展品 **3.0 OUT**。

**裁决：**

1. **2.0：** `market search/show` **可** 返回 `subjectType=4` 项（PARITY 列表）。
2. **2.0：** `node exhibit sign` preflight 对合集 → **code 4**，`reason: collection_exhibit_not_supported`，hint 指向 3.0 / Console。
3. **不** 在 2.0 注册合集展品 CRUD 命令。

---

### 2.10 Q10 · sign 后资源 lifecycle 变化

**背景：** sign 时 resource status=1；之后作者 `offline` 或 freeze，展品仍存在。

**裁决：**

1. **`exhibit online` preflight** 须读 **当前** `Resource.info`（或 batchInfo）：若 `status !== 1` 或 frozen → **code 4**，`reason: resource_not_online` 或 `resource_frozen`。
2. **已 online 展品** 后资源下架：CLI **不** 自动 offline 展品；文档说明访客侧可能异常；维护动作 `exhibit offline` 或 Console。
3. Agent hint 含：`market show` / `exhibit show` 查当前资源状态。
