# 一期 CLI 场景校验集

> **文档角色：** 场景分册不是主设计入口，而是历史用户场景校验材料。当前主线方案见 [../产品方案/README.md](../产品方案/README.md)，交互拓扑补充见 [../02-CLI体验拓扑设计.md](../02-CLI体验拓扑设计.md)。

最后更新：2026-08-31

## 1. 怎么用

主流程先看：

```text
Console 事实总账
  → 01 产品设计总纲
  → 02 CLI 体验拓扑
```

场景分册只做三件事：

1. 验证一个真实用户目标能否完整走完。
2. 暴露异常、误解、恢复、handoff 等边角情况。
3. 把重复出现的问题回归到 02，而不是在每个场景复制。

## 2. 场景模板

每个 Sxx 文档都应保持这个骨架：

| 顺序 | 小节 | 必须回答 |
|:---:|---|---|
| 1 | 用户目标 | 用户手上有什么，想完成什么 |
| 2 | Console 对齐点 / CLI 原生差异 | 对齐哪些字段、API、状态门禁；哪些是 CLI 自己的体验 |
| 3 | 资源类型或对象模型 | 类型从哪里来，是否逐级选择，最终 leaf 怎么确认 |
| 4 | TTY 连续向导 | 一次命令后用户每一步看到什么 |
| 5 | AI/CI 等价命令 | 无 prompt 时如何表达同一业务 |
| 6 | 常见情况处理 | 输错、冲突、网络、权限、handoff、恢复 |
| 7 | 回归到总设计 | 这个场景要求 02 或命令面补什么 |

如果某个场景不需要其中一项，也要写“无特殊差异”，不能缺标题让读者猜。

## 4. 回归规则

读完场景后只做一种判断：

```text
场景能按 02 走通
  → 场景保持简洁

场景需要新全局规则
  → 先改 02
  → 场景只保留差异

场景发现 Console 事实不清
  → 先改 Console 事实总账或列为待实测
  → 不在场景里猜实现
```

场景文档不是越长越好；能让产品、研发、测试在 5 分钟内判断该场景是否闭环，才算合格。
