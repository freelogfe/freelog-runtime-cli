# 单资源 JSON 与快速批次发行设计草案

日期：2026-09-15。状态：待复核，未实现。**优先级高于合集管理实现。**

2026-09-16 用户明确边界：**快速发行是独立的单资源能力，与合集没有必然关系。** 单份/多份发行输入、执行、报告、恢复和验收均不包含合集操作。本稿为独立讨论材料；方案未定稿期间不修改 `脚手架设计/` 内的正式文档。

2026-09-16 复核补充：已明确恢复时使用旧任务的完整意图快照、按阶段校验而非重新创建，并补充JSON修改、外部变更及运行目标的具体语义。

## 1. 本轮方向调整

用户的新要求是：面对一份、多份或几十份本地单资源，让 AI 按标准准备完整信息，再由 CLI 连续发行，减少逐命令交互。

因此增加两项核心能力：

1. **单资源发行 JSON**：完整描述一份资源本次要创建/发布的内容，机器可以校验，AI 不需要为每个属性调用一条命令。
2. **批次执行器**：一次读入多份发行 JSON，统一检查，逐项调用已有单资源领域服务，记录进度并可接续。

快速发行以完成用户指定的单资源发行目标并给出结果报告为结束。用户可以完全不创建或使用合集；若之后需要管理合集，再独立查询线上资源进行添加。

本次是用户明确提出的新设计范围，扩展了此前“暂不做批量独立资源发行”的边界。这里的批次是本地标准数据驱动的连续发行，不要求移植网页端的批量编辑界面，也不引入批量建壳 API 绕过既有单资源业务校验。

## 2. 用户路径

```text
准备文件
  → AI 根据 CLI 的标准和平台类型能力生成发行 JSON
  → 一次校验所有输入，集中修正错误
  → 一个命令执行整个批次
  → 看逐项结果，修复失败项后接续
  → 完成单资源发行任务
```

用户既可以一份 JSON 描述一个资源，也可以把多份资源内联到一份批次文件。二者使用同一份单资源 Schema，不能维护两套字段规则。

建议文件组织：

```text
course/
  videos/01.mp4
  videos/02.mp4
  release/01.resource.json
  release/02.resource.json
  release.plan.json
  .freelog/                 现有身份、工作稿与本次任务恢复数据
```

输入文件由用户/AI维护，CLI不覆盖。它们表达本次执行意图；N.json保存身份，N.version.json保存实际未提交工作稿，平台保存已发版本。JSON 中写了“上架”不能证明平台已经上架。

## 3. 拟议命令：先保持少而清楚

下列命令尚未实现。

| 命令 | 用途 |
|---|---|
| `resource spec --type <code> --output <文件>` | 查询类型能力后生成单资源输入模板，给出随包 JSON Schema 路径；不猜名称、文件或策略ID |
| `resource check <JSON文件> --env dev` | 接受单资源输入或批次输入；本地和只读平台校验，集中输出所有可提前发现的问题 |
| `resource run <JSON文件> --env dev --yes` | 一次运行单资源或整个批次；执行前内置同样的校验，不强制先手工 check |
| `resource run <JSON文件> --resume <runId> --env dev --yes` | 根据该任务的已确认进度继续；结果未知先核验，不自动重发 |

`--cwd`、`--env`、`--yes`、`--json` 沿用公共参数。输入已明确每份资源身份，run拒绝额外 `--resource` 或 `--artifact` 覆盖，避免多份输入被一个全局参数误指向同一目标。

`spec` 应给 AI 一次完整的准备资料：静态 Schema/字段说明、该类型完整路径和动态能力、所需系统附加字段说明，以及策略模板/线上依赖的查询方式。需要用户决定或平台才知道的值保留明确占位提示，check不能把占位符当合法发行意图。

只写一份JSON也能run，后续多资源没有第二套发行入口。现有交互和逐项编辑命令继续作为手工维护方式，底层共享业务服务。

## 4. 单资源 JSON 合同（拟议 v1）

### 4.1 创建视频资源示例

示例模板ID必须通过平台查询替换。视频类型是否允许可选配置由后台决定，因此此例配置为空，不假定所有视频支持配置。

```json
{
  "schemaVersion": 1,
  "kind": "resource-release",
  "operation": "create",
  "resource": {
    "name": "course-video-01",
    "title": "第一课：准备工作",
    "typeCode": "RT006003"
  },
  "artifact": "videos/01.mp4",
  "version": {
    "number": "1.0.0",
    "description": "第一课初次发行",
    "systemInputs": [],
    "attributes": [
      { "key": "author", "name": "作者", "value": "张三", "remark": "" }
    ],
    "options": [],
    "dependencies": []
  },
  "policies": [
    { "key": "public", "name": "公开策略", "templateId": "<查询到的模板ID>", "enabled": true }
  ],
  "listing": { "intro": "课程入门视频", "tags": ["课程"] },
  "stopAfter": "online"
}
```

### 4.2 字段约束

| 字段 | 规则 |
|---|---|
| `schemaVersion` / `kind` | 固定版本与输入种类；未知版本/种类拒绝，不能猜测解析 |
| `operation` | `create` 或 `update`，显式区分；不能依据某个名称已存在就偷偷改成更新 |
| `resource`（create） | name、title、typeCode；name为授权标识短段。采用既有规范化/长度校验，预览最终标识；规范化后批内撞名先报错 |
| `resource`（update） | 精确 `id` 或完整 `name` 二选一；不得带类型改写等创建字段，不按可重复标题查找 |
| `artifact` | 当前工程根下的相对路径；普通资源为文件，主题/插件为已准备好的文件或构建目录。先按既有真实路径/锚点规则核验 |
| `version.number` | create只能1.0.0；update为明确的大于当前latest的新号。批次首版不提供bump，避免重跑时无意生成下一版 |
| `version.baseVersion` | update必填，表示本次明确采用的来源；不隐式跟随变化后的latest。执行计划固定该来源及目标号 |
| `version.description` | 本次版本说明；create默认空，update缺省继承明确来源，空串明确清除 |
| `version.systemInputs` | `{key,value}` 数组，针对系统附加属性；定义/类型/必填以本次文件分析为准。不能填写伪造的SHA、文件大小等计算事实 |
| `version.attributes` | `{key,name,value,remark?}` 数组，映射readonlyText；复用名称/键/长度/条数及重复校验 |
| `version.options` | 文本 `{key,name,mode:"input",defaultValue,remark?}`；下拉 `{key,name,mode:"select",items:[...],remark?}`。下拉默认第一项，禁止另外指定默认值；后台允许才可添加/提交 |
| `version.dependencies` | `{resource:"id:...或name:username/name",versionRange,policyId?}`；range明确且命中已发版本；缺授权时policyId必填。签约成功即可继续，支付留浏览器 |
| `policies` | 拟新增策略列表；每项key为本资源输入内稳定键，name为策略名；templateId与textFile二选一；enabled明确开关。模板参数/事件DSL仍受已知后端契约限制 |
| `listing` | intro、tags、cover；update还支持title。create标题只写resource.title，禁止同时写listing.title。cover为本地封面相对路径，沿用格式/大小限制。update缺省不变，intro空串、tags空数组、cover为null明确清空；title空串/null均拒绝 |
| `stopAfter` | `version` 或 `online`；缺省为version，由本次单资源发行意图决定。不是平台状态缓存，只是本次任务希望走到哪一步 |

普通数组字段在create中省略表示空；update中的版本表单字段省略表示继承baseVersion，显式数组表示完整替换，`[]`表示明确清除。先把来源和输入合成为完整目标表单，再统一校验，不能把“不写”解释成“删光”。

`policies` 是追加意图而不是全量替换：省略或空数组都不删除、停用任何现有策略。策略在任务记录中用输入key关联已创建policyId，不能以可重复策略名判定已完成。更新已有策略仍由显式策略管理操作完成，首版JSON不加入含糊的策略全量覆盖语义。

`stopAfter:version` 表示完成输入声明的版本、listing和策略步骤后停止，不执行上架；为online则继续做上架门禁与读回。create到online但没有可用启用策略的输入应尽早报错。update未声明新增策略时可使用平台已有启用策略，不自动挑选模板或开启全部停用策略。

选择version不会主动下架原来已上架的资源。update成功后的新版本可能立即供线上使用，任务预览必须说明原上架状态；只有显式offline命令才下架。输入中的title/属性/配置等字段，禁止未知字段、重复JSON键及不明确的null语义，不静默忽略拼错字段。

update来源含当前CLI不能无损处理的上抛/排除/未知字段时应报告限制，不能靠JSON通道绕过既有保护。未来扩展以字段对照表和平台契约为依据。

### 4.3 Schema、业务校验与动态分析的分工

- 随CLI交付可机器读取的JSON Schema、完整示例与版本号。AI和编辑器可发现未知字段、类型错误、必填项和互斥字段。
- 字段间重复、跨资源名/路径冲突、semver、类型叶子/配置能力、账号归属、策略与依赖有效性由共享业务校验器处理。
- 文件上传分析后才能知道的必填项不能假装离线已校验。check明确列“需上传后确认”的项；run完成分析后校验完整表单，缺值就停在该资源并输出准确字段位置，不进入逐字段TTY问答。
- 错误返回文件路径、批次key、JSON Pointer（例如 `/version/options/0/items/1`）、错误code、原因和可接受约束。一次列出全部当前可判断错误，减少AI反复调用。
- schema与实际执行共用同一数据模型和校验常量，不能用一份手写Schema加另一份含义不同的代码。当前文档仅定义拟议合同，尚未生成可执行Schema或注册命令。

`spec` 输出模板只表示字段形状，不保证所填内容可直接发行。`check` 报告至少区分本地校验结果、平台只读校验结果和上传后待确认项；平台不可达不能以“本地字段合法”返回整体ready。AI据此一次补充已知错误，再执行run；不会把不能预判的分析字段假装成已通过。

## 5. 多份输入与公共信息

批次示例：

```json
{
  "schemaVersion": 1,
  "kind": "resource-release-batch",
  "resources": [
    { "key": "lesson-01", "specFile": "release/01.resource.json" },
    { "key": "lesson-02", "specFile": "release/02.resource.json" }
  ]
}
```

- 每项 `specFile` 与内联 `spec` 二选一。key只定位本次任务输入，不能作为平台资源身份。重复key或同一线上资源的两次操作拒绝，避免一次任务给同资源连续发两版。
- 批次文件、specFile、artifact、textFile、cover路径全部相对有效工程根（--cwd解析后），不根据JSON所在目录改变解释；禁止越界、循环引用、隐式递归扫描。文件列表顺序固定；可移植地支持带空格中文路径。
- 可提供批次 `defaults`，首版只允许typeCode、policies、listing.tags、stopAfter；逐资源显式值覆盖默认值。数组整体替换，不按名称深合并；明确空数组可取消默认策略追加。解析后打印可导出的有效单资源输入，单文件和批次最终使用同一完整模型。
- defaults.typeCode填入resource.typeCode，其它默认值映射到同名字段。原始批次资源允许缺少可由defaults补齐的字段；规范化后必须通过完整单资源Schema。单份直接run没有批次defaults，缺这些必填项就报错，不能加载隐含的全局发行配置。
- defaults.typeCode只用于create；update的真实类型必须从指定线上资源读取。defaults.policies同样是追加意图，预览逐项展开新增策略，不能将公共默认值理解成“给所有资源重新建一套策略”。defaults变化会影响所有继承它的资源，resume按每项实际生效值逐一判断是否允许修改。
- 不要求AI重复几十遍公共策略和类型信息；没有defaults时也完全可运行。平台ID和动态能力先集中查询一次再生成输入，禁止AI臆造。
- 第一版直接依赖只引用已存在的线上资源；同批尚未发行资源之间的引用依赖后续DAG设计，发现此类输入在写入前报明确不支持，不按数组顺序赌它能成功。
- 单份/批次输入都不定义afterResources、collection、members等合集操作字段。旧草案中的afterResources方案撤销；输入未知字段仍严格拒绝，不保留默认执行的合集钩子。

## 6. 一次运行怎么执行

### 6.1 全批预检

读取并规范化所有spec和defaults，固定输入清单；校验字段、文件锚点、名称冲突、明确版本/来源、账号环境、动态类型、模板和依赖。所有可提前发现错误一次返回；有这些错误时不建壳、不上传、不签约。

预检的资源选择和输入不能在运行中悄悄改变。正式写入仍重查目标身份/owner/冻结、必要版本与输入文件指纹；预检不是放弃提交前门禁。

**首次执行与resume使用不同阶段条件。** 首次create检查名称可创建，首次update检查新号大于latest；resume先读取任务记录，再按每项已完成阶段检查。任务已建壳时核实记录中的同一ID，不能因同名存在而报“创建冲突”；目标版本已成功时核验其完整内容，不能再要求该目标号大于latest，也不能再次执行版本POST。没有可验证任务记录则不得按名称或SHA自行接管现有资源。

resume也按剩余步骤决定是否检查本地产物：仍需上传/提交就检查文件；版本已确认、仅处理策略或上架时使用保存的版本提交事实，不因旧视频文件已经移走而失败。

重复执行原run而未带resume时，如果存在该输入对应的未完成任务，应在写入前返回runId和精确resume命令；若有多个任务则明确列出，不选最近一个猜测。工作区缺少任务记录时沿用首次执行的查重/版本门禁。任务发现可以扫描有效runs记录，不为它再建立长期资源索引。

### 6.2 每份资源按阶段执行

```text
校验 / 对齐已有任务身份
  → create建壳或update绑定明确目标
  → 上传、文件分析
  → 完整表单规范化与校验
  → 明确依赖签约
  → 原子保存一份完整N.version.json
  → 现有单资源版本提交
  → 声明的listing与策略处理
  → 按stopAfter决定是否上架
  → 平台读回、记录该项结果
```

这些是执行阶段，不是要启动多个CLI子进程。共享底层校验和提交服务；不能让AI通过脚本直接写未验证的N.version.json，也不能循环执行几十次attr/option命令。

已有非本任务的本地工作稿必须先报冲突并保留；不能为了自动化而隐式reset。update的完整表单来自明确来源，不从N.json拿版本信息。

执行器应让当前文件只上传/分析所需次数，使用该次准备结果进行本次提交前核验；不得将“减少重复准备”实现为忽略文件变化、复用历史SHA或越过分析状态。现有createVersion内部准备/上传与提交的边界需要按此目标提取。

所有静态校验通过后，个别资源遇到明确业务拒绝或分析缺字段：保留其工作稿和结果，可继续其它独立资源。账号失效、环境异常、工程状态损坏、未知远端写结果必须停止整个批次。当前工程只有一条pending记录，不能一边有未知提交一边继续写别的资源。

### 6.3 运行报告与接续

执行记录保存runId、账号/环境、**规范化后的有效输入快照**、产物指纹/准备后的SHA、已绑定ID、已完成阶段及真实平台回执。每个远端写入前还保存该次请求的非秘密预期业务字段与摘要；外部策略文件、defaults、继承的baseVersion表单必须先展开，不能只留下路径或hash。这样用户改了JSON、策略文件或源版本描述后，仍能核验中断前真正请求的内容。令牌、密码、cookie、视频内容和临时压缩包不进入记录。

它是本次任务恢复依据，可放在被忽略的 `.freelog/runs/<runId>/`，不是另一份长期资源索引或版本历史。永久身份仍在N.json，未完成表单仍在N.version.json；任务数据不能覆盖二者的事实。最终成功后保留可清理的任务报告，已决pending及时清理；不可自动清理仍有未知请求或未完成阶段的恢复依据。

已发布和已上架必须分别记录。例如第7个视频上架失败，重试不能重新创建资源或另发一个新版本，只处理尚未完成的策略/上架阶段。

| 状态 | 接续行为 |
|---|---|
| 尚未发送写入 | 可根据当前输入重新校验并执行 |
| 已建壳、版本未提交 | 精确核实ID、owner、类型，继续既有工作稿；不靠同名重新创建 |
| 版本已确认、listing/策略/上架未完成 | 固定该版本与输入，不重新发行版本；逐项核实并补齐剩余步骤 |
| 整份资源已完成 | 核实阶段完成事实；同一任务不重复建壳、策略或发新号 |
| 某次写入结果未知 | 查询可证明的事实；不自动重发POST、签约或策略追加。无法证明就保留记录并停止 |
| 输入JSON/文件发生变化 | 不把旧进度直接用于新意图；见下方修改规则 |

每个写阶段依次持久化prepared、sending、已确认回执/结果；必须先写sending再调用接口。平台成功而本地记录失败，也按sending待核验处理，不能重新执行。全局pending需要扩展识别runner的阶段并与runs记录关联，让现有手工写命令也能阻断冲突；只写一份runner内部日志、其它命令仍可穿插改同一资源是不够的。

同一阶段远端业务状态已被外部改动时：例如策略后来被停用、资源被下架、目标版本之后又有新版本，resume报告实际状态与任务期望，不自动修复已确认完成的步骤，不重新bump或选择其它策略。用户明确调整任务或执行管理命令后再核验。只读阶段无需重新依赖已提交文件仍在磁盘；完成发行后处理上架，源文件已移走也不应阻断。

输入修改必须按阶段判断：未发送阶段的输入可在resume预览差异后更新；已成功版本的文件/属性/配置/依赖变化需要新任务显式update和新版本号。已执行创建步骤的resource输入整体固定（包括创建时title）；后续改展示标题使用显式listing管理，不回头重执行创建。已准备但未提交的文件或表单修改需要失效相应分析/校验进度并重新准备；已经签约的合约不会因为改JSON回滚。

| 修改发生时 | 允许修改的范围与接续处理 |
|---|---|
| 某项尚无任何远端写 | 可改该项输入并重做预检；修改key仍视为换任务项，不能继承另一项进度 |
| 已建壳、版本尚未发送 | resource创建输入和实际ID固定；可改文件/表单，失效准备与相关校验；已有成功签约保留 |
| 版本已确认、策略尚未添加 | 可修正尚未发送的策略输入，经预览/再校验继续；版本内容固定 |
| 某策略已发送未知 | 即使换templateId也必须先核验旧请求；不能改key来绕过 |

resume中的资源key集合与顺序保持稳定；修正只改允许阶段的字段。新增资源、去掉已成功资源等另开批次，避免删掉一项输入就丢掉失败或未知结果。修改默认值时展示受影响的全部项；其中任何已完成阶段被改变，必须拒绝这次意图更新，不能只修改未完成项却声称同一默认配置已应用。

任务输入已改且存在未知请求时先核验旧意图；不能通过编辑JSON把未知记录变成“尚未执行”。文件删除、任务记录缺失、状态损坏也不按名称猜测成功；需显式绑定/核验现有资源后重新制定输入。

新入口必须同时处理建壳、版本、签约、策略、listing、上架这些阶段的恢复边界。现有版本recover只以版本/SHA判定的保证不够覆盖整个任务；runner对完整发布意图仍应逐字段核对，不能据此认定JSON所有目标已完成。

成功结果输出一个结构化报告；`--json` 时进度去stderr、stdout只含报告，结果包含每个key的阶段/ID/版本/错误/下一步。单资源任务中有部分失败或未知则退出非零；不能以“9个成功”掩盖第10个失败。其它独立任务（例如后续合集操作）的结果不反向改变本次发行任务的成功状态。

## 7. 独立交付与结果使用

快速发行只负责单资源。一份输入可以独立运行，多份输入是同一单资源能力的批次执行；二者都不需要合集ID、合集身份或合集工作稿。

结果报告提供已确认的资源ID、完整标识、版本、环境和查询时的状态，供用户/AI后续使用，不包含“必须加入哪个合集”的指令。这些字段是本次结果，后续使用者仍需按其业务重新查平台。

合集管理只是结果的一种可选用途：用户独立进入合集流程，选取这些或其它线上资源；合集侧重新核验本人、单资源、已上架资格。合集添加失败不改变先前发行成功的事实，合集没有实现也不影响快速发行的开发、发布和验收。

移除发行JSON、移动文件或在下一批省略某项，都不自动删除线上资源。是否使用这些资源以及怎样管理合集，由相应的独立操作决定。

## 8. 为什么会更快

| 当前主要成本 | 设计改进 | 衡量方式 |
|---|---|---|
| 每个资源反复询问、每个字段一条命令 | AI一次生成完整输入；一条run处理全部 | 对30份资源每份10个属性，执行器不产生300次属性CLI调用；一次运行即可装载所有表单 |
| 每次命令启动、读取账号/状态、查询同类元数据 | 单进程复用公共服务，类型/模板只读元数据在本次任务内按env/type等键复用 | 记录进程启动数、类型/模板请求数；写前目标门禁仍保留 |
| 一个错误改一次再继续猜 | 全批静态+只读预检，按文件/JSON路径集中报错 | 同一次check返回所有当前可判断字段错误 |
| 中断后人工查每个资源进度 | 按资源/阶段保留任务记录，明确resume | 已确认阶段的重复建壳/版本POST/策略追加次数为0 |
| 发行完逐个查询执行结果 | 一次输出各项ID、版本、完成阶段与错误报告 | 单资源结果可一次读取，不需要为确认执行结果逐条启动CLI |

首版优先单进程顺序写入，契合现有工程锁和单pending模型；不靠同时启动几十个CLI进程提高速度。只读预检可采用有界并发和批量查询。上传/平台写并发要另行设计per-resource锁和独立未决记录后才开放。

文件传输与平台分析耗时仍存在，必须分别统计。没有对照测试前不承诺“快几倍”；首要验收是减少AI往返、进程启动和重复准备，同时保证完整字段与接续正确。

## 9. 实现影响与优先顺序

证据入口：现有 `domain/create/create.ts` 负责建壳；`domain/version/createVersion.ts` 和 `updateVersion.ts` 编排版本；`domain/version/file.ts` 上传分析；`domain/version/submit.ts` 构建/提交payload；`domain/version/form/` 校验/存稿；`domain/policy/list.ts` 管策略；`domain/listing/update.ts` 改listing；`local/pendingOperation.ts` 为工程级单未决操作。校验数值以 [字段级校验对照表](./业务梳理/字段级校验对照表.md) 为准。

这些服务部分仍将交互、身份选择、单字段落盘与业务校验耦合。应提取“完整表单校验/规范化”和“准备后提交”接口，保证JSON和手工命令走同一校验；不能单纯在外面套shell循环。

优先顺序：

1. 明确单资源输入合同、机器Schema、模板与完整表单校验。
2. 单份JSON完整创建/更新并上架，包含属性、可选配置、依赖、策略和listing；先证明不丢字段。
3. 多份输入/defaults、集中预检、报告、接续和失败分类，测试30份的实际调用开销。
4. 独立完成单资源真网验收、包内Schema与使用文档、性能对照，形成可交付能力。

合集设计与实施另行规划，不作为快速发行的实现步骤或验收条件。当前只更新本独立草案及规划记录，方案定稿前不修改 `脚手架设计/` 正式文档。

不能为了“快”省略update：标准输入同时规定create/update两种明确模式，分别使用原业务流程。现有手工命令回归、包内Schema和使用文档交付必须与新入口一起验收。

## 10. 验收重点

- 1/10/30份输入；同类型共享defaults与混合类型；每份完整属性/可选配置/依赖；不同策略和listing。
- 多文件/单批内联两种表示生成同一有效输入；默认值覆盖、空数组、update继承/显式清空一致。
- 名称规范化后重复、锚点重复/嵌套、未知字段、错误类型、配置不支持、模板ID无效、依赖无匹配版本、未提供策略、来源号冲突一次集中报告。
- 文件分析后出现新增必填项：准确定位该资源字段，留稿，允许其余独立项处理，不伪造全量预检通过。
- 第7项失败、第7项未知、第7项已发版本但上架失败分别验证；连续resume不产生重复资源、版本或策略。
- 改未发送字段、改已建壳身份、改已发布文件、修改时仍有未知请求；应按阶段明确允许/失效重算/拒绝。
- resume时已存在本任务创建的名称、已存在本任务目标版本、default/策略文件变化、JSON删改key、源文件发行后已删除：按阶段恢复，既不重报首次创建冲突，也不跳过真实外部冲突。
- 平台成功而本地确认写入失败；任务记录只有sending；其它手工命令与runner交错：共享pending可阻断，原始展开意图可核验。
- 用户已有手工工作稿时不覆盖；一项未知时遵守工程级pending全局阻断。
- 完全没有合集身份和合集功能时，单份与多份快速发行都能独立完成；输入夹带合集操作字段应在写入前被拒绝。
- Windows/macOS一致读取JSON路径和非交互输出；禁止通过大量子进程绕过锁或暴露凭据。
- dev完整执行含属性/文本及下拉配置/依赖的单资源创建和更新链，以及多个本地视频独立发行上架的批次；配置以类型实际能力为准。平台不支持的分支记BLOCKED，不能算PASS。合集验收另行执行，不混入本能力通过条件。

## 11. 本轮交付边界

本轮仅提出独立单资源能力的可复核设计。JSON Schema、命令和批次执行器均尚未实现，也没有进行新的dev发行。后续继续在独立草案讨论字段合同和恢复行为；用户明确确认定稿及后续修改范围之前，不修改 `脚手架设计/` 内文档，不自动进入实现。
