## 🚨 一、P0 级严重问题（必须立即修复）

### Z-P0-01: Owner 字段展示时机不明确

**问题描述**: 
- A01-A05 等多个场景发现，CLI 启动时未展示资源 owner 信息
- owner 不一致时的处理逻辑模糊
- 只读命令是否豁免 owner 检查未定义

**影响范围**: 所有涉及远端写入的命令

**修订建议**:

#### 在 04-CLI 流程与命令设计中补充：

```markdown
## X. 环境与身份确认规则

### 启动时必须展示的信息
无论什么命令，首次接触远端数据前必须展示：
- 当前登录账号：username (ID: xxx)
- 环境：dev/test/production
- 资源 owner（如已知）：owner_username (ID: yyy)
- owner 是否一致：✓ 一致 / ✗ 不一致

### owner 不一致的处理流程
| 命令类型 | owner 不一致时 | 强制绕过方式 |
|---------|--------------|------------|
| 写操作（publish/update） | ❌ 拒绝执行 | --force-admin（需管理员权限） |
| 只读操作（info/list） | ✓ 允许但显示警告 | 无 |
| 批量发布 | ⚠️ 逐个跳过不匹配的 | --ignore-owner |
```

#### 在 02-Console 业务流程字段接口中补充：

添加"owner 校验列"到字段约束表:

| 字段 | HARD 约束 | DYNAMIC 约束 | owner 校验 |
|-----|----------|-------------|-----------|
| title | ≤100 字符 | - | 仅写操作校验 |
| name | ≤60 字符，唯一 | - | 写操作强制校验 |
| version | semver 规范 | >latestVersion | 写操作校验 |

### Z-P0-02: Checkpoint 数据结构缺失定义

**问题描述**:
- A02, C05, F06 等场景验证了 checkpoint 的必要性
- 产品方案 06 只有伪代码，没有定义具体的数据结构
- accountId 校验机制缺失

**影响范围**: 会话恢复、断点续传、批量 resume

**修订建议**:

#### 在 06-实现解决方案中补充：

```typescript
/**
 * Checkpoint 数据结构定义
 */
interface Checkpoint {
  version: "1.0";                    // Checkpoint 格式版本
  runId: string;                     // 唯一运行 ID
  accountId: string;                 // 账号 ID（用于校验）
  environment: string;               // 环境标识
  
  completedSteps: string[];          // 已完成步骤列表
  pendingFields: Record<string, any>; // 待完成字段
  
  partialResources?: {              // 部分创建的资源
    resourceId?: string;
    version?: string;
    fileSha1?: string;
  };
  
  metadata: {
    timestamp: string;               // ISO 8601 时间戳
    cwd: string;                     // 工作目录
    command: string;                 // 原始命令
    cliVersion: string;             // CLI 版本
  };
  
  status: "active" | "abandoned" | "completed";
}

/**
 * Checkpoint 生命周期规则
 */
const CHECKPOINT_RULES = {
  // 何时创建
  onCreate: ["command_interrupt", "network_error", "user_save"],
  
  // 何时加载
  onLoad: ["command_start", "--resume flag"],
  
  // 何时删除
  onDelete: ["success", "user_cancel", "account_mismatch"],
  
  // accountId 校验
  accountIdCheck: {
    match: "resume_allowed",
    mismatch: "show_warning_and_offer_options",
    force_resume: "requires_explicit_confirmation"
  }
};
```

### Z-P0-03: 依赖版本范围命中检测不够提前

**问题描述**:
- C02-1, D05-1 等场景发现应该在上传前就提示授权缺口
- 产品方案 04 的流程图中依赖检查的位置不够靠前

**影响范围**: 主题/插件发布的依赖配置

**修订建议**:

#### 在 04-CLI 流程与命令设计中补充单资源发布流程:

```
原流程:
资源壳创建 → 版本上传 → 策略配置 → Listing 设置

修订后流程:
资源壳创建 → 依赖预检 → 版本上传 → 策略配置 → Listing 设置

依赖预检阶段新增内容:
  1. 扫描本地依赖声明
  2. 调用平台 API 查询可用版本
  3. 验证版本范围是否命中
  4. 输出详细报告:
     ✓ res_plugin_a ^2.0.0 - 已命中 (最新: 2.3.1)
     ✗ res_plugin_b ^3.0.0 - 未命中 (最新: 2.5.0)
       选项：降级范围/排除依赖/升级插件
```

```markdown
## SXX - 批量发布中的冻结状态处理

**前置条件**: 待批量发布的资源中有若干处于冻结状态

1. 扫描阶段识别冻结资源

```
