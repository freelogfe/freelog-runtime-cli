## 1. 结论与评审方法

当前核心模型合理，可以继续使用：一个工程中的多个视频、图片、主题或插件分别对应多份 `N.json`；每个资源只保留一个当前 `N.version.json`；平台保存已发布版本历史；主题/插件只在目录上传时多一个压缩步骤。

**当前产品还不足以判定健壮。** 主要问题集中在规则之间的衔接：新增和接续如何区分、选中身份后如何保持目标不变、换文件如何避免破坏其他资源、坏状态如何恢复、远端已成功但本地未完成如何判断。部分场景写了“能走通”，却依赖尚未实现的交互或恢复入口。

本轮按五层核对：

1. 用户起点：已有素材、已有源码、已有线上壳、已有版本、换机器、自动化调用。
2. 产品不变量：工程边界、身份唯一性、版本事实归属、产物归属、环境和账号。
3. 命令组合：建立身份 → 选择 → 备稿 → 编辑 → 发布 → 管理 → 恢复。
4. 失败切点：选择后、上传后、分析后、远端写入后、本地事务中断后。
5. 证据：架构/PHASE/真实场景/场景实现/使用手册互相核对，再追踪源码和隔离复现。

证据等级：**复现**表示本轮用真实本地实现和隔离夹具观察到；**静态确认**表示完整调用路径或文字存在明确问题；**待验证**表示平台事实或跨进程行为尚无充分证据。平台与账号依赖在本轮复现中用模拟接口替换，未读取真实凭据，未发送网络请求。

“134 项测试通过”是上一轮自动化结果，不是本轮重新执行的结果，也不等于以下风险已关闭。本轮未重复运行与评审无关的全量测试。

## 2. 应保留的产品边界

| 事项 | 保留的规则 |
|---|---|
| 同目录多资源 | 同一素材目录内的 `video.mp4`、`cover.jpg` 可以分别建壳、发版、管理，不要求拆目录。 |
| 操作范围 | 常规资源命令一次处理一个资源；`resource sync` 是已存在的批量标题同步例外。 |
| 两层状态 | `N.json` 保存资源身份、标题与可变默认产物；`N.version.json` 保存唯一当前工作稿。 |
| 版本历史 | 不复制历史大文件、不建立多版本本地档案、不引入“历史版本绑定本地文件”系统。 |
| 成功发布 | 确认平台发布成功后清除当前工作稿；后续可从 latest 或指定已发版本拉新稿。 |
| 文件变化 | `a.mp4 → b.mp4` 更新本资源默认路径与当前工作稿；线上旧版本不变。 |
| 主题/插件 | 模板只负责初始化；目录发版时临时压缩；显式文件、包括 zip，直接上传。 |
| 公共选择 | 保留 `id:`、`name:`、`title:`、`artifact:`、`file:N.json`，保留无参数时零/一/多状态规则。 |
| 用户恢复 | 用户可以备份、删除选定资源的本地状态后重新 bind；无需建立复杂自动迁移系统。 |

## 4. 按风险和产品影响分析

### R01：工程路径必须唯一解释，不能选对资源却上传错文件

优先级：P0，复现 E01。

现实起点：用户从素材目录的上级运行 `--cwd media-a`，上级也有同名视频；或者 AI 从另一个工作目录调用 CLI。资源状态从正确工程读入，但 `resolveExistingPath` 先检查进程当前目录中的相对路径；这一优先级能让 SHA 和上传内容来自另一个文件。

建议：所有资源产物只按 `path.resolve(projectRoot, relativePath)` 解释。检查、SHA、上传、记录回写必须使用同一个已解析对象。文件选择参数和 `--cwd` 的出现位置不得改变结果。封面和策略文件也要在各自命令文档中明确路径基准，不能靠底层偶然行为决定。

补充边界：软链接真实目标、跨平台分隔符和大小写需要明确规则；`.freelog/` 及其子文件不得作为发行产物；目录内仅有空目录不能视为有构建结果。现有路径检查主要是字符串检查，尚不能当作这些边界已验收。

### R02：唯一性必须在写入之前保证

优先级：P0，复现 E02，发版回写同样静态确认缺少全工程候选校验。

当前“读取时拒绝重复”不能防止合法命令制造重复。`setPath` 直接生成新身份并提交，`file.ts` 的发版回写也直接写路径；下次命令才发现冲突。用户只是换了一个文件，就可能让整个素材目录不能继续操作。

建议：任何将修改身份的入口都先构造“变更后的完整身份集合”，验证资源键、标识符和规范产物路径，再执行写入。`create` 还应在远端建壳前检查本地名称冲突。发版换路径应在上传前拒绝占用，避免花费上传时间后才失败。并发情况下，在持锁状态中重复校验最终目标。

验收必须断言：拒绝后所有其他资源状态字节不变、选中稿不变、平台写调用为零；不能只检查出现了报错。

### R03：新增另一文件与接续旧立项仍有歧义

优先级：P1，复现 E03。

唯一未绑定状态自动接续，是为 `init a → create` 的便利而设；但在多素材目录里，用户可能先立项 A，又临时创建 B。现有路由无论 `--artifact` 是否变化，都把唯一未绑定状态当目标。多份未绑定时则阻止创建 C，用户缺少“保留现有未绑定状态、另建一份”的清晰路径。

建议将 `create/bind` 的新增意图单独写入规则，详见 §5.2。显式 `--resource` 才表达“接续这份且允许换锚点”。未带选择器但给了新产物时，在未绑定集合中按同一规范路径查找；未命中则新增。这里的 `--artifact` 表示新建/接入的产物归属，不扩展为 `status/version/online` 的资源选择参数。

这是一项需要同步修改原规则的产品建议，并非把 E03 仅当实现打错字修复。

### R04：环境、完整标识与 owner 没有形成统一资源上下文

优先级：P0，复现 E04/E05，其他门禁静态确认。

当前凭据环境与命令环境对齐，并不代表选中 `N.json.env` 也对齐。`resource sync` 单独检查身份环境，版本、展示信息和上下架没有复用同等检查。owner/冻结检查也不一致：bind、部分 policy 有校验；listing/offline 等可直接发出写请求。

`name:username/name` 只比较最后一段，实际上没有验证用户输入的完整标识。短标识在一个账号的命名空间内唯一，不能与完整资源标识视为同一个全球唯一键。

建议：统一解析 `ResourceContext`，至少包含工程根、N、resourceId、identityEnv、typeCode、filePath、显示标题；远端动作先确认身份环境，再读取详情核对 ID/owner/冻结/主体类型。完整 `resourceName` 应由 create/bind 从可信账号或远端详情保存，旧状态通过同步补齐；补齐前不能忽略错误的用户名前缀。

同工程如保留不同环境的状态，ID/完整标识的冲突键要包含 env；单个产物能否关联多环境仍按现行“路径独占”处理，不自动放开。无需据此增加多账号会话功能。

### R05：恢复顺序与正常校验互相阻断

优先级：P0，复现 E08，相关并发问题静态确认。

ARCHITECTURE 08 要求先持锁、恢复事务、再全量校验；根 `preAction` 却在未显式选择时先校验全部状态。一个合法的中断事务可能暂时表现为身份和工作稿不一致，因而永远进不到预期恢复入口。显式选择器可能绕过根预检，使同一个残留事务因参数不同出现不同结果。

另外，`bind` 在拿项目锁前查询远端；listing 在远端写入成功后才调用持锁的 `updateIdentity`。若这时 N 被另一命令换绑，回写标题可能落到另一份身份。零状态时直接进入某些持锁领域方法又可能创建空 `.freelog/`，与“零状态只提示、不建状态”冲突。

建议：短临界区先恢复并得到可信快照，再选择；长交互结束后重新取锁并核对选中身份没有变化。真正写入期间保持锁；只读查询使用完整快照。已有工程的暂态恢复属于维护动作，应明确区别于“只读命令不改用户工作稿”的承诺。无状态工程无需先创建锁目录。

事务日志还需补硬边界：当前恢复使用日志中的绝对路径，未像新建事务那样复验目标属于当前 `.freelog`，也未先检查全部条目再逐项应用。复制工程或移动目录带来残留日志时，不应访问旧工程路径；所有目标和 before/after 应在任何回放写入前统一验证。此项为静态确认，未对真实工程执行日志回放试验。

### R06：reset 预检只查存在性，不足以承诺“错误输入不丢稿”

优先级：P0，复现 E06。

普通资源给一个已有目录、主题给空构建目录等，均可能通过 `confirmLocalPath` 的存在性检查，之后才在上传准备阶段被拒绝；旧稿已被删除。更新版 `--reset --reuse-version <不存在版本>` 也在删稿后才经 `draftPull` 检查来源版本。

建议：确认丢稿前完成路径范围、文件/目录形态、目录非空、排除工程状态文件、路径占用、类型能力、版本来源和新号的全部可确定校验。进入 reset 的成功确认只授权放弃旧稿，不应替代这些校验。

保留已确认的简化边界：通过预检并确认后，后续网络失败可保留新稿或空状态，旧稿无需恢复，但错误要明确说明已放弃旧稿。不要用这一边界解释本来可提前发现的输入错误。

### R07：失效系统附加属性有阻断状态，却没有闭合处理流程

优先级：P1，静态确认。

`file.ts` 将消失的属性放进 `orphanedInputAttrs`，`submit.ts` 拒绝非空列表；但是命令树没有对应复核入口，`attr rm` 仅删自定义属性，`attr set` 不清除待处理项。源码还只按 key 是否存在保留旧值，没有实现设计承诺的格式兼容判断。

此外，更新稿只能 `draft pull` 拉取旧版本后编辑，或直接进入 `update-version --yes` 上传并提交；缺少对新文件“先分析、处理属性，再提交”的独立路径。遇到新文件要求的新附加字段，用户容易陷入“提交失败后才能改稿”的流程。

建议：补 `version draft prepare --artifact <新路径>`，为已有更新稿上传/分析新文件，输出兼容值与待处理值，不提交版本。未有更新稿时明确要求先 pull；首版仍使用已有 `create-version --prepare`。复核优先扩展现有 `version attr` 的显示/修改/删除能力，通过明确的待处理项范围逐项解决，不另建一套表单或大型会话。只清除明确处理的项，保留其他自定义、依赖、描述；`--yes` 不代表同意自动丢弃所有旧值。不恢复已经禁止的 `update-version --prepare`。

同一组还需修正工作稿生命周期：`attrAdd`、`optionAdd`、`depAdd` 在无稿时会从空对象起步，可能给已有线上版本的资源生成 initial 稿，与“先 pull 再编辑”不符。对于用户/AI 手工修改的稿，当前数组元素主要以宽泛对象校验，`submitVersion` 没有统一重做完整字段约束与类型能力校验；逐条命令写入时校验不等于手工稿提交时已校验。建议建立共用业务校验入口，在落盘和提交前分别校验当阶段必需的约束，补齐直接手改超过条数/长度、非法可选配置和失效附加值的测试。

### R08：远端“失败”缺少“结果未知”这一类

优先级：P1，设计缺口，网络结果待真实故障注入验证。

当前“POST 成功删稿、失败留稿”覆盖不了：服务端已接收并完成发布，但响应超时；或已收到成功响应，本地删稿失败。下一次执行 `--bump patch` 可能把同一内容又发一个更高版本，或者因旧稿来源不匹配让用户无从判断。

建议把结果分成“确认成功 / 确认失败 / 尚无法确认”。结果未知时按本次 resourceId、环境、目标版本查询平台；核对文件 SHA、提交字段后再判定。无法确认则保留当前工作，提示准确的查询/重试路径，不能自动增加版本号或自动重发。建壳、添加策略、依赖签约也要各自说明恢复依据。

本期最低要求是精确错误与人工查询恢复；如果要求跨进程自动核验，建议额外保留**仅一条未完成提交的瞬态标记**，记录环境、resourceId、目标版本和请求摘要，确认后清除。它不是版本历史或永久回执；是否采用需评估新增状态成本，不能声称单靠现有 `.txn.json` 已能解决远端请求原子性。

### R09：同一状态文件名不是永久资源标识

优先级：P1，复现 E07。

现有编号取当前 `max+1`。删除最高编号，或者删除整个 `.freelog` 后重建，会重用编号。与“用户随时删除后 bind”组合后，旧 AI 脚本中的 `file:2.json` 可以指向新资源。

建议保留 `file:N.json`，但把它定义为**当前工作区当前状态的精确地址**。删除/重建后，脚本应重新枚举并核对资源 ID；长期自动化优先 ID。为保持简单，建议撤销无依据的“永不复用”承诺。若一定要求工作区存续期间编号单调递增，则必须增加持久化高水位，且仍不能承诺删除整个状态目录后稳定。

### R10：交互产品规格与已实现命令不是同一套体验

优先级：P1，静态确认。

创建/更新 PHASE 承诺首版/更新版会话菜单、TTY 询问版本号、确认默认文件；场景实现 02 又明确“没有自动表单会话”。代码在未带 `--yes` 时拒绝真实提交，并未提供 PHASE 的整套菜单。用户复制某些 PHASE 示例，会在预期进入问答时直接失败。

建议一期优先统一成：分步备稿和编辑为完整主流程，TTY 提供资源选择、缺少必需参数的询问、写入前摘要和确认。大型循环会话菜单如不做，就从规格中明确移除并同步所有场景，不能让文档承诺它已经存在。上下架/listing 的确认行为也要统一；目前 online/offline 没有把 `--yes` 传进领域层以控制确认。

### R11：资源管理存在普通用户直接会遇到的细节断点

优先级：P1，复现 E09，其他为静态确认。

`--cover` 在帮助中是路径，规格要求验证图片后上传，代码却直接当 URL 放入请求。`--tags ""`、`--intro ""` 的空值与“未提供”也被 truthy 判断合并；设计承诺的清空标签无法表达。空调用、空值、取消和无变更必须分别设计。

`version show` 对无线上版本或缺少 resourceId 返回普通字符串，可能成功退出；对指定不存在版本也没有像 `draft pull` 一样检验有效版本内容。自动化因此可能误把失败当成成功。默认展示、版本不存在的判定和退出码应共用规则。

### R12：多文件和视频场景的规模边界不足

优先级：P1/P2，静态确认，实际容量待压测。

当前 SHA 和上传均用 `readFileSync` 整文件读入内存，尚未看到发版链路落实 `fileMaxSize` 与本地上传能力校验。实际视频可能很大；两次读取之间文件还可能被构建/编辑进程改写，使计算 SHA 与提交内容不一致。主题目录压缩同样需要定义构建过程中变化的结果。

建议：文件大小/类型限制在上传前检查；采用流式哈希与平台允许的流式上传，或明示当前限制；对本次输入验证文件身份/大小/修改时间并在变化时拒绝。无法保证一致性时使用本次操作的临时稳定副本，结束清除，不形成历史归档。目录压缩可继续使用临时包，线上 filename 建议使用可读、稳定的逻辑名，不暴露 pid/时间戳作为默认产品文件名。

`resource sync` 当前对全部目标直接 `Promise.all`，上百份素材需要受控并发、超时和逐项失败摘要。资源列表和 TTY 选择需要搜索/分页，不能只以两三份测试推定大目录可用。

### R13：恢复指导和人工/机器可见性尚不完整

优先级：P1，静态确认与设计缺口。

“所有单资源命令先校验全部工作稿”让坏稿阻断 `draft discard/pull`，但多份文档又建议用这两个命令恢复坏稿，形成恢复死路。整目录停止写入可以作为保守策略，但用户必须能看到哪一组损坏、影响什么、怎样保留其余资源后恢复。

建议增加一个本地清单入口（候选 `resource list`），展示编号、ID、完整标识、标题、默认产物、文件是否存在、工作稿状态、环境和错误。零份输出空列表成功；坏记录逐项标注，正常记录仍可看；该能力与“常规写命令全量预检失败就停止”不冲突。

一期恢复可继续使用手工备份、删除指定完整状态单元、重新 bind；但实际错误必须点明文件和命令。若提供 CLI 丢弃损坏稿，只能以明确目标及确认处理，不依赖先成功解析坏稿；遇到未知事务先停止，不能删除其依赖文件后回放。

`--json` 目前使用手册承诺的是错误 JSON，而 ARCHITECTURE 08 又承诺 sync 每份结果 JSON。建议统一正常/失败输出结构，JSON 模式 stdout 只放结构化数据，进度和说明去 stderr；涉及损坏身份不得输出凭据。选择失败候选要能正确引用带空格的标题/路径，标题歧义和零匹配也应列候选，不能只在未提供选择器时列。

### R14：多份文档仍保留相互冲突的规则

优先级：P1，静态确认。

| 冲突 | 当前证据 | 应统一到的方向 |
|---|---|---|
| 产物是否必填 | 使用 03 仍写普通资源初始路径“可无”；ARCHITECTURE 08 规定必填 | 保留必填产物锚点的已确认设计。 |
| 改目录时是否须存在 | 使用 03、ARCHITECTURE 06 写 `version set` 目录可以不存在；实现与后续规则要求存在 | 明确创建/修改锚点须存在；以后丢失不等同于身份损坏。 |
| 发版是否写 N.json | 创建/更新 PHASE 开头说“不写 N.json”，后文又要求回写 filePath | 只可回写当前默认路径，准确写明成功阶段。 |
| 路径何时回写 | “确认后”“上传成功后”“发布成功后”与实现“分析成功后”并存 | 采用 §5.3 的原子准备完成边界。 |
| 授权完成度 | 提交章节写“有依赖未授权就拦”；同页末尾写授权完成度不是客户端提交门禁 | 保留已确认的不处理支付、不按授权完成度阻断；其他真实平台前置另行表述。 |
| 策略范围 | 真实 S53/管理总览写只加免费策略；策略正文允许全部适用模板 | 同步到当前全部适用模板、操作本身不支付的规则。 |
| 显式歧义 | 08 主规则说显式标题歧义不再菜单；同步小节又说可交互选择 | 已给歧义选择器时报候选失败，只有未给才菜单。 |
| 起点有无文件 | 真实 S45、旅程表仍称空工程普通资源；快速教程同时说要已有文件和拒绝其他工程内容 | 普通资源起点应是已有文件；不覆盖边界区分通用接入与模板初始化。 |

这些矛盾不能仅靠“08 优先级最高”长期解决；子文档会被用户、开发者和 AI 单独阅读。

## 5. 推荐的简洁完整设计

以下为待落实建议，以保留 §2 的核心模型为约束。新增能力只用于闭合真实流程。

### 5.1 所有命令围绕同一份已解析资源上下文

建议顺序：参数语法校验 → 确定工程根 → 恢复可信事务 → 读取/校验状态 → 选择资源 → 检查环境/账号 → 检查操作前置 → 展示影响 → 确认 → 执行 → 写回 → 输出结果。

本地只读或编辑不需为了选择资源强制登录；远端动作在网络调用前检查身份环境。只有需要真实产物的动作检查文件是否存在。跨交互或耗时等待重新取得锁后，要验证选中的 N 与 resourceId/环境仍对应，不能只记一个编号重新盲读。

| 资源选择情况 | 建议行为 |
|---|---|
| 零状态，普通单资源命令 | 明确 create/bind 指引，非零退出，不创建资源状态。 |
| 唯一状态，无选择器 | 自动选择；后续业务前置照常校验。 |
| 多状态，TTY 无选择器 | 清单选择或退出；支持搜索，显示产物和资源字段。 |
| 多状态，非 TTY/--yes 无选择器 | 非零退出，结构化/可复制候选，不默认第一份。 |
| 显式选择器零条或多条 | 给出原因与候选；不猜、不回退其他匹配形式。 |
| 标题旧了 | 可用 ID/标识/产物选择，按需 sync；错误不能暗中按近似标题操作。 |
| `file:N.json` | 精确定位当前状态；删除或重建后需要重新核对 ID。 |

### 5.2 create/bind 的新增与接续

| 输入/状态 | 建议结果 |
|---|---|
| 显式 `--resource` | 只接续或换绑指定状态；create 拒绝已绑定，bind 换绑定遵守 force/yes。 |
| bind 的远端 ID 已在本地对应环境存在 | 幂等使用对应状态；显式选择另一份则拒绝冲突。 |
| 未显式选状态，给出的 `--artifact` 恰好匹配未绑定状态 | 接续该份；类型不一致不得默默重写，要求明确意图。 |
| 未显式选状态，给出的 `--artifact` 是未占用的新路径 | 新增身份，即使还有其他未绑定状态也不抢占。 |
| 未给 `--artifact`，只有一份未绑定 | 沿用该份路径和类型，完成 init → create 的便捷链路。 |
| 未给 `--artifact`，没有或多份未绑定 | 交互询问目标或明确提示缺参数；非交互停止，提供新增与接续两条指引。 |
| 新路径已被已绑定资源占用 | create 拒绝；bind 只有同一资源幂等情况允许，否则要求显式选择并确认换绑。 |

普通多素材主路径建议直接 create/bind；通用 init 保留为首份本地接入的可选步骤。已存在项目的模板初始化仍不覆盖源码。

### 5.3 默认路径与工作稿的写入时机

推荐统一采用“**准备成功后，默认路径与新分析稿一起写入**”的规则。它与当前实现的大方向接近，但必须补齐占用预检和用户可见结果。

| 动作阶段 | N.json.filePath | 当前工作稿 |
|---|---|---|
| `version set --artifact b` 成功 | 改为 b | 保留；查看时说明当前稿文件与下次产物可能不同。 |
| 发版显式选择 b，但路径/占用/类型校验失败 | 不变 | 不变。 |
| 上传或分析失败 | 不变 | 原稿保留；reset 已确认放弃旧稿时单独说明。 |
| 新文件分析及兼容处理结果准备成功 | 与新分析稿同事务改为 b | SHA/文件名来自 b，保留兼容表单，失效项显式待处理。 |
| 后续提交失败 | 保留 b | 保留当前稿；重试不能无声回到 a。 |
| 平台确认提交成功 | 保留 b | 清稿。 |
| 平台结果未知 | 保留当前状态并说明 | 保留，先核验目标版本，不自动再 bump。 |

`artifact:a.mp4` 是随路径变化的选择器；成功准备 b 后应提示以后使用 `artifact:b.mp4` 或稳定 ID。不得再次解析旧的可变标题/路径来决定同一条正在执行的命令的目标。

### 5.4 缺文件、坏状态、可恢复中断分开处理

| 情况 | 建议处理 |
|---|---|
| N.json 合法，只是原文件被删/移动 | 身份仍有效；允许 status、线上管理、查看/拉稿、set 新路径；实际发版要求现存产物。 |
| 工作稿合法但属性待复核 | 能显示、编辑、逐项解决；仅提交被阻断。 |
| 某组状态损坏 | 清单/诊断能显示错误；保守停止业务写入；允许按明确文件范围备份后恢复。 |
| 可证明安全的残留事务 | 先恢复完整状态，再做普通业务校验。 |
| 事务目标越界或与磁盘冲突 | 任何回放写入前停止，指出冲突；不能借重新 bind 掩盖。 |
| 本地可重建状态全部放弃 | 提示未提交改动会丢失；不涉及删除真实素材或线上版本；重新 bind 后编号不视为稳定。 |

### 5.5 交互、自动化和资源管理

一期以可组合的独立命令为主，不依赖大型隐式会话。所有真实写入在 TTY 下展示“当前环境、资源标识/ID、产物或目标版本、将改变的内容”；提供参数但未加 `--yes` 不应被各命令任意解释成直接写或无条件失败。

自动化明确环境和资源；非交互缺少必要参数就失败，不用确认默认值猜测。`--json` 建议统一成功/失败输出，至少给操作目标、结果状态、错误码、恢复动作和批量逐项结果；不要仅依赖中文错误字符串。完整资源清单是 AI 获取 `file:N.json` 的入口。

展示信息遵守三值语义：参数未提供=不改；提供有效值=替换；提供空值=按字段契约清空或报错。标题不能清空；标签可以清空；封面清空仍按已确认的平台能力决定。封面路径走图片校验/上传，再用平台 URL 更新 listing。

### 5.6 本地事务和远端动作的分界

本地锁保证同一工程的状态更新不交错；它不能阻止另一机器在平台发版，也不能使平台 POST 与本地删稿成为一个原子事务。提交前重新读取 latest/权限是必要检查，但请求超时仍要有结果核验。

日志建议使用当前 `.freelog` 内的相对目标或在恢复时严格绑定当前工程；限定可写文件类别、拒绝重复条目和符号链接逃逸、整体预检后回放。复制/移动工程时恢复不应触及原目录。

状态 schema 的任何新增字段应明示兼容策略。完整资源标识可以由远端同步补齐；本期不要求自动把任意损坏旧稿迁移成新稿。未来瞬态提交标记仅用于确认未决操作，确认后清除。

### 5.7 控制复杂度的推荐取舍

| 设计问题 | 本轮推荐方案 |
|---|---|
| 是否保存多版本历史 | 不新增。本地仍是一份身份和一份当前稿。 |
| 为发现资源增加多少命令 | 增加一个本地 `resource list`；常规 status 仍面向单份资源。 |
| 为更新文件补什么能力 | 增加一个 `version draft prepare`，复用已有文件链路；旧值复核扩展现有 attr 命令，不另造编辑系统。 |
| 是否实现 PHASE 中的大型会话 | 一期推荐收敛为独立命令加必要问答/确认，明确撤掉未实现菜单的承诺。 |
| 是否永不复用 N | 推荐明确其工作区内当前地址语义，删除/重建后重新发现；不为编号单独增加永久登记系统。 |
| 是否增加远端操作回执 | 一期先保证结果未知时准确提示和指定版本核验；不强制新增永久回执或历史文件。跨重启自动恢复是后续增强，采用单条瞬态标记前单独评估。 |
| 是否自动修复所有损坏状态 | 不做猜测式修复；提供可读清单、精确备份/移除范围和 bind 重建路径。 |
| 是否新增资源身份字段 | 仅建议补可信完整资源标识供精确匹配；env/ID/owner 在操作时统一核验，旧状态有明确补齐路径。 |

上述命令与规则均是本次评审推荐方案，尚未注册或修改实现。选择这些取舍的目的是让常见操作有完整出口，同时把新增状态和新概念控制在必要范围内。

## 6. 必须补齐的现实场景与验收

沿用现有 S1–S68；以下使用 R 场景名，正式落地时再分配编号，避免凭编号数量伪造覆盖。

| 场景 | 必须观察到的结果 | 验证层 |
|---|---|---|
| 两个工程有同名视频，从第三个目录用 --cwd 发版 | 上传字节及 SHA 来自指定工程 | 本地文件链路 + CLI |
| 同工程 A/B/C 连续 create、bind、发首版、新版、管理 | 每步只影响目标状态和远端资源 | CLI + dev，文件内容不同 |
| A 未绑定，用户新建另一个文件 B；多份未绑定再新增 C | A/B 保留，C 新增；接续规则可解释 | CLI + 领域 |
| 普通/主题/插件分别换到另一资源占用路径 | 上传/写盘前拒绝，所有状态不变 | 领域 + CLI |
| 路径改 b 后提交失败，再次重试 | 使用 b；旧 artifact 选择器失效有指引 | 文件链路 + 提交模拟 |
| 原文件不存在，用户只查看或下架；随后 set 新文件 | 管理可继续，发版缺文件才拦 | CLI + dev |
| 标题重复、标题含空格、标题在网页改名 | 不误选，候选可复制，sync 可恢复展示 | CLI + dev |
| name 带错用户名、跨 env ID、旧状态缺完整标识 | 正确拒绝/指引，不忽略前缀或环境 | CLI + 模拟 API |
| 删除最高编号、删除全部状态、重建后旧 AI 脚本重跑 | 不宣称编号永久稳定；脚本重新核对目标 | 本地 + CLI |
| 普通资源 reset 指向目录；主题 reset 指向空目录 | 旧稿保留，提前报错 | 文件链路 + CLI |
| reset 选择不存在的源版本 | 确认丢稿前拒绝，旧稿保留 | 模拟 API + dev |
| 换文件后附加字段消失、同 key 格式改变 | 待处理项可查看、修正/丢弃，处理后能成功提交 | 表单 + 文件链路 |
| 已发资源无稿直接 attr/option/dep add；AI 手工写非法条目 | 无稿提示先拉；已有稿的提交重验字段，不依赖曾经走过编辑命令 | CLI + 模拟 API |
| 线上版本不存在、无版本、无 resourceId | 准确提示和非零退出；不报假成功 | CLI + dev |
| 远端发布成功但客户端超时；远端成功后本地清稿失败 | 能核验确切目标版本；不自动发下一个号 | 故障注入 + dev |
| 建壳请求结果未知、策略追加结果未知 | 有具体查询恢复路线，不盲目重复写入 | 故障注入 + dev |
| 换绑事务已写身份未删旧稿，带/不带选择器重启 | 两种命令入口均先正确恢复 | 本地事务 + CLI |
| 标题 PUT 与同编号换绑并发 | 不把旧资源标题写入新绑定身份 | 并发模拟 + CLI |
| 工程移动/复制后带残留事务；日志指向工程外 | 不回放到旧工程或任意文件 | 本地事务 |
| 一个坏稿与两份正常资源并存 | 可列出诊断和恢复方案；不误删其他资源 | CLI |
| 封面缺失/超大/动画 GIF；空简介/标签；无变更 | 校验、清空、不改三者明确；请求载荷正确 | CLI + 图片校验 + dev |
| 数百素材、GB 级视频、上传中内容变化 | 有界内存/并发、超时、正确内容或明确拒绝 | 压测 + 文件故障注入 |
| 主题目录/插件目录/显式 zip 的首版和更新 | 目录只压一次、文件不压，临时包失败也清理 | 本地 + dev |
| 每类命令在 TTY/非 TTY/--json 及 --resource 不同位置 | 目标一致，确认和输出协议一致 | CLI 命令树真实执行 |

测试应通过真实 CLI 入口验证共享选项传递和目标 API 参数，不只检查“帮助里存在 --resource”。每个高风险用例同时断言目标状态变化、其他状态不变、请求次数/参数和失败后的恢复路线。

## 7. 实施影响与建议顺序

本节是本次建议的影响分析，落实各项前仍需按实际选定方案复核。

## 8. 外部验收记录的使用边界

本轮已读取移至 `test/` 的 [0.5.3 验收记录](../../../test/CLI2-0.5.3-验收问题记录.md)，将其作为待核验线索。

- “第二份资源首版失败，疑似误走建壳接口”：当前源码 `submitVersion` 调用的是 `Resource.createVersion`，不能仅凭平台报错文案认定误走建壳。需记录已安装包的确切版本/构建、请求方法/URL/资源 ID/内容 SHA；以不同内容的两份文件及同内容对照排除平台去重或资源类型限制。**本轮未真网复核，既不宣布成立，也不宣布已修复。**
- “status --json 非 JSON”：现有使用手册只承诺错误 JSON，属于产品协议不完整与文档不一致，不能仅凭其他 CLI 的惯例定性为既有契约违约。本文建议完善为统一协议。
- “多资源先要求选择而不是登录”：对只读本地选择和零状态诊断可合理先选择；关键是任何远端动作前完成环境/凭据/身份校验。无需仅为改报错次序推翻公共选择规则。
- 类型搜索为空、策略模板为空、平台属性映射等仍需要同版本真网证据；不能把缺数据、接口映射和产品不支持混为一谈。

旧测试通过、已发布版本号、同名验收文档都不能替代本轮具体证据。交接时须分别写清“规格已确认、实现已完成、本地已验证、真网已验证、发布包已验证”。
