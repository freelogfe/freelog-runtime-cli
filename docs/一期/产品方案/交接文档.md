### 2026-09-09 本地状态必须有产物锚点

**影响分析与结论：**用户确认“只含类型而不关联本地产物”的 `N.json` 没有产品意义，故 `filePath` 升级为每份资源状态的必填身份字段。受影响命令是 `init`、`create`、`bind`、`version set` 以及所有读取/重建 `index.json` 的路径；未绑定状态、创建时直接新增状态和 bind 时直接新增状态均不得再写无路径主本。普通资源锚定一个工程内已存在的文件；`RT001`/`RT002` 锚定一个已存在的文件或构建目录（目录仅在发版时临时压缩）。模板 `init theme/widget` 负责创建空 `dist/` 目录后落状态；通用 `init --type RT001|RT002 --artifact <文件或目录>` 是已有项目的本地接入入口，不复制模板、不创建线上资源。普通资源的通用 `init` 同样必须给显式 `--artifact`，因此不再支持“产物尚不存在却先立一份空身份”。`create` / `bind` 在无可续接本地状态时必须给产物路径，且在平台调用前完成路径存在性预检；已有合格状态可复用其锚点。`version set` 只能改为现存且类型匹配的锚点。旧版无 `filePath` 状态不自动猜测迁移：CLI 保留文件并提示先备份、删除同编号身份与工作稿整组，再以 `init --artifact`、`create --artifact` 或 `bind --artifact` 重建。必须同步本地 schema、索引、事务前校验、普通/主题/插件场景、ARCHITECTURE 02/03/04/08、创建 PHASE、使用手册、单元/CLI/dev 真网验证；不允许仅放开 `init --type RT001` 而保留其它无锚点写入口。

### 2026-09-09 基础场景复核：同一素材目录的多文件不是一个资源

**影响分析与结论：**用户再次确认，`media/` 中的 `video.mp4`、`cover.jpg` 等文件各自发行独立资源，是多资源工程的基础场景；“一个工程可管理多份独立单资源”绝不能被解释为“每份资源必须另建目录”。这不改变状态 schema、事务或平台 DTO：每次新增资源仍在同一 `.freelog/` 创建下一编号 `N.json`，其中各自保存唯一且已存在的 `filePath`。受影响入口为 `create` / `bind` 的新增路由（不得被根选择钩子强制挑已有资源）、所有后续单资源命令（必须以 `--resource` 定位 N）、`init`（仅接入第一份而非多资源追加入口）及用户对 `--artifact` 的理解（只指向当前资源产物，不选择资源）。普通文件、主题和插件均可在同一目录中多份管理，差别仍只有目录能否作为主题/插件锚点；平台每个文件仍单独建壳、单独发行，绝不形成批量发行。同步修正使用手册、创建 PHASE、真实/实现场景和领域测试；删除“create/bind 路径可暂时不存在”的旧语义。验证须覆盖同目录连续 `create --artifact video.mp4`、`create --artifact cover.jpg` 分别写入 `1.json` / `2.json`，以及后续以 `--resource file:N.json` 精确发版。

**实现复核修正：**复核发现主路由正确，但 `validateLocalState` 曾按原始字符串比较 `filePath`；手工状态中的 `./video.mp4` 可绕过与 `video.mp4` 的重复检测，进而破坏“一份产物只能属于一份身份”的多资源不变量。现统一以工程内规范路径做全量冲突检测，并增加回归测试。另发现 `create` / `bind` 在接续未绑定身份、且用户省略 `--artifact` 时会复用 `filePath`，却没有重新检查该文件或主题/插件构建目录是否已被删除；现统一通过同一锚点校验，缺失时在任何线上写入或本地绑定写入前以 `ARTIFACT_ANCHOR_MISSING` 停止。零状态提示也改为“可直接 create，init 仅可选首份接入”，避免把 `init` 误导为每个资源的必经步骤。该修正不改变资源编号、工作稿归属或主题/插件压缩规则；bind 为取得远端类型可先查询详情，但不会写入身份。

### 2026-09-09 已定设计：本地只保留当前工作稿，不保存已发布版本历史

**影响分析与结论：**用户否决“每个已发布版本写本地回执、按历史版本绑定本地文件”的扩展。平台是版本历史和版本内容的唯一数据库；本地不复制大文件、不缓存每个已发布版本的 SHA/表单，也不新增 `receipt`、历史文件绑定或版本回执目录。保留既有的两层状态：`N.json.filePath` 是该资源下一次发版的可变默认产物路径，`N.version.json` 是唯一未 POST 的下一版工作稿（文件 SHA、文件名、属性、依赖和更新说明）；成功 POST 后删除工作稿。`a.mp4 → b.mp4` 是一次新的本地工作稿与默认路径更新，不需要保留 `a.mp4` 的本地历史，历史事实由平台版本详情查询。普通资源与主题/插件显式文件（含 zip）同样处理；主题/插件目录仍只是可变构建输入，提交时临时压缩。

**命令与恢复边界：**不新增“对历史版本 bind 本地文件”的命令。`version draft pull [--version <线上版本>]` 只把线上版本表单拉为当前可编辑工作稿；随后以 `create-version` / `update-version --artifact <当前文件>` 准备并提交下一版。`version set --artifact <路径>` 仅修改当前默认产物，绝不触碰线上历史。`status` / `version show --version` 查询平台事实，`version show --local` 只显示当前工作稿。此决定不改变 `N.json`、`N.version.json`、索引、事务、命令树、迁移或多资源选择实现；已核对 ARCHITECTURE 02/05/06/08、PHASE、场景和使用手册均以“唯一未提交工作稿、成功后删除、平台保存历史”为现有口径，故本轮只更新交接事实，不新增代码或测试。

### 2026-09-09 用户场景复核：多资源可见性与恢复文案

**影响分析与结论：**本轮不改变资源路由、`N.json` / `N.version.json` schema、事务或平台请求；只补齐已定规则在交互、非交互提示与用户手册中的可见性。受影响入口是根 `preAction` 的资源选择、所有继承该钩子的单资源命令，以及 `resource sync` 的发现入口。TTY 列表必须补齐文件名、标题、短标识、资源 ID、类型、产物路径、工作稿状态；非 TTY / `--yes` 拒绝必须列出可复制的 `file:N.json` 示例。普通文件、主题和插件只在产物路径形态不同，选择信息与恢复规则完全相同。平台调用边界不变：选择、取消和非交互拒绝均在平台调用前；工作稿状态仅本地读取。真实场景 S63/S64/S65、场景实现、使用手册（多资源、标题同步、完整状态单元恢复）和 CLI 级测试同步更新。

**标识符约束核验：**业务梳理规定创建使用短 `name`，但以 `username/name` 调 `Resource.info` 查重；同一账号命名空间内不得重复，创建后不可修改（[P0-F0-Step1](./业务梳理/创建流程%20-%20发行单个资源/P0-F0-Step1-创建授权条目.md) §字段约束）。因此不允许同工程重复短标识；本地 `resourceId` 是最终全局唯一键，`name:<username/name>` 仅是对当前已记录短标识的便利匹配，不新增字段或放宽重复检查。

### 2026-09-09 使用手册信息架构复核

**影响分析与结论：**本轮只重构发布包内 `使用/` 手册的阅读路径，不改变命令、参数、资源路由、本地 schema、事务或平台调用。受影响的是用户和 AI 的发现路径：原结构按专题讲解充分，但没有一份只依赖发布包、能完整映射公开命令至前置条件与副作用的索引，容易把 `version draft description` 与 `version description` 混用，也难以找到 `--reset` / `--reuse-version` 等恢复入口。现以 `README` 作为按目标导航和通用契约，新建 `10-命令参考` 覆盖命令树，并让版本工作稿、场景和错误恢复交叉链接同一套术语。普通资源与主题/插件仍仅在产物形态上不同；多资源规则明确区分：常规命令零份提示初始化/接入、单份自动选中、多份 TTY 选择或非交互显式 `--resource`，而 `create` / `bind` 是新增或接续身份、`resource sync` 是批量标题同步。审计当时发现的 `--reset` 删除时序问题已在后续“有损工作稿操作统一化”条目中通过预检与确认契约修复。构建已确认该目录完整复制至发布包 `dist/docs/`。后续新增、删除或改名公开命令时，必须同时更新命令参考、相关专题和至少一个场景，而不是只改设计 `COMMANDS.md`。

### 2026-09-09 有损工作稿操作统一化

**影响分析与结论：**使用手册复核发现 `version draft discard` 设计要求的 TTY 确认未实现，`create-version --reset` / `update-version --reset` 又在门禁、版本号与产物校验前删稿；这会让取消、无效命令或缺失产物造成不必要的本地工作损失。受影响命令是 `draft discard`、`draft pull` 覆盖、两条 `--reset` 发行路径与 `bind --force --yes`；受影响状态仅为选中身份的 `N.version.json`，身份/索引事务和平台 DTO 不变。统一规则写入 [05-版本工作稿与独立命令](./脚手架设计/ARCHITECTURE/05-版本工作稿与独立命令.md#0-统一的有损工作稿操作契约)：TTY 默认否确认、非 TTY 必须 `--yes`、取消/前置校验失败保留稿、确认后的外部失败不恢复、领域层拒绝未确认删除。`bind --force --yes` 继续使用同事务身份换绑语义。PHASE、真实/实现场景、用户手册、命令层与领域层测试必须同步；特别覆盖多资源只影响选中稿、TTY 取消、非 TTY 拒绝、错误路径保留与确认后失败。

### 2026-09-09 场景证据回溯：多资源同步、生命周期与本地恢复

**影响分析与结论：**本轮不改变公开命令、状态 schema、平台 DTO 或普通资源/主题/插件的产品规则；目标是让场景证据与已批准设计一致。审计发现 S65/S66 先前只有 TTY 选中后 `update --title` 的真网证据，缺少另一工作区改标题后精确/批量同步，以及多资源工程连续 create/bind 的实际状态分配；这些补入同一未发布 dev 验证脚本。另发现 S48 未明确“进程中断后事务恢复”与“另一命令占用工程”的用户结果。该缺口横跨所有本地身份和工作稿写入，但不应借此修改平台调用：存活锁必须在任何平台调用前拒绝；可校验的 `.txn.json` 必须在下一个持锁操作中前滚为完整状态；无法证明安全的冲突日志必须保留并提示备份。真实场景、场景实现、场景索引与本地事务/锁测试需同步；dev 真网只验证平台相关的 S65/S66，本地中断/锁竞争以确定性自动化复现，不伪造平台证据。

## 当前事实

| 项 | 当前口径 |
|---|---|
| 范围 | 仅普通单资源、主题、插件；合集、批量发行、RSS、支付、上抛、session、studio 不做。 |
| 环境 | 显式使用 `--env dev` 或 `--env test`；省略是 prod，而 prod 平台调用当前被拦截。 |
| 发行 | 无线上版本只能 `create-version` 发布 `1.0.0`；有线上版本只能 `update-version` 发布新号；两条命令不可合并。 |
| 工程边界 | 一个工程可管理多个独立单资源：同一素材目录的多个文件可分别对应 `.freelog/N.json` 与 `N.version.json`，`index.json` 是派生索引。常规资源命令用 `--resource` 选择；未指定时单份自动选择、多份交互选择。`create` / `bind` 则可新增或接续身份，不能被迫先选已有已绑定资源。 |
| 产物路径 | 公开命令只使用 `--artifact <path>` 表示产物路径；它绝不选择资源。身份通过 `--resource <selector>` 或交互列表选择。 |
| 本地状态 | `N.json` 是身份、标题与默认产物路径；同号 `N.version.json` 是未提交下一版，POST 成功即删除。`update --title` 成功后回写标题，`resource sync` 可按资源 ID 批量同步当前环境的标题。没有 `N.template.json`。重复身份、路径冲突或孤儿工作稿一律保留并报错，给出备份、删除完整状态单元或重新 bind 的选项。 |
| 模板 | `init theme` / `init widget` 仅安装受控、固定版本的线上模板；不渲染、不安装依赖、不写模板元数据。 |
| 主题/插件产物 | `RT001` / `RT002` 的目录产物由 CLI 在发版时打临时 zip；其它类型传目录失败。 |
| 可选配置 | 只能在类型详情 `supportOptionalConfig === 2` 时添加。当前 dev 的 `RT001` 不满足此条件，主题不能假定支持可选配置。 |
| 依赖 | 只看 `Resource.batchAuth` 的 `isAuth`；未授权时列出全部启用策略，用户选一条签约，签后直接写稿；不区分免费/付费，不查合约，不处理上抛。 |
| 本地可靠性 | 状态写入使用锁、原子文件替换；跨身份/工作稿改动写 `.txn.json`，下一次持锁操作前滚恢复。 |

推荐主路径：

```text
普通文件（首个，可选）：login → init . --type <leaf> --artifact video.mp4 → create --title <标题> --name <标识> → create-version --prepare → create-version --yes
普通文件（同目录继续新增）：create --title <标题> --name <标识> --type <leaf> --artifact cover.jpg → create-version --resource file:2.json --prepare
主题/插件：login → init theme|widget . --template <id> → create → 自己构建 dist → create-version --artifact dist --yes
已有资源：login → bind <id|username/name> --artifact <文件或目录> → version draft pull → update-version --yes --bump patch
```

`login` 后再 `init .` 是允许的：init 会保留唯一既有的 `.freelog/auth` 认证选择器；任何其它业务文件或既有身份状态仍拒绝覆盖。

### 设计变更影响分析：主题/插件允许直接提交压缩文件（2026-09-09）

**变更动机**：主题/插件不是另一套资源版本系统。模板功能只影响 `init theme/widget`；压缩功能只在发版时、且产物是目录时介入。用户显式提供已压缩的文件时，CLI 不得再次压缩，也不得拒绝该文件。

| 受影响面 | 需变更或复核的内容 |
|---|---|
| 命令入口与本地状态 | `create`、`bind`、`version set` 记录的 `filePath` 可为目录或普通文件；`create-version`、`update-version` 的 `--artifact` 仍只表示路径，不影响资源选择。 |
| 发版实现与平台调用 | `RT001` / `RT002` 仅在路径为目录时临时压缩；路径为文件（包括 `.zip`）直接计算 SHA、上传、解析和提交。非主题/插件仍拒绝目录。 |
| PHASE、架构与手册 | 修订 06、创建/更新版本、命令速查和主题/插件使用说明，删除“主题/插件只能目录 / zip 必须拒绝”的旧规则。 |
| 场景与测试 | 主题/插件首版和新版本各覆盖目录自动压缩、显式 zip 直传、普通文件直传、空目录/工程根拒绝；验证临时 zip 只在目录分支创建和清理。 |
| 不受影响的边界 | 不改变模板来源、类型 `RT001` / `RT002`、资源选择、工作稿模型、目录压缩内容规则、普通资源的“目录失败”规则，且 CLI 不运行构建命令。 |

该分析已复核：没有引入新的平台接口、版本字段或本地状态类型；核心不变量是“按产物形态决定是否压缩”，而非“按主题/插件类型强制目录”。
