2. 改行为前先读 [脚手架设计](./脚手架设计/README.md) 的对应 ARCHITECTURE、PHASE 和 COMMANDS；字段、长度、DTO 以 [字段级校验对照表](./业务梳理/字段级校验对照表.md) 为准。

4. 当前工作区有大量与本轮相关的未提交修改。不得 `reset --hard`、`checkout --` 或覆盖不相关修改。

## 已确认产品边界

| 主题 | 当前规则 |
|---|---|
| 资源模型 | 每份资源是一个独立单资源。合集、批量发行、RSS、支付、session、studio 均不做。 |
| 身份主本 | `.freelog/N.json` 是永久的本地身份与产物锚点，不是版本历史。已绑定后的 `resourceId`、完整 `resourceName`、类型、环境是身份事实；`title` 只是可过期、可重复的展示缓存。 |
| 工作稿 | `.freelog/N.version.json` 仅为同号资源当前未提交工作稿。确认版本 POST 成功时删工作稿；平台保存历史。 |
| 资源选择 | `--resource` 只选择身份：`id:`、完整 `name:`、`artifact:`、`file:N.json`。不支持 `title:`；标题同步只能显式 `resource sync`。 |
| 产物参数 | 公开命令只使用 `--artifact <path>`；它只表示文件或构建目录，不选择身份。没有公开 `--file`。 |
| 产物形态 | 普通资源必须锚定/提交普通文件。主题、插件可锚定文件或构建目录；仅目录在提交时临时压缩，显式文件（含 zip）直接上传。 |
| 模板 | 模板在线安装并原样复制；当前不渲染 `package.json`。没有 `N.template.json`。主题/插件的类型固定，无需用户选择。 |
| 环境 | 显式 `--env dev` / `test`；省略为 `prod`，当前 prod 平台调用被拦截。身份环境必须与当前环境一致。 |
| 远端写入 | 已绑定资源的写入前必须以 `resourceId` 重查详情，严格确认响应 ID、当前 owner（`userId` / `ownerId` / `creatorId`）和未冻结。 |
| 策略与依赖 | 策略模板分页展示所有适用模板；依赖未授权时展示对方所有启用策略，由人或脚本显式选择 `--policy-id`，绝不取“第一条”。 |

## 本轮已落地的实现

下列项目已同步正式设计、实现和至少针对性自动化测试；它们仍须纳入本轮全量与 dev 真网验收，不能单独视为最终交付。

| 领域 | 已落实的关键行为 |
|---|---|
| 身份与路径 | 删除公开标题选择；缓存完整 `resourceName`；编号通过 `.sequence` 单调不复用；所有产物路径以最终工程根解析并做真实路径、软链接、重复和目录嵌套检查。 |
| 本地状态 | `N.json` 是唯一身份集合，不读取/重建 `index.json`；遗留 `index.json` 仅由 `resource list` 提示。新事务禁止写索引，旧事务恢复仍可安全处理旧索引条目。 |
| init/create/bind | 普通资源必须关联现存工程内文件；主题/插件可关联现存文件或构建目录。`init`、`create`、`bind` 在写入前检查锚点；create/bind 新增与接续不再靠“第一份未绑定状态”猜测。 |
| 版本提交 | SHA-1 流式计算，上传使用文件 Blob；上传/分析前后核验文件指纹。主题/插件目录打稳定排序的临时 zip，拒绝软链接和非正常条目，并清理临时文件。 |
| 工作稿安全 | `reset` 在删稿前做路径、形态、生命周期等确定性校验；失效系统附加属性可用 `version attr review` 逐项查看/放弃。 |
| 远端门禁 | listing、策略、上下架、版本、依赖签约等写入口均有环境、精确 ID、owner、冻结核验；`validate --for online` 与 `online` 使用同一门禁。create 查重和 bind 同样兼容三种 owner 字段。 |
| 远端版本结果未知 | 版本 POST 前创建 `.pending-operation.json`；未知结果保留未决记录与稿，阻断后续业务写。`resource recover [--apply --yes]` 只核验、不重发，只有目标版本号与 SHA-1 精确一致才可收尾。恢复会核验 ID 与 owner；冻结不妨碍只读核验。 |

## 已知未完成或需继续复核的事项

1. **远端未知结果不是全覆盖。** 已可靠闭环的是版本 POST。create、listing、策略、上下架和依赖签约尚未全部建立同等的可证明 recovery；其中没有平台幂等键或不可歧义查询条件的操作，不能伪造“已经可恢复”。新扩展必须先说明平台可证明事实、用户确认点和无法证明时的保留策略。
2. **实际 TTY 的 dev 伪终端证据待补。** 本机没有 `expect` / 其它伪终端工具；`verify-multi-resource-tty` 与 `verify-draft-safety` 已明确跳过这两段实际交互，同时完成其余 dev 路径。多资源选择和确认取消已有包内单测。安装可用伪终端后应重跑两脚本以补终端端到端证据，不能把“跳过”写成通过。
3. **未知提交不能稳定地在 dev 人为制造。** 版本 POST 的未知结果由 pending/recover 单测覆盖；若以后有可控网络中断环境，需用真实 POST 中断后按 `resource recover` 再补一次端到端证据。
4. 已完成本轮最终静态精校：非归档文档不再把 `index.json`、`--file`、`artifactMode`、标题选择器或“仅免费模板”描述成现行规则；主题/插件的预制 zip 换锚点也已补入用户手册。
5. [当前设计健壮性问题与目标模型](./当前设计健壮性问题与目标模型-2026-09-10.md) 和 [治理计划](../../../.omx/plans/2026-09-10-单资源CLI健壮性治理计划.md) 仍须在每次新增设计决定后同步状态；不要让早期“全部未实现”表述继续误导后续工作。
6. **下一轮先讨论策略与依赖设计，暂不据此改代码。** 需从用户场景逐项确认：资源自身授权策略的模板适用性、分页/搜索/选择与配置工作稿；依赖资源的授权状态、全部启用策略的显式选择、签约结果与支付边界；策略变更、依赖替换/删除、版本提交、上架之间的约束；以及远端写入失败、未知结果和恢复的可证明边界。讨论结论须先落到正式设计与使用场景，再进入实现和 dev 验证。

## 下一步顺序

1. 任何**新的产品取舍**先向用户说明场景、命令、本地状态、平台边界、异常恢复、普通资源/主题/插件差异和测试，再等待复核；对已经确认的正式规则，仍必须先更新设计文档再改代码。
2. 先完成“策略与依赖”设计复核：按上一节的场景、命令、本地状态、平台边界、失败/恢复和测试形状逐项讲解、讨论、确认；在正式设计与场景文档更新并经用户复核前，不修改相关业务代码。
3. 安装可用伪终端后补跑实际 TTY 的多资源选择、标题更新和默认取消；保留脚本的“无工具则跳过”提示。
4. 若平台提供幂等键或可精确查询条件，再逐项设计 create、listing、策略、上下架和依赖签约的未知结果恢复；不要把版本 POST 的方案生搬过去。
5. 每次变更继续跑完整本地验证、构建和发布包验证；检查打包后的 docs 与 CLI help，并按影响面补 dev 场景。

## 不要违反

- 不实现或注册 `publish`、顶层 `release`、顶层 `dep`、合集、session、studio 命令。
- 不把 `create-version` 与 `update-version` 合并；没有 `update-version --prepare`。
- 不把 `--artifact` 当身份选择器，不按多份状态或策略列表的“第一条”自动操作。
- 不在 `N.json` 放版本号、策略、listing、SHA-1、模板元数据或秘密；标题只作展示缓存。
- 不用不存在本地产物的旧 SHA 发版；不要求主题/插件用户预先手工压 zip。
- 不把历史评审中的“建议”“待实现”“未确认草案”当作可用功能。
- 不将密码、token、cookie 写进仓库、文档、测试输出或终端记录。
