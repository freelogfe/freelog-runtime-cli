# 资源生命周期：创建、接入与发版

本页解释资源从“还不存在”到“后续持续发版”的日常路径。它回答该用 `init`、`create` 还是 `bind`，以及首版和更新版为何是两条命令。版本工作稿的字段编辑、恢复细节见[版本工作稿](./04-版本工作稿.md)；按你当前实际处境直接执行的方案见[按场景操作](./09-按场景操作.md)。

## 创建新资源

```text
login → init（可选）→ create → create-version → 配策略 / 上架（可选）
```

| 阶段 | 命令 | 结果 |
|---|---|---|
| 选类型并立项 | `init [dir] --type <leaf-code> --artifact <path>` | 用现存产物写未绑定本地身份，不创建线上资源。主题/插件模板 `init theme/widget` 自动创建并记录 `dist`，是例外。 |
| 建壳 | `create --title <title> --name <name> [--type <leaf-code>] [--artifact <path>]` | 创建线上资源，写入 `resourceId`。新建本地状态时 `--artifact` 必填；接续已有未绑定状态时可复用其路径。 |
| 仅准备首版 | `create-version --prepare` | 上传并解析文件，留下首版工作稿。 |
| 提交首版 | `create-version --yes` | 提交 `1.0.0` 并清理成功的工作稿。 |

`create-version` 只适用于尚无线上版本的资源。`--prepare` 与 `--yes` 都会以当前产物上传并等待解析；前者只保存可编辑的工作稿，后者才提交固定的 `1.0.0`。已经有版本时它会停止并提示使用 `update-version`。

## 发布新版本

```text
version draft pull → 改工作稿 → update-version
```

先把已发版本作为新版本的底：

```powershell
freelog-cli version draft pull --version 1.0.0 --env dev
freelog-cli version show --local --env dev
freelog-cli update-version --version 1.1.0 --yes --env dev
```

也可以让 CLI 按规则递增版本号：

```powershell
freelog-cli update-version --bump patch --yes --env dev
freelog-cli update-version --bump minor --yes --env dev
freelog-cli update-version --bump major --yes --env dev
```

规则如下：

- `--version` 必须是合法 semver，且严格大于提交瞬间的线上 latest。
- `--version` 与 `--bump` 不能同时使用。
- 提交更新版时，必须同时明确提供 `--version <新号>` 或 `--bump <方向>`，并带 `--yes`；CLI 不会擅自猜测版本号或执行提交。
- `update-version` 不支持 `--prepare`；需要分阶段编辑时用 `version draft pull` 建稿。
- 发版前改文件可附 `--artifact <文件或构建目录>`；成功确认后该路径会回写身份记录。多资源工程以 `--resource <selector>` 选择身份。

## 接入已有资源

当资源已在网页、另一台机器或别的工程中创建时，不要再运行 `create`：

```powershell
freelog-cli bind <resourceId 或 username/name> --artifact video.mp4 --env dev
```

`bind` 会读取平台详情，且只接入当前账号拥有的单资源。它不会下载文件、拉取版本工作稿或修改线上资源。

接入后按线上是否已有版本分流：

| 线上状态 | 下一步 |
|---|---|
| 没有 `latestVersion` | `create-version --prepare` 后编辑并 `create-version --yes`，发行首版。 |
| 已有 `latestVersion` | `version draft pull`，编辑工作稿后以 `update-version --version` 或 `--bump` 发新号。 |

主题/插件的 `<path>` 可以是构建目录（`dist` / `build`）或已生成的单个文件（包括 zip）；在尚无产物记录的既有项目中，`bind --artifact` 必填。

- 已有相同资源 id 时，重复 `bind` 是幂等的。
- 要将一份本地身份换绑到另一个资源，使用 `bind <id> --force --yes`；旧工作稿会被清理。

## 查看与只读操作

```powershell
freelog-cli status --env dev
freelog-cli version show --env dev
freelog-cli version show --version 1.0.0 --env dev
freelog-cli version show --local --env dev
```

前三条读取线上事实；`version show --local` 只读取未提交工作稿。它们不会覆盖、提交或删除工作稿。

## `--artifact` 的含义

一个工程可管理多份独立资源身份；每一份身份各自有一个默认 `filePath`。`--artifact` 只表示**本次选中资源**的产物路径，绝不选择资源。多份状态时统一传 `--resource id:<资源ID>`、完整 `name:<username/name>`、`artifact:<已记录的相对文件或目录>`，或 AI/脚本精确使用的 `file:N.json`；不传时交互终端列出完整信息供选择，非交互会列出全部可复制候选并停止。标题可重复、可变化且可能落后线上，只在列表展示；人工和脚本使用稳定的 `id:` / `name:`，同一目录多文件可用 `artifact:`。新增本地身份的 `init` / `create` / `bind` 都用 `--artifact` 记录一个**当前已存在**的默认路径；接续已有合格身份时可复用其路径。`create-version` / `update-version` 用它指定本次文件或目录，发版产物也必须真实存在：

| 场景 | 传入的路径 |
|---|---|
| 普通资源 `--artifact` | 一个实际文件。目录会被拒绝。 |
| 主题 / 插件 `--artifact` | 一个构建产物目录（例如 `dist` / `build`）或已生成的单个文件（包括 zip）。目录由 CLI 临时压缩，文件直接上传。 |

发版未传 `--artifact` 时，CLI 只会在已记录路径确实存在时采用它；`--yes` 遇到缺失路径会失败，要求显式给出 `--artifact`。不支持 `--file`；一个工程可管理多份独立资源身份。
