# 按场景操作

本页是决策入口：先判断资源是否已经在线上存在、是否已经发行过版本、当前工程是否已有 `.freelog/` 身份，再复制对应路径。不要把 `init`、`create`、`bind` 当成同义词：它们分别是立项、建线上资源壳、接入已有线上资源。需要解释命令语义时回到专题页；需要完整参数和副作用时查[完整命令参考](./10-命令参考.md)。

所有例子以 `--env dev` 为例；多资源工程中，除新增或接续身份的 `create` / `bind` 外，每一条涉及某资源的命令都补上 `--resource <selector>`；产物始终用 `--artifact <path>`。

## 先选入口

| 你现在的情况 | 从这里开始 | 不要做 |
|---|---|---|
| 已有普通文件、资源还未上线 | `init --type <最终叶子> --artifact <文件>`，再 `create`；也可直接 `create --type … --artifact …` | 把父类型或类型名称交给 `--type`，或让状态没有产物路径。 |
| 空目录，要从官方主题/插件模板开始 | `init theme|widget <目录> --template <id>` | 选择资源类型，或手工复制本地模板。 |
| 已有主题/插件工程、没有线上资源 | `init --type RT001|RT002 --artifact <文件或目录>`，再 `create`；也可直接 `create` | 运行会复制模板的 `init theme/widget`，或让 CLI 再压已准备的 zip。 |
| 线上有自己的壳但没有发行版本 | `bind <资源ID或username/name> --artifact <文件或构建目录>`，再 `create-version` | 再次 `create`。 |
| 线上已有发行版本 | `bind <资源ID或username/name> --artifact <文件或构建目录>`，再 `version draft pull` 和 `update-version` | 用 `create-version` 再发 1.0.0。 |
| 已有本地身份和未提交工作稿 | `version show --local` 后继续编辑或丢稿 | 手工编辑工作稿 JSON。 |
| 同一工程有多份资源身份 | 先用 `status --resource id:<资源ID>`、`name:<标识>` 或 `artifact:<文件>` 确认目标，再在后续命令沿用同一 `--resource` | 用 `--artifact` 上传参数、标题或状态文件顺序猜测目标。 |
| 只改展示信息、策略或上下架 | 进入资源管理命令 | 为此创建新版本或新资源壳。 |

## 场景一：从空目录发行普通文件首版

```powershell
freelog-cli login --env dev
freelog-cli init . --type RT006003 --artifact video.mp4 --yes --env dev
freelog-cli create --title "我的视频" --name my-video --artifact video.mp4 --yes --env dev
freelog-cli create-version --prepare --env dev
freelog-cli version show --local --env dev
freelog-cli create-version --yes --env dev
```

不知道最终叶子 code 时，先运行 `type search <关键词>`，或省略 `init` 的 `--type` 进入层级、搜索和直接输入 code 的选择器。首版固定为 `1.0.0`。

## 场景二：已有普通文件工程，创建首版资源

不需要也不能为了写状态覆盖已有工程。登录后直接明确类型与文件：

```powershell
freelog-cli login --env dev
freelog-cli create --title "已有视频" --name existing-video --type RT006003 --artifact video.mp4 --yes --env dev
freelog-cli create-version --prepare --env dev
freelog-cli create-version --yes --env dev
```

`create` 在建壳前确认 `--artifact` 指向工程内真实文件；它不上传文件。空文件、大小限制或内容解析等发行校验仍会在 `create-version` 停止，线上不会出现半个版本。

### 同一素材目录连续发行多个独立资源

不需要为每个视频、图片另建工程目录。一个素材目录可以依次为每个文件建立一份资源身份：

```powershell
# media/ 下同时有 video.mp4 与 cover.jpg
freelog-cli create --title "视频" --name my-video --type <视频叶子code> --artifact video.mp4 --yes --env dev
# 写入 .freelog/1.json，filePath=video.mp4
freelog-cli create --title "封面图" --name my-cover --type <图片叶子code> --artifact cover.jpg --yes --env dev
# 写入 .freelog/2.json，filePath=cover.jpg

freelog-cli create-version --resource artifact:video.mp4 --prepare --env dev
freelog-cli create-version --resource artifact:cover.jpg --prepare --env dev
```

第二次 `create` 不会要求选择或覆盖 `1.json`：在没有未绑定状态时，它新增下一个编号。后续发版、状态、上下架等操作才用 `--resource` 精确选择其中一份；可用 `id:`、`name:`、唯一 `title:`、`artifact:` 或 AI/脚本使用的 `file:N.json`。`--artifact` 从不承担资源选择职责。

## 场景三：从官方模板创建主题或插件并发行首版

```powershell
freelog-cli login --env dev
freelog-cli template list
freelog-cli init theme my-theme --template vite-react-ts --yes
freelog-cli create --cwd my-theme --title "我的主题" --name my-theme --yes --env dev
# 在工程自己的流程中运行构建，得到 dist/
freelog-cli create-version --cwd my-theme --prepare --env dev
freelog-cli create-version --cwd my-theme --yes --env dev
```

插件把 `theme` 换为 `widget`；它的固定类型是 `RT002`，主题是 `RT001`。模板初始化后的建壳不传 `--type`，固定类型已在身份中。

## 场景四：已有主题或插件工程，创建首版资源

既有项目不运行会复制模板的 `init theme`，也没有必要补造模板元数据。先明确其固定类型和构建目录：

```powershell
freelog-cli login --env dev
freelog-cli init . --type RT001 --artifact dist --yes --env dev
freelog-cli create --title "已有主题" --name existing-theme --yes --env dev
# 自己完成构建后
freelog-cli create-version --prepare --env dev
freelog-cli create-version --yes --env dev
```

插件在 init 使用 `--type RT002`。也可直接 `create --type RT001|RT002 --artifact dist` 一步建壳。`dist` / `build` 是目录时，CLI 仅在提交前临时压缩其中内容；若指定已有 zip 或其它文件，则直接上传并可记录到 `filePath`。

## 场景五：自己的线上资源未发行，在本地补接后发首版

```powershell
freelog-cli login --env dev
freelog-cli bind <resourceId或username/name> --artifact video.mp4 --env dev
freelog-cli create-version --prepare --env dev
freelog-cli create-version --yes --env dev
```

主题/插件把 `video.mp4` 换成 `dist`、`build` 或已有 zip。`bind` 会从平台读取类型；对主题/插件，没有已记录产物时须传 `--artifact`。

## 场景六：自己的线上资源已发行，在本地接入并发新版本

```powershell
freelog-cli login --env dev
freelog-cli bind <resourceId或username/name> --artifact dist --env dev
freelog-cli version draft pull --env dev
# 编辑属性、可选配置、依赖或说明
freelog-cli update-version --bump patch --yes --env dev
```

普通文件把 `dist` 换成文件。使用 `--version 1.1.0` 也可以代替 `--bump patch`；两者不能同时传。若已有本地工作稿，先 `version show --local`，决定继续、`version draft discard`，或用 `version draft pull --yes` 明确覆盖。

## 场景七：构建路径、工作稿或多资源工程发生变化

- 构建输出从 `dist` 变成 `build`：单份资源用 `version set --artifact build`；多份资源用 `version set --resource artifact:dist --artifact build`。只更新记录，不上传也不提交。
- 文件或目录不存在：先恢复真实产物；CLI 不会复用旧 SHA1 发新版本。
- 一个工程中有多份身份：`create-version`、`update-version`、`version draft pull` 等既有资源操作传对应的 `--resource id:<ID>`、`name:<标识>`、`artifact:<当前文件>` 或 AI/脚本使用的 `file:N.json`；不传时 TTY 可选择，非交互会停止，不会猜第一份。`create`、`bind` 例外：它们可在没有未绑定状态时新增 `N.json`；要接续某份未绑定状态时优先传 `--resource artifact:<当前文件>`，没有可用产物路径时才用 `file:N.json`。发版要换产物时再传独立的 `--artifact <新路径>`。
- 想从另一线上版本重新开始：`version draft pull --version <版本> --yes`；这会覆盖当前未提交工作稿，先看命令打印的摘要。

## 场景八：版本表单、依赖和上线

首版先 `create-version --prepare`，更新版先 `version draft pull`，之后再用 `version attr`、`version dep` 和 `version draft description` 编辑；仅当当前类型支持时才用 `version option`。依赖签约时从对方显示的**全部启用策略**中选择；签约成功后才写入工作稿。详情见 [版本工作稿](./04-版本工作稿.md)。

展示信息、策略、上架和下架不属于版本工作稿；按 [资源管理](./05-资源管理.md) 单独操作。合集、批量资源、前端库/package 模板和支付不在本期单资源 CLI 范围内。

## 场景九：只修改一个已发布版本的说明

不需要建立工作稿，也不会产生新版本号：

```powershell
freelog-cli version show --version 1.1.0 --env dev
freelog-cli version description --version 1.1.0 --description "补充发布说明" --env dev
```

这与 `version draft description` 不同：后者只修改尚未提交的更新稿。多资源工程在两条命令上都传相同的 `--resource id:<资源ID>`、`name:<标识>` 或 `artifact:<文件>`。

## 场景十：更新稿过期，选择重建或继续旧底

线上 latest 已变化而本地稿仍基于旧版本时，通常重建最安全：

```powershell
freelog-cli version show --local --env dev
freelog-cli version draft pull --yes --env dev
freelog-cli update-version --bump patch --yes --env dev
```

只有确认仍需按旧底提交时，才使用 `--reuse-version`，并让它与工作稿来源完全一致：

```powershell
freelog-cli update-version --reuse-version 1.0.0 --version 1.1.0 --yes --env dev
```

若工作稿本身不要了，可把前两步改为 `update-version --reset --bump patch --yes`；它会先校验路径与版本号，确认后才删除当前稿并重新建立。TTY 可阅读摘要后确认；确认后的网络或提交失败不会恢复旧稿，不要把它当成无损刷新。
