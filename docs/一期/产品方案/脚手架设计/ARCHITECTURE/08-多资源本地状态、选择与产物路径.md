# 08 - 多资源本地状态、选择与产物路径

本文件自 2026-09-08 起覆盖先前“一个工程只能管理一个资源”“固定 `1.json`”“发现多份身份即要求拆工程”的决定。一个工程可以管理多份**独立的单资源**；这不引入合集、批量发行或一个版本包含多个资源。

它还覆盖旧文档中把 `--file` 同时用作“选择身份”和“产物路径”的写法。公开命令只用 `--artifact` 表示产物路径；资源选择统一使用 `--resource` 或交互选择。

## 1. 状态模型

```text
<project>/
  .freelog/
    auth                 # 非秘密账号选择器
    1.json               # 资源 A 身份
    1.version.json       # 资源 A 的未提交下一版（存在时）
    2.json               # 资源 B 身份
    2.version.json       # 资源 B 的未提交下一版（存在时）
    .sequence            # 已分配的最大 N，防止复用
    .pending-operation.json # 结果未知的远端版本提交（存在时）
    .lock / .txn.json    # 瞬态可靠性文件
```

`N.json` 与同编号的 `N.version.json` 是一个资源的状态单元，编号只作文件名，不是业务排序，也不复用。所有身份选择直接扫描并校验 `N.json`；不维护第二份路径索引，以避免主本与索引分叉。

每份身份（包括未绑定立项）都必须记录：`typeCode` 与 `filePath`。已绑定身份再记录 `resourceId`、完整 `resourceName`、兼容展示用短 `name`、`title`（资源标题）与非 prod 的 `env`；未绑定身份没有这些绑定缓存。`filePath` 是现存工程内产物的唯一锚点：普通资源为文件；主题/插件可为文件或构建目录。扫描 `N.json` 时必须检查每一条路径冲突，不得存在或忽略无路径状态。`title` 仅用于展示：它不是线上标题的缓存真源，也不得参与资源匹配或平台写入判断。

`update --title <title>` 在平台成功后，必须在同一资源的 `N.json` 回写该标题。用户也可显式运行 `resource sync`：它按每份身份的 `resourceId` 从平台读取详情，**仅当响应也返回完全相同的 `resourceId` 时**才批量更新本工程中对应的 `title`，以处理 Console、其他 CLI 或其他机器造成的标题变化。

旧版 `N.json` 可以没有 `title`：读取时显示为“未同步标题”，不参与标题选择；不会因补字段而改写本地文件。新建或 bind 的身份必须写入标题。用户在确认当前环境正确后运行 `resource sync`，成功才补齐旧身份的标题；同步失败仍保留旧状态，不得填入猜测值。

## 2. 两个互不混淆的参数

| 参数 | 含义 | 适用命令 |
|---|---|---|
| `--resource <selector>` | 本次操作哪一份 `N.json`；是所有单资源命令共享的匹配协议 | 所有需要本地资源身份的命令 |
| `--artifact <path>` | 当前资源的文件或构建目录；绝不选择身份 | `init`、`create`、`bind`、`create-version`、`update-version`、`version set` |

`--resource` 可精确指定资源 ID、完整资源标识、当前产物路径或状态文件名。完整标识的重复约束以平台的 `username/name` 命名空间为准：创建前查重，创建后不可改；同工程不得保存重复完整标识和规范化产物路径。公开支持的显式形式是：`id:<resourceId>`、`name:<username/name>`、`artifact:<相对工程的文件或构建目录>`、`file:N.json`。`file:` 是本地状态文件的精确选择器，必须保留给 AI、脚本和恢复；它**不是**资源产物文件选择器。人工日常操作优先使用稳定的 `id:` / `name:`，或在同目录多文件时使用 `artifact:`。标题可重复且过期，只在列表中显示，绝不作为选择器。无前缀旧写法仅为兼容保留，不作为文档或新脚本接口；得到零条或多条都不猜测，提示用户使用显式形式。

`--artifact` 是写入身份时的必填产物锚点：`init` / 新增 `create` / 新增 `bind` / `version set` 都先验证它存在于工程内；普通资源必须是单个文件；`RT001` 主题和 `RT002` 插件可为单个文件或构建目录。路径不得落入 `.freelog/`，已存在路径必须在解析软链接后的真实路径上仍留在工程内；同一真实文件不能归两份身份，任一主题/插件目录也不能包含或被另一锚点包含。发版时它是实际上传路径且成功后回写；主题/插件目录还须非空，CLI 才临时压缩目录内容，主题/插件文件（包括 zip）直接上传。已有合格状态由 create/bind 复用既有锚点时可省略 `--artifact`，但也必须在写入前重新验证该锚点仍存在且形态匹配；它已被删除时不得建壳或 bind。

## 3. 命令路由与选择规则

每个命令必须先归入下表的一种路由，不能只因“看起来会调用 `resolveIdentity`”而省略该设计。除只读诊断 `resource list` 和未决远端恢复 `resource recover` 外，任何身份相关路径都按同一顺序执行：持锁并恢复 `.txn.json` → **全量**校验所有状态单元 → 解析目标 → 再调平台或写入。全量校验包括：所有 `N.json` 可解析；`resourceId`、标识符与规范化 `filePath` 没有重复；每个 `N.version.json` 都有同号身份且资源 ID / 类型匹配。任一项失败，保留文件、退出且零平台调用。

### 3.1 命令路由矩阵

| 路由 | 命令 | 未传 `--resource` | 传 `--resource` |
|---|---|---|---|
| 无资源 | `login`、`logout`、`template`、`type` | 不读取身份 | 不接受或忽略为未知选项；不得暗中绑定身份 |
| 本地产物接入 | `init` | 新建一份带 `typeCode` + `filePath` 的未绑定身份；模板子命令创建 `dist/` | 不接受；`init` 不向已有状态追加 |
| 单资源操作 | `status`、`version show/set/draft/description/attr/option/dep`、`create-version`、`update-version`、`update`、`policy list/template/apply/set`、`validate`、`online`、`offline` | 零份：给 create/bind 指引并失败；一份：静默选中；多份：TTY 选择或退出，非 TTY / `--yes` 失败 | 只接受恰好一份精确匹配；零条/多条均失败 |
| 创建资源壳 | `create` | 未传 `--artifact` 时仅一份未绑定状态可接续；传入 artifact 时仅同路径未绑定状态可接续，其余新路径新建 `N.json` | 只能选择未绑定状态；已绑定状态失败，绝不覆盖或重建线上壳 |
| 接入线上资源 | `bind <id\|name>` | 同一资源 ID 已存在时幂等使用那份；未传 artifact 时仅一份未绑定状态可接续；传入 artifact 时仅同路径未绑定状态可接续，其余新路径新增 `N.json` | 选择目标状态；若该资源 ID 已在另一份，失败；替换已绑定目标必须 `--force --yes` 并同事务删除该份工作稿 |
| 工作区标题同步 | `resource sync` | 同步当前 `--env` 下**全部**已绑定身份；这是唯一批量例外，不弹选择菜单 | 只同步精确命中的一份，且其 `env` 必须等于当前 `--env` |
| 本地诊断 | `resource list` | 扫描 `.freelog` 的所有身份、工作稿和未决记录；不读平台、不写文件 | 不接受；诊断必须完整显示，不能只看被选中的一份 |
| 未决远端恢复 | `resource recover` | 由 `.pending-operation.json` 固定唯一 `N.json`，无需且不接受选择器 | 不接受；见 [02 §2.1.1](./02-本地状态.md#211-远端结果未知只核验不重发) |

`init` 的模板子命令保持“不覆盖非空工程”的边界；通用 `init --artifact` 可以在没有资源状态的已有项目中接入**第一份**产物，但不得向已有状态追加身份。`create` 与 `bind` 是新增或接续状态单元的专属生命周期入口，不能套用“多份就先选一份”的通用钩子；这确保已经有多个已绑定资源时，用户仍能新增资源。

对“单资源操作”路由：

1. `--resource` 已给：按 §2 精确解析，得到一条才继续。
2. 未给且工程只有一份可用 `N.json`：静默自动选择该份，不提示选择，保持单资源工程的便捷性。
3. 未给且没有 `N.json`：不弹出空选择列表，不调平台。提示按意图直接执行 `create --type <叶子类型> --artifact <路径>`（新资源；也可先 `init` 再 create），或 `bind <资源 ID|标识符> --artifact <路径>`（接入已有资源）；以 `IDENTITY_NOT_FOUND` 失败。
4. 未给且有多份：TTY 列出 `N.json`、标题、完整标识、资源 ID、类型、产物路径和是否有工作稿；用户选择一项或明确退出。退出不写本地、不调平台。
5. 未给且多份但非 TTY 或给了 `--yes`：失败并逐份列出可复制的 `id:`、`name:`、`artifact:` 与 `file:N.json` 候选；绝不按“第一条”执行。`file:` 让 AI/脚本可精确重试，人工不必记住编号。

标题不是唯一键，也不是选择条件；资源 ID、完整标识、`N.json` 文件名和规范化产物路径必须在一个工程内唯一。即使在 TTY 中，**已显式给出的歧义选择器也不再弹第二次猜测菜单**：CLI 报出候选并要求改用 `id:`、`name:`、`artifact:` 或 `file:`。只有完全未传 `--resource` 时才进入选择列表。`artifact:` 只用于选择已记录的资源；本次上传或修改默认路径仍只能用另一个参数 `--artifact <path>`，两者不可混淆。

## 4. 已有本地状态冲突与恢复

CLI 先持有 `.lock` 并恢复可验证的 `.txn.json`，再检查所有状态单元。遇到下列冲突均停止，不访问平台、不删除或覆盖任何身份/工作稿：

`resource list` 是这条规则的只读例外：即使某一身份或工作稿坏了，它也必须逐文件报告“有效 / 损坏 / 孤儿 / 冲突”，让用户知道正常状态与坏文件各是什么；它不选择资源、不访问平台、不自动修复。此时其它资源命令仍整体停止，因为无法证明冲突不会影响目标。用户先备份 `.freelog`，再按报告人工删除完整状态单元或修复文件；CLI 不根据 mtime、标题或目录顺序猜测保留哪一份。

| 冲突 | 处理与用户选项 |
|---|---|
| 手工复制造成两份 `N.json` 的同一 `resourceId`、`name` 或 `filePath` | 报出冲突文件。用户可备份后删除整组重复的 `N.json` + `N.version.json`，或保留一组、删除另一组后重新 `bind`。CLI 不选“较新”者。 |
| `N.json` 缺少 `filePath`，或新路径不在工程内 / 不存在 / 形态不匹配 | 视为不完整状态，停止且不访问平台。CLI 不扫描或猜测文件；用户备份后删除同编号状态单元，再用现存产物重新 `init --artifact`、`create --artifact` 或 `bind --artifact`。 |
| `N.version.json` 没有同号身份，或身份与工作稿的资源 ID / 类型不一致 | 报出两份文件并保留。用户可备份后丢弃孤儿工作稿，再 `version draft pull`；不得把稿自动接到另一资源。 |
| `bind` 的资源 ID 已存在 | 选择已存在的那份；同 ID 且类型一致时幂等。若用户要替换该份绑定，须显式 `--force --yes`，并在同一事务内删除其工作稿。 |
| `bind` / `create` / `version set` 指向已被另一资源占用的规范化或真实 `filePath`，或主题/插件目录与另一锚点嵌套 | 拒绝并显示占用的 `N.json`；用户可选择那份资源、为新资源传新的 `--artifact`，或先有意识地更改旧资源的 `version set --artifact`。 |
| 标题相同 | 不是状态冲突；交互列表展示 ID / 标识符供选择，非交互必须给唯一 `--resource`。 |

### 4.1 标题同步的边界与失败

`resource sync --env dev|test|prod` 只请求同一环境的已绑定状态：`env=dev` 只在 dev 同步，`env=test` 只在 test 同步，未写 `env` 的身份只在 prod 同步。它必须先检查本地身份/工作稿冲突；存在重复 ID、损坏身份或孤儿工作稿时，整体停止，以免把远端标题写到不可信的本地状态。

请求成功的标题先留在内存；所有请求完成后，把成功项的 `N.json` 放进同一 `.txn.json` 原子提交。任一资源的请求失败、不可见或环境不匹配时，该份标题保持原值；命令打印成功数、失败的 `N.json` 与原因，并以非零退出。这样允许网络部分失败而不留下半写 JSON，也不会把失败误报成已同步。`--json` 输出每一份的结果，便于重试。

同步是显式命令，普通资源操作不会因标题可能过期而额外批量访问平台；需要选择资源的命令仍可用 ID、完整标识、文件名或交互列表可靠定位。标题只作展示和本地搜索提示，搜索结果仍须以稳定选择器确认。

用户可以随时备份或删除某个资源完整的本地状态单元（`N.json` 与同号 `N.version.json`），之后在空位重新 `bind <id> --artifact <path>`。删除未提交工作稿会丢失本地未 POST 的属性、配置、依赖和描述；CLI 在任何提供删除动作前必须提示这一点。当前没有自动清理或自动拆分命令。

## 5. 实现与验证边界

所有本地状态写入继续采用锁、原子替换和跨文件 `.txn.json`。资源选择发生在任何平台调用之前；写入目标始终是已解析 `N` 的那一组文件。

最少测试覆盖：零身份时的无平台提示；单份静默自动选择；多份 TTY 选择与退出；多份非交互拒绝及完整候选；按状态文件、ID、完整标识和 `artifact:` 路径选择；标题重名、过期或唯一时均不能选择；重复 ID/标识符/路径拒绝；软链接逃逸、真实文件冲突、主题目录嵌套拒绝；孤儿或不匹配工作稿拒绝；`bind --force` 工作稿清理的事务恢复；`update --title` 回写；`resource sync` 的按环境过滤、全量/单资源范围、部分远端失败与事务恢复；以及普通文件、主题、插件的 `--artifact` 形态差异。
