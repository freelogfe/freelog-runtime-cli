# 02 - 本地状态与续作

当前单资源与合集的独立主链均已实现，身份可以共存于同一工程。本文件主要规定单资源工作稿与本地事务；单资源选择以 [08](./08-多资源本地状态、选择与产物路径.md) 为准。合集身份使用 `subject:"collection"`，禁止 `filePath` 和同号版本工作稿；目标选择、表单草稿及发布恢复见 [PHASE/合集](../PHASE/合集/README.md)，不能套用单资源产物模型。

本地 `N.json` 只记资源身份（已绑定后不可变）与立项阶段必须保留的最小草稿（类型、对应文件）；listing / 策略 / 上下架 / 已发版事实不缓存。
属性和可选配置往往很多，一次会话加不完（人 / AI 想到一个加一个）。所以另有 **版本工作稿** `.freelog/N.version.json`：加一项就写盘，下次接着加。  
拉 / 盖 / 丢缓存用 `version draft pull` / `discard`，不要绑在发新号上。改稿入口可以是会话菜单，也可以是独立命令（`version attr` / `version option` / `version dep`），见 [05](./05-版本工作稿与独立命令.md)。只有 `create-version` / `update-version` 会 POST。  
不做平台版本草稿（不对 `lookDraft` / `saveVersionsDraft`）。  
接续只发生在「有壳、还没有版本」。`bind` 细则见 [04](./04-bind.md)。创建步骤见 [PHASE/单资源](../PHASE/单资源/README.md)。

没有 `pull` 回写身份。继续前 **GET 平台**，对比身份，TTY 确认再写。

## 1. 原则

| 线上 | 本地 |
|------|------|
| 进度、listing、策略、版本 | 不管；每次现问 |
| 已提交的步骤 | 用详情判断 |

本地产品目录只有 **`.freelog/`**：非秘密账号选择器、编号身份主本与工作稿。秘密凭据只在系统凭据库，见 [01](./01-账号.md)。

`status` **只打印现状**，不改文件、不自动打下一步。

```
已 create、还没有版本 → 必须走 create-version（唯一接续）
已经有版本           → 创建结束；策略 / listing / 上架见 [单资源/管理](../PHASE/单资源/管理/00-总览.md)
```

### 1.1 `status`：只读事实，不补造线上数据

单资源按统一选择器定位后，保持三段文本：本地身份、工作稿有无、线上ID与latest。未绑定时未填写的名称显示空串，不打印程序值`undefined`；线上为“未查询”，不要求登录、不请求平台。已绑定时先过环境/登录与本地完整性检查，再且仅再调用一次`Resource.info({resourceIdOrName:选中ID,isLoadLatestVersionInfo:1})`。身份/稿损坏、环境不符或未登录时零请求。当前不新增成功JSON契约或上下架字段。

请求成功不等于详情可信：必须是`ret:0/errCode:0/data:对象`，`data.resourceId`为精确相同的字符串，`latestVersion`为字符串。只有平台明确返回空字符串才显示`latestVersion=无`；非空值须符合字段对照表的semver规则，原样显示，不改写版本。缺字段、null、数组、错误ID、畸形版本不能用本地ID或“无”兜底，更不能把对象转字符串后称为线上事实。Console实际版本页也使用`latestVersion === ''`识别无版本壳；已用dev只读详情确认此形状。

| 失败 | 稳定错误码 |
|---|---|
| 请求抛出未知网络/程序异常 | `STATUS_REQUEST_FAILED`，固定安全说明，不读取异常message/cause或序列化原对象 |
| 不是成功信封或没有有效data对象 | `STATUS_RESPONSE_INVALID` |
| 详情ID缺失、类型错误或与选中ID不同 | `STATUS_ID_MISMATCH` |
| latest缺失、非字符串或非空但不符合semver | `STATUS_LATEST_INVALID` |

失败通过统一错误出口非零退出，不打印半份成功三段；已受控`CliError`沿用其代码和说明。不把资源暂不可见、超时或404解释为未创建，也不重试。status不要求本人owner、不阻止冻结资源的只读查询；只核本次详情的身份真实性，不复用写门禁。

无论成功、失败或存在pending，status均不上传、不签约/支付、不写平台，也不刷新标题、修复事务、清理marker/稿或改本地任何字节。需要恢复时用户另行执行`resource recover`；只读查询不抢占写锁或宣称跨编辑器原子快照。

## 2. `.freelog/`

根上不再放 `freelog.manifest.json` / `.freelog-auth`。身份编号使用 `.sequence` 维护，不引入业务 `state.json`。

| 路径 | 角色 | Git |
|------|------|-----|
| `.freelog/auth` | 工作区凭据**选择器**，只含凭据引用和账号元数据，不含 token | 否 |
| `.freelog/1.json`、`2.json`、… | 单资源或合集身份；仅单资源记录本地产物，未绑定立项仅用于单资源 | 宜提交 |
| `.freelog/1.version.json`、… | **版本工作稿**（本次未提交的文件 sha1、属性、可选配置、依赖、描述） | 宜提交 |
| `.freelog/.sequence` | 已分配的最大身份编号；防止用户删除状态后复用编号 | 否 |
| `.freelog/collection-forms/<env>/<resourceId>.json` | 合集本地表单操作稿，从已发布快照建立，不含 Console 草稿 | 按团队协作规则 |
| `.freelog/collection-forms/intents/<resourceId>.json` | 合集未收尾发布的核验意图，使用 `collection publish resume` 处理 | 否 |
| `.freelog/.pending-operation.json` | 已发送但尚未能确认结果的**远端版本提交**最小核验记录；不是版本历史，也不是工作稿 | 否 |
| `.freelog/.lock`、`.freelog/.txn.json`、初始化 staging 标记 | 瞬态锁 / 本地文件事务恢复日志，不是业务状态 | 否 |

`resource list` 是本地诊断入口：即使身份、工作稿或未决记录已损坏，它也只读列出每个文件的状态，不选资源、不调平台、不自动删除。正常业务命令仍必须全量校验后才继续；不要用“还能列出来”误解为损坏工程可以安全写入。

编号只当文件名，**不是排序**。新资源 `max+1`，用过的号不复用。  
`filePath` 是**每份单资源 `N.json` 的必填产物锚点**，不是可选提示；合集身份禁止此字段。它必须是相对工作区根目录的规范路径：去掉 `./`、统一为 `/`，不得为空、不得指向根目录本身，也不得以绝对路径或 `..` 逃出工作区，也不得指向 `.freelog/`；已存在路径还必须在解析软链接后的真实路径上留在工程内。同工程不得锚定同一真实文件，主题/插件构建目录也不得与另一锚点互为父子，避免两份资源共享同一构建树。普通资源锚定一个现存的普通文件；主题 `RT001` / 插件 `RT002` 可锚定一个现存的构建目录或显式文件（包括 zip）。模板工程创建时先建立空 `dist/` 目录再写入锚点；空目录不能发版。路径后来被人移动或删除时，状态仍保留其最后明确关联，但任何需要产物的命令必须在平台调用前停止，不能续用旧 SHA1。身份选择直接扫描并校验所有 `N.json`，不维护第二份路径索引。
打不打 zip、发版怎么确认路径见 [06](./06-发行物与压缩.md)。不再用 `artifactMode` 决定压缩。

```
.freelog/1.json     filePath: 09-01.mp4
.freelog/2.json     filePath: 09-02.mp4
```

命令路由以 [08 §3.1](./08-多资源本地状态、选择与产物路径.md#31-命令路由矩阵) 为准：`status`、版本、策略和上下架等常规命令以统一的 `--resource <selector>` 落到一份 `N.json`；选择器只能是 `id:`、完整 `name:`、`artifact:<已记录的相对产物路径>` 或 AI/脚本精确使用的 `file:N.json`。标题仅展示，不能选择身份。未传时零份报恢复指引、一份静默选择、多份由 TTY 选择或非交互失败。`create` / `bind` 按专属生命周期新增或接续状态，`resource sync` 是唯一工作区级批量例外。独立参数 `--artifact <path>` 只表示本次上传或默认产物路径，绝不选择身份。

### 2.1 一致性与恢复

所有会改 `.freelog/` 的命令（`init`、`create`、`bind`、`version set`、工作稿修改、提交后的清理）必须使用同一个工作区独占锁。锁的获取必须是原子创建，不得先 `exists` 再写；锁记录进程、开始时间和命令摘要，便于报告占用者。

- 锁仍被存活进程持有：等待一个短、可配置的时间后失败，并显示占用命令；不得并发写入。
- 遗留锁：只在能确认原进程已退出时自动恢复；不能确认时要求显式恢复动作，不能靠删除未知文件“赌一把”。
- 每个 JSON 先在同目录写临时文件、校验 schema、flush 后以原子 rename 替换。禁止直接截断写主文件。
- 需要同步改多份文件时，先写 `.txn.json`（操作、目标、前后校验和），再逐份原子替换；下次命令启动时只前滚这笔可验证事务，绝不根据目录顺序猜测回滚。
- 读到 JSON 损坏、未知 schemaVersion、身份之间冲突或孤儿工作稿时，停止写入并打印冲突文件与恢复方向；身份 / 工作稿不得猜测修复。

### 2.1.1 远端结果未知：只核验，不重发

版本 POST 前，CLI 在持锁状态下原子写 `.pending-operation.json`。记录仅覆盖 `kind=version-submit`，并记录：`resourceId`、本地 `N`、环境、目标 `version`、待发 `fileSha1`、原始稿字节的`draftSha256`、创建时间和随机操作号；不保存 token、完整提交体、文件内容或平台版本历史。新记录使用 schemaVersion 3，并有 `state`：

1. `prepared`：所有本地 / 远端前置校验已完成，但**尚未允许调用** POST；
2. `sending`：紧接在调用 `createVersion` 前以原子替换写入。此后即使进程消失，也不能证明请求没有离开本机。

旧 schemaVersion 1 没有阶段事实，读取时必须按保守的 `sending` 解释；旧 v1/v2 都没有稿摘要，不能从恢复时的当前稿补造。`prepared → sending → POST`保留同一schema和摘要，顺序不可反转。摘要与提交体必须来自**同一次实际读盘**，在异步类型/属性校验后、建立记录前再次比对；已观察到稿变化时以`SUBMIT_DRAFT_CHANGED`停止，零POST、不新建marker，保留当前稿。任何异常都不自动重发、不重新计算bump，也不覆盖工作稿。

“同一次”还包括主体与操作：读盘稿必须与本次选中的资源ID/类型/环境一致；异步校验后重新核对身份，错配以`DRAFT_IDENTITY_MISMATCH`零POST停止。创建prepared时返回本次原始记录摘要；sending转换必须用该摘要校验前态，不能重新读取任意另一条prepared再发送旧payload。转换及读回发现记录已替换时以`LOCAL_TXN_CONFLICT`停止、零POST，完整保留替换记录和稿。

若请求返回成功，CLI清理本次未决记录；仅当当前稿原始字节摘要仍与本次发送快照相同，才在**同一个本地事务**中删除该稿。稿已变化则成功结论不变、只清本次marker，完整保留当前稿并明确提示；已无稿则不重建稿。若`sending`后网络断开、超时、进程中断或返回形状不足以证明平台拒绝，则两份文件都保留，命令报“结果未知”，并指向`resource recover`。明确字段/4xx拒绝只清本次记录，保留工作稿供修正。

`resource recover`只读显示记录和核验结论，不重发。`prepared`显示“尚未发送”，`--apply --yes`零平台请求、仅清本次marker并保留稿。`sending`（含旧v1/v2）先查询精确资源并核对本人owner，再查询目标版本；详情自身的resourceId/version/fileSha1全部精确匹配才确认远端成功。冻结不阻止只读核验。未确认、身份/环境/owner冲突或查询失败时，marker与稿原字节都保留。

远端精确成功后，按2026-10-18用户确认的收尾规则执行：

| 当前稿 | `recover --apply --yes` |
|---|---|
| v3摘要相同 | 同事务清本次marker和该稿 |
| 稿已变化（含属性/配置/依赖/说明/来源、空白、无效JSON或错配内容） | 只清本次marker，完整保留稿并提示；不解析/修复该新稿来决定删除 |
| 旧v1/v2无法证明未变 | 只清本次marker，完整保留当前稿并提示，不伪造摘要 |
| 已无稿 | 只清本次marker，不重建 |

只读预览须说明将保留还是清理稿；所有apply仍需`--yes`。最后一次远端await后重新核对本地资源ID/类型/环境并重读原始稿，不能用查询前快照决定清稿。事务创建时校验待删稿及marker的预期前态摘要，冲突则保留现场、拒绝删除另一份记录/新稿；正常事务前滚沿用既有前态检查。这不是对外部编辑器的原子锁，不能承诺在任意并发改盘下无冲突；也不把本地收尾错误说成可重发POST。存在未决记录时，其它业务写仍被阻止。

初始化还需在目标目录外使用初始化锁和 staging，完整顺序见 [03 §4](./03-init.md#4-原子性目录与提交顺序)。

恢复核验不能只相信请求参数或相同SHA：版本详情本身必须同时返回与未决记录精确相同的字符串`resourceId`、字符串`version`和`fileSha1`。缺失/畸形标识或目标错配均不能证明这次提交成功；只读时报告“冲突/无法证明”，`--apply`时以`RECOVER_NOT_CONFIRMED`拒绝。两种路径都保留未决记录与稿的原始字节，不重发、不补造响应身份；SHA相同但来自另一资源或版本也不例外。查询失败同样保留现场，不把超时推断为目标不存在。完整正确详情的只读、显式收尾、冻结后恢复及prepared本地收尾行为不变。

### 2.1 该记

| 字段 | 谁写入 |
|------|--------|
| `subject` / `typeCode` | `init` / `create` / `bind` |
| `resourceName` / `name` | **仅** `create` 成功或 `bind`；前者是完整不可变标识，后者只是展示兼容的短段 |
| `resourceId` | **仅** `create` 成功或 `bind` |
| `title` | `create` / `bind` 的平台详情；`update --title` 成功后回写；`resource sync` 批量刷新 |
| `env` | **仅**非 prod 的 `create` / `bind` |
| `filePath` | **所有身份写入均必填**：`init --artifact`；模板 `init theme/widget` 创建 `dist/`；`create` / `bind` 在新增身份时的 `--artifact`；`version set --artifact` / 发版确认后的回写 |

`init` 不写 `resourceId` / `env` / `title`。未写 `env` = prod。三套环境、`--env` 与 tools-lib：见 [07](./07-环境.md)。

### 2.2 数据在哪

| 种类 | 放哪 | 例子 |
|------|------|------|
| 不可变身份 + 对应文件 + 标题展示缓存 | `N.json` | `resourceId` / `resourceName` / `name` / `title` / `typeCode` / `filePath` |
| 版本工作稿 | `N.version.json` | 本次文件 sha1、属性、可选配置、依赖、描述 |
| 这条命令的参数 | 只在当次进程 | `create --title`、`update-version --version` |
| 已经提交的 | 平台 | 标题、策略、已发版、上架 |

未绑定的 `N.json` 只有：

```
schemaVersion: 1
subject, typeCode, filePath
# 不要再写 artifactMode；打不打 zip 看 typeCode 是不是 RT001/RT002
```

旧版缺 `filePath` 的 `N.json` 是不完整状态，而不是可用的“仅类型立项”。CLI 不猜测它应关联哪个文件，也不允许后续命令绕过该问题；用户先备份，再删除同编号 `N.json` 与 `N.version.json` 整组，以现存产物重新 `init --artifact`、`create --artifact` 或 `bind --artifact`。这符合本地状态可由用户删除、重新接入的恢复边界。

`create` / `bind` 成功后才增加：

```
resourceId, resourceName, name, title
env   # 仅非 prod
```

`N.version.json` 只装**还没 POST 的下一版**。它不是松散的“表单缓存”，而是有判别状态、来源校验和分析版本的工作稿；形状与字段归属见 [版本表单](../PHASE/单资源/版本表单/README.md)：

```
schemaVersion: 1
draftKind: initial | update
resourceId                  # 必须等于同编号 N.json.resourceId
resourceTypeCode            # 必须等于同编号 N.json.typeCode
fromVersion                 # 仅 draftKind=update 必填；initial 禁止出现
fileSha1                    # 当前待发文件；没有文件时为 null
filename
analyzedSha1                # 成功解析系统属性的 sha；未解析为 null
description                 # initial 固定 ''；update 可编辑
inputAttrs                  # 已通过当前 analyzedSha1 校验的系统附加值
orphanedInputAttrs          # 文件/分析变化后待复核的旧值，默认 []；不会自动丢弃
customPropertyDescriptors   # 自定义属性 + 可选配置
dependencies
baseUpcastResources         # 本期恒 []
authExcludedItems           # 本期恒 []；不从线上回显
```

不准写 listing、策略、资源 `latestVersion`、认证结果或合约 id。系统 `raw` 与系统字段格式不进工作稿（按 `analyzedSha1` 现解析，只展示 / 校验）。`fileSha1` **进工作稿，不进 `N.json`**；`N.json.filePath` 只记本地路径。

### 2.2.1 工作稿不变量与文件分析

`draftKind` 是唯一的流程判别，不再用“有没有 `fromVersion`”推断首版或更新版：

| 状态 | 必须 | 禁止 / 固定 |
|------|------|-------------|
| `initial` | 已有 `resourceId`；`description=''`；空数组字段存在 | `fromVersion`；编辑版本描述 |
| `update` | `fromVersion` 是存在的已发版本；`description` 可为空或编辑 | 把首版空表当回显稿 |
| 待文件 | `fileSha1=null`、`filename=null`、`analyzedSha1=null` | 提交、编辑系统附加属性 |
| 已分析 | `analyzedSha1 === fileSha1` | 使用旧文件的系统字段格式直接提交 |

每次 `create-version` / `update-version` 确认本地文件后都必须重新计算 sha：

1. sha 未变化且 `analyzedSha1 === fileSha1`：重新读取派生系统字段格式后，可继续用工作稿的 `inputAttrs`。
2. sha 改变或尚未分析：先完成新 sha 的平台解析和系统字段格式读取，再和原 `inputAttrs` 按 key 与格式逐项比对。
3. 仍存在且符合当前平台格式的值保留（包括允许的空字符串）；消失、格式不兼容或不再允许的值移动到 `orphanedInputAttrs`，不得悄悄丢弃或提交。后续分析若同 key 再次出现，且旧值通过当前规则校验，才自动恢复并从待复核队列移除；仅 key 相同不能证明值可恢复。
4. `version attr review` 必须展示保留 / 待复核摘要；人只能用 `version attr review discard <key>` 逐项确认丢弃。`--yes` 只要仍有待复核项就提交失败，要求先人工复核。写入新的 `analyzedSha1` 不等于清除待复核队列。

这使 raw 保持派生数据而不落盘，同时保证中断恢复、换文件和系统属性变化不会提交旧值。每次独立 `version attr set`、显示会话和提交前也必须按稿内 SHA 重新获得当前系统字段格式；不能只信内存结果。拉稿后 `analyzedSha1=null` 时，`attr list` 可只读解析来源 SHA，`attr set` 则先解析并在成功编辑时一并写入 `analyzedSha1=fileSha1`；解析/编辑失败不写稿。该标记不替代提交时重新计算本地文件 SHA。

从已发行版本拉稿时，系统附加值以 `systemPropertyDescriptors` 中 `insertMode===2` 的 `valueDisplay` 为来源，保留空值并转换为字符串，写入 `inputAttrs`；不从不存在的版本详情 `inputAttrs` 猜测恢复。拉稿不是对本次本地文件完成分析，编辑附加值前仍需准备/解析当前文件。自定义/可选配置与系统字段冲突时保留原稿并报错，不静默删除，不通过读取或修改 Console 草稿来“同步”。

### 2.2.2 旧工作稿

本期采用不兼容的 v1 状态切换，不保留旧工作稿迁移代码。没有 `schemaVersion=1`、身份快照不全或违反本节不变量的 `N.version.json` 都是不支持的旧/损坏状态：CLI 只读报错并保留原文件，不猜测字段、不覆盖、更不将其转换成新稿。用户可先备份，再显式 `version draft discard` 或 `version draft pull` 建立新稿。

本期没有 `N.template.json`。主题/插件模板只决定 `init theme/widget` 下载什么工程；模板不渲染，模板 id、项目名和项目版本也不会参与资源创建或发版。以后若恢复模板渲染，必须另行设计明确的渲染输入和生命周期，不能从 `N.json.name`、标题或下一版号猜测，也不能补写旧缓存。

四种动作不要搅：

| 动作 | 命令 | 写不写工作稿 |
|------|------|----------------|
| 看线上已发号 | `version show` | **不写** |
| 看本地工作稿 | `version show --local` | **不写** |
| 拉 / 盖某一号进缓存 | `version draft pull [--version]` | 按 `draftKind=update` **整份写入**。有稿时 TTY 默认不盖并确认，非 TTY 须 `--yes`。 |
| 丢掉缓存 | `version draft discard` | 有稿时 TTY 默认不删并确认，非 TTY 须 `--yes`；确认后删文件。 |

`update-version` 无稿时为了一次会话仍会按回显源拉一次（写入同 `draft pull`）。有稿且对不上：TTY 默认仍用这份；`--yes` **失败**，不要默默重拉再交。  
`version show` 有工作稿时只打一行提示，**不要**为了看线上覆盖缓存。

只看两样，**不看**平台版本草稿（不对 `lookDraft` / `saveVersionsDraft`）：

1. 线上 **`latestVersion`**（`Resource.info`，`isLoadLatestVersionInfo=1`）。没有上一版就没有回显源。
2. 本地 **`N.version.json`**：`draftKind`、`resourceId` / `resourceTypeCode` 是否仍匹配 `N.json`，以及 update 稿的 `fromVersion` 是否等于**本次回显源**。

回显源 = `update-version --reuse-version`，未传 = **latest**。`fromVersion` 只跟本次回显源比，不跟「曾经的 latest」比。  
只拉、不交：`version draft pull`（未传 `--version` = latest）。不要用 `update-version --prepare`。

| 线上 `latestVersion` | 本地工作稿 | `create-version` | `update-version` | `version draft pull` |
|---------------------|------------|------------------|------------------|----------------------|
| 没有 | 没有 | 空表走首版。`--prepare` 只建稿。视频可以不建稿 | 失败，去 `create-version` | 失败，去 `create-version` |
| 没有 | 有，`draftKind=initial` | 首版续改。TTY 提醒，**默认继续**。`--yes` 续用 | 失败（还没有版本） | 失败（还没有版本） |
| 没有 | 有，`draftKind=update` | **不读**。打印「这是更新版本的稿，发行版本不用」。本命令一旦写盘，整份按首版模型重写 | 失败（还没有版本） | 失败（还没有版本） |
| 有 | 没有 | 失败，去 `update-version` | 按回显源写入 update 稿（一次会话方便） | 按 `--version` 或 latest 写入 update 稿 |
| 有 | 有，`draftKind=initial`（首版残留） | 失败，去 `update-version` | TTY：问是否用回显盖，**默认否**。`--yes` **失败**，去 `draft pull --yes` | TTY 默认不盖；`--yes` 覆盖 |
| 有 | update 稿 `fromVersion` **等于**本次回显源 / 要拉的那一号 | 失败，去 `update-version` | 续改。TTY 提醒，**默认继续**。`--yes` 续用 | TTY：稿已是这一号，再拉？**默认否**。`--yes` 覆盖 |
| 有 | update 稿 `fromVersion` **不等于**本次回显源 / 要拉的那一号 | 失败，去 `update-version` | TTY：对不上，**默认仍用这份**。`--yes` **失败**，不重拉不交 | TTY 默认不盖；`--yes` 覆盖 |
| 人指定 `--reuse-version 1.0.0`，稿的 `fromVersion` 也是 `1.0.0`，即使 latest 已是 1.1.0 | — | 本文没有 `--reuse-version` | **等于回显源**，不算落后，续用 | 拉 1.0.0：来源已是这一号，规则同上 |

`--reset`：先完成路由、版本号与产物路径等不改盘校验；产物不仅要存在，还必须可上传（普通资源为文件；主题/插件目录非空且非工程根；显式文件含 zip 可直传）。有稿时再按统一有损操作契约确认并删除。`create-version` 再空表；`update-version` 再按回显源拉。确认后的结果等价于 `version draft discard` + 准备。坏文件、错误形态或错误命令路径失败时稿必须保留。
先按 [08 §3.1 的单资源操作路由](./08-多资源本地状态、选择与产物路径.md#31-命令路由矩阵) 以 `--resource` 或零/一/多状态规则落到哪一份。
发版确认路径、打 zip：见 [06 §3](./06-发行物与压缩.md)。记录的 `filePath` 只是提示；本地不在不要续用稿里的 sha1。`--artifact` 是本次要上传且要回写的路径；改记录而不发版用 `version set --artifact`。
解析只走 `filesListInfoSse`，从建立连接起最长 **120 秒**；连接异常、流无效或未收到终态当失败。
`fileCommitMode` 不含本地上传（`2^0`）：整命令失败。  
提交前**再** `info` 一次：`create-version` 发现已经有 `latestVersion` → 失败，去 `update-version`，稿留下；`update-version` 新号仍须 **> 当时的** latest，不够大则失败，稿留下。

每加 / 改一项、每次上传成功，立刻通过 §2.1 的原子写入落盘。退出后还在。人 / AI 可以直接改这个文件，但下次 CLI 必须先做 schema / 业务校验；坏稿只报错，不覆盖。
`create-version` / `update-version`确认POST成功后，只清理本次发送且字节未变的稿，与未决记录同事务；当前稿已变化则保留并提示，见§2.1.1。不能误续已提交旧稿，也不能误删后来新稿。明确失败留稿；结果未知保留稿和记录，走`resource recover`。
`bind` 换成另一个 `resourceId`（含 `--force`）：删掉该份工作稿。同一 id 幂等：先校验稿内 `resourceId` / `resourceTypeCode` 与身份一致，一致才保留；不一致视为损坏状态，停止写入而不是猜测复用。

### 2.3 不记（身份里）

简介、封面、策略、`latestVersion`、上下架。这些不进 `N.json`。标题仅作为可刷新、非权威的选择元数据保存在 `N.json`，并由 `update --title` 与 `resource sync` 同步。
不把版本工作稿写进 `N.json`。不对接平台版本草稿。

### 2.4 一夹多个单资源

每天一条仍是多条 F0：每次 `create --artifact` 建立或选定一份状态；后续用 `--resource`（或单份自动选择）执行 `create-version`。
线上已有：`bind <id> --artifact <path>`，不要 `create` / `pull`。

## 3. 接续

策略 / listing / 上架不接续。`init`、再发、登录不接续。

`create` 成功但 `N.json` 还没有 `resourceId`：`bind` 同一 id。禁止再 `create`。

| 线上 | 行为 |
|------|------|
| 没有 | 可以 `create`。同名已存在 → 改 `name` |
| 有壳、无 `latestVersion` | 接续 `create-version`（上传 `filePath`） |
| 已有 `latestVersion` | 创建结束。再发一版：`update-version`，见 [更新版本](../PHASE/单资源/更新版本/01-更新版本.md) |

## 4. 上传

没有版本：`create-version`，走 [发行版本](../PHASE/单资源/创建/02-Step2-发行版本.md)。  
已有版本：`update-version`，走 [更新版本](../PHASE/单资源/更新版本/01-更新版本.md)。两条命令不要互相改口。  
`directory-zip`：按磁盘时先打临时 zip 再当文件，见 [06](./06-发行物与压缩.md)。  
上传成功把sha1写入工作稿。会话每改一项写盘。中途断了整文件再传。POST成功只清本次未变稿，后来变稿保留并提示。`--reuse-version`只出现在`update-version`。

## 5. 禁止

- 按策略 / listing / 上架接续；用 `pull` 写回 manifest 或代替 `bind`
- 同名已存在当成功；已有自己的壳再 `create`
- 根上再放 `freelog.manifest.json`、把 token 写进 `.freelog/auth`
- 用编号当排序；prod 还写 `env`
- 把属性 / 可选配置 / 依赖写进 `N.json`
- 按 scaffold 决定有没有工作稿
- 对接平台版本草稿；一次会话必须把属性加完才能退出
- 用 `version show` 把线上写进工作稿；成功 POST 后还留着工作稿
- 用 `update-version --prepare` 当拉缓存；`--yes` 对不上还默默重拉再交
- 本期按合集写 `N.json` / 工作稿 / 接续
- 主题/插件要求人先自己打 zip；或把工程根当 `filePath` 默默压进去
- 写出或接受没有 `filePath` 的资源状态；按扩展名或目录扫描猜测锚点
- 发版未确认路径就按记录或旧 sha1 上传；其余类型传目录还当成功
- 先查锁是否存在、再写锁；直接覆盖 JSON；用坏状态猜测恢复
