# 批量发行单资源：数据协议与执行

状态：本轮讨论稿，待复核；代码尚未实现。

本功能让人或 AI 用一份严格 JSON 描述多份新建的**单资源（`subjectType=1`）**，由 CLI 先集中校验，再按可恢复的阶段持续发行。它解决“几十份文件逐份手工填写”的效率问题；不是合集功能、不是目录扫描、不是多资源合并成一个资源，也不是批量更新已有资源。

## 审阅速览

先用这一页确认三件事，再阅读具体字段和恢复规则：

| 问题 | 本设计的答案 |
|---|---|
| 它替代什么？ | 将多个**新单资源**的首版发行编排为可检查、可中断恢复的任务；不替代已有资源的更新。 |
| 它绝不做什么？ | 不扫描目录猜资源、不调用 Console 的黑盒批量接口、不创建合集或把资源自动加入合集。 |
| 一次失败会怎样？ | 已确认成功的资源保留；明确失败仅停止该资源；任一远端写结果未知则停止整批，先读回再决定。 |
| 用户如何填？ | 先用 `spec` 生成一份**可直接运行的完整批次文件**，再用 `check` 预检，最后 `run`。 |

```text
人工或 AI 填写 release-batch.json
  → resource batch check：集中发现可提前判断的问题
  → resource batch run：先逐项建壳，再逐项处理首版
  → 每项：产物准备 → 表单校验 → 依赖签约 → 发行 1.0.0 → listing / 策略 → 可选上架
  → 逐项报告；失败或中断用同一 runId 核验后接续
```

合集若需要这些资源，只能等其中资源已成功上架后，再由用户独立运行 `collection item add` 从线上资源库选择。批次 JSON 不允许出现 `collection`、`items`、`afterResources` 或任何合集钩子。

## 1. 范围与命令

V1 只处理 `operation:"create"` 的首版发行，首版固定为 `1.0.0`。已有壳、已有版本、绑定已有资源、批量新版本和批量改 listing 是不同问题，继续使用既有单资源命令；不得因名称存在就把 create 静默改成 update。

建议命令组：

```text
freelog-cli resource batch spec --type <leaf-code> --output <release-batch.json> --env <env>
freelog-cli resource batch check <release-batch.json> --env <env> [--json]
freelog-cli resource batch run <release-batch.json> --env <env> [--yes] [--json]
freelog-cli resource batch resume <run-id> --env <env> [--yes] [--json]
```

- `spec` 读取实时类型能力，生成一份含一个待填写 `resources[0]` 的**完整可执行批次文件**，并给出随 CLI 发布的 JSON Schema 路径；它不猜文件、授权标识、依赖、策略 ID 或动态分析值。
- `check` 不产生远端写入。它返回结构、文件、批内冲突、类型、名称、依赖目标/范围/策略和可读取的平台事实；必须清楚区分“已通过”与“上传分析后才能确定”。
- `run` 自带同样的预检，未运行过 `check` 也安全；每个远端写入前后记录状态。
- `resume` 只接续指定任务的原始有效输入快照，先核验已完成阶段，绝不从当前 JSON 猜测或重发未知 POST。

`--env` 属于执行环境，不写入输入 JSON；同一输入可在 dev 或 prod 分别运行，但运行记录必须绑定账号与环境。`--yes` 只跳过每次确认，仍不允许在未授权依赖时自动选择策略。

## 2. 为什么不调用 Console 的 `createBatch`

Console 当前批量发行页选择**同一个** `resourceTypeCode`，然后调用：

```text
POST /v2/resources/createBatch
{
  resourceTypeCode,
  createResourceObjects: [
    { name, version, fileSha1, dependencies, batchSignContracts, policies, ... }
  ]
}
```

该一次请求同时创建壳、首版、策略、依赖和内嵌签约。它的部分成功结果只以资源名映射返回，无法为每一阶段建立精确恢复点，也会绕开当前 CLI 已验证的“逐依赖查询授权 → 用户明确选策略 → 签约 → 写版本稿”链路。

CLI 采用更可靠的两阶段模型：

1. 通过已有 `Resource.create` **逐项**创建全部资源壳，立即核验并写各自的 `N.json` 身份；
2. 再按资源逐项调用现有产物准备、表单、依赖签约和版本提交能力。

这仍满足“先批量创建壳、再逐个处理依赖与发行”，同时支持混合资源类型、明确的部分成功报告和安全恢复。CLI 不调用 `Resource.createBatch`，也不把 `batchSignContracts` 塞进 `createVersion`。

## 3. 输入协议 v1

输入文件名建议为 `release/release-batch.json`。所有路径均以该命令的 `--cwd`（默认当前目录）为根解析，不能逃出工程根；不以 JSON 文件所在目录改变路径含义。

```json
{
  "schemaVersion": 1,
  "kind": "freelog-resource-release-batch",
  "resources": [
    {
      "key": "lesson-01",
      "operation": "create",
      "resource": {
        "name": "course-video-01",
        "title": "第一课：准备工作",
        "typeCode": "RT006003"
      },
      "artifact": { "path": "videos/01.mp4" },
      "version": {
        "description": "第一课初次发行",
        "systemInputs": [],
        "attributes": [
          { "key": "author", "name": "作者", "value": "张三", "remark": "" }
        ],
        "options": [],
        "dependencies": [
          {
            "resource": "name:publisher/shared-material",
            "versionRange": "^1.0.0",
            "policyId": "policy-id-if-auth-is-missing"
          }
        ]
      },
      "listing": {
        "intro": "课程入门视频",
        "tags": ["课程", "入门"],
        "cover": "covers/lesson-01.png"
      },
      "policies": [],
      "publishOnline": false
    }
  ]
}
```

顶层只允许 `schemaVersion`、`kind` 和 `resources`。未知字段、重复 JSON 键、错误类型、未知 schema 版本和 `null` 的含糊语义一律拒绝，不能静默忽略 AI 拼错的字段。

### 3.1 每项资源

| 字段 | 规则 |
|---|---|
| `key` | 批内稳定键，仅定位报告与恢复；1–80 字符且唯一，不能作为平台身份。 |
| `operation` | V1 固定 `create`。 |
| `resource.name` | 授权标识短段，沿用 `create` 的规范化、1–60 字符和查重规则；输入完整 `username/name` 失败。规范化后批内重复也失败。 |
| `resource.title` | `trim()` 后 1–100 字符；可变展示值，不参与查重或恢复匹配。 |
| `resource.typeCode` | 当前环境启用、`subjectType=1` 的最终叶子；每项可不同，不能按类型名称猜 code。 |
| `artifact.path` | 工程根下的明确单个发行物。普通资源必须是文件；主题/插件按该类型既有规则接受构建目录或预制 zip，并复用当前压缩和产物锚点校验。解析后路径（含符号链接/junction 的真实路径）不得逃出工程根；绝不扫描文件夹“猜”出多份资源。 |
| `version` | 首版表单，绝不填写版本号或 SHA；CLI 固定 `1.0.0`，文件 SHA、文件名和分析结果必须由 CLI 计算。 |
| `listing` | 可省略；出现的字段在首版成功后写入。`intro:""` 和 `tags:[]` 是显式空值；封面必须是工程根下的图片路径，沿用单资源封面校验和“CLI 不裁剪”的提示。 |
| `policies` | 新增自身策略意图，见 §3.4；不是现有策略全量替换。 |
| `publishOnline` | 布尔值，默认 `false`。`false` 完成首版及输入中声明的 listing/策略后停止；`true` 再执行独立上架。该字段不改变资源的其它状态。 |

### 3.2 版本表单

`systemInputs`、`attributes`、`options` 和 `dependencies` 复用单资源首版表单的实际字段约束，不能另造一套批量语义。

```json
{
  "systemInputs": [{ "key": "language", "value": "zh-CN" }],
  "attributes": [{ "key": "author", "name": "作者", "value": "张三", "remark": "" }],
  "options": [
    { "key": "subtitle", "name": "字幕", "mode": "input", "defaultValue": "", "remark": "" },
    { "key": "quality", "name": "清晰度", "mode": "select", "items": ["高清", "标清"], "remark": "" }
  ],
  "dependencies": []
}
```

- `systemInputs` 映射 `inputAttrs`；只有文件/类型分析实际给出的附加字段才可填写，不能伪造 SHA、大小等计算事实。
- `attributes` 映射 `readonlyText` 的 `customPropertyDescriptors`；`key`、名称、长度、数量和重复约束完全复用字段级校验。
- `options.mode:"input"` 映射 `editableText`；`mode:"select"` 映射 `select`，`items` 至少一项且第一项就是默认值。可选配置是否允许由实时资源类型能力决定，不能因资源是主题、图片或视频就硬编码推断。
- 所有数组出现即为这次首版的完整声明；省略等同空数组。类型/文件分析后来要求的字段未填写时，任务在该资源停止并指出 JSON Pointer，不进入逐字段 TTY 补问。

### 3.3 依赖

每项依赖是：

```json
{ "resource": "id:<resourceId> 或 name:<loginName/name>", "versionRange": "^1.0.0", "policyId": "<可选>" }
```

执行时，对每项资源逐条复用单资源依赖链：目标必须是可用普通单资源、有可命中范围的已发版本且无基础上抛；再循环检查、`Resource.batchAuth` 查询、必要时列出对方全部启用策略并调用 `Contract.batchCreateContracts`。

- 已有授权时直接写入版本稿，不签约；提供的 `policyId` 不生效也不替代授权判定。
- 未授权时，交互可选择一条策略；`--yes` 或非交互必须由 JSON 提供 `policyId`，并在实时策略列表中精确命中，绝不按第一条自动选。
- 签约成功后直接写入稿并继续，不复查 `isAuth`；付费策略仍遵循现有边界：签约可继续，支付留在浏览器端，CLI 不伪造付款完成。
- 每次签约的 `licenseeId` 是本批当前正在发行的资源壳 ID，绝不能错用批次键、下一个资源或合集 ID。签约记录只写任务恢复状态，不写进版本依赖字段。
- 同批资源不能互相作为 V1 依赖：在批次开始时都没有可被验证的已发版本。发现 `id:`/`name:` 指向本批任一资源，预检失败，而不是依赖数组顺序赌成功。

### 3.4 自身策略与上架目标

策略仍是“追加”语义：省略或 `[]` 不删除、不停用资源已有策略；每个策略 `key` 必须在批内唯一，用它与任务中平台返回的策略 ID 关联，不能用可重复名称判定重试是否完成。`name`、`sourceFile`、文本编译和启用状态均复用单资源策略的实时校验；策略源文件同样必须经真实路径校验后位于工程根内。

在策略后端模板/DSL 契约尚在调试期间，V1 协议只允许已核验的本地策略文本文件：

```json
{ "key": "public", "name": "公开策略", "sourceFile": "policies/public.txt", "enabled": true }
```

`sourceFile` 必须是工程根内文件；策略文本格式、编译和平台错误仍由现有策略实现处理。模板 ID、模板参数、收费策略等未来可在策略契约定稿后新增一个显式 `source` 联合类型，不能现在凭空固化一套错误的模板字段。

`publishOnline:true` 要求该项最终存在至少一条启用的自身策略；未声明策略且线上也无法证明有可用启用策略时，该项在上架前失败，不能自动创建“默认策略”。策略后端未恢复前，批次仍可安全完成到 `publishOnline:false`。

## 4. 执行与失败边界

### 4.1 全批预检

先读取并规范化全量 JSON，固定输入顺序和每项 `key`，并取得批次互斥锁。任何写入前集中检查：真实路径、文件存在、名称规范化冲突、标题和 listing、静态表单字段、类型叶子及能力、依赖目标与范围、显式策略 ID、批内互相依赖、账号/环境和线上名称占用。循环依赖检查需要当前资源壳 ID，故在阶段 B、签约前逐项执行；它不能被伪装成阶段 A 已完成的离线检查。

文件上传后才能知道的分析字段会被报告为“待运行时分析”，不能被 `check` 伪装成已通过。预检中出现任一可判定错误时，**不创建任何壳**。

### 4.2 阶段 A：逐项建壳

预检通过后，按输入顺序逐项调用现有 `Resource.create` 逻辑：再次实时查重并确认类型仍是可用的 `subjectType=1` 叶子 → `POST /v2/resources` → 校验返回 `resourceId` → 原子写入对应 `N.json`。这是“批量创建壳”阶段，不上传文件、不签依赖、不创建版本。

明确的单项业务失败（例如授权标识被抢占）记录该项失败后可继续其它独立项；认证失效、环境异常、本地身份写入损坏或任一 POST 结果未知则停止整个批次。绝不以名称、标题或文件 SHA 猜测一个未知 create 是否成功。

### 4.3 阶段 B：逐资源发行

所有已成功建壳的项目按输入顺序、一次一项执行：

```text
确认资源壳仍属于当前账号且未冻结
  → 按类型准备产物、上传、分析并固定本次 SHA
  → 以分析结果校验系统附加字段、属性、可选配置
  → 逐条检查依赖；必要时显式签约
  → 原子写入该资源自己的 N.version.json
  → POST createVersion(version: 1.0.0)
  → 读回确认版本
  → 写入声明的 listing
  → 追加声明的策略
  → publishOnline=true 时执行独立上架门禁
```

不并行提交版本、签约、策略或上架：当前工程未决远端写入是全局安全门，且每个 `N.version.json` 必须始终只属于一份资源。已通过建壳的其它项目不是失败资源的回滚对象；不删除平台壳、不清除已成功签约、不自动下架。

版本提交、策略追加和上架出现明确业务失败时，保存该项已确认阶段及工作稿，继续不依赖它的后续资源；出现网络超时/断连等未知写结果，立即停止全批并进入恢复，不带着未知事实继续处理下一项。

## 5. 运行记录、恢复和输出

执行开始即在 `.freelog/runs/<runId>/` 写入只读意图快照：规范化后的 JSON、账号、环境、每项对应的 `N.json`、路径和产物指纹、资源 ID、依赖选择、请求阶段与平台回执摘要。它只服务于这一次工作流恢复，不是版本管理缓存：资源身份仍在不可变的 `N.json`，未提交表单仍在各自的 `N.version.json`。

每个远端写入按 `prepared → sending → confirmed | rejected | unknown` 持久化。平台成功但本地写确认失败也算 `unknown`，不能因为进程重启就再次 POST。

`resume <runId>` 的规则：

| 已知状态 | 接续动作 |
|---|---|
| 壳已确认、首版未提交 | 核验同一 ID、owner、类型后继续准备/签约/提交；不重新 create。 |
| 版本已确认、listing/策略/上架未完成 | 固定 `1.0.0` 和已确认 SHA，只执行剩余步骤。 |
| 某写入未知 | 先只读查询证明结果；不能证明则保持停止，不自动重发。 |
| 输入或产物变了 | 不用旧任务覆盖新意图。已建壳的项不能以 `operation:create` 新开 run：恢复原始输入/产物后继续原 run，或退出批量流程并用 `bind` 与单资源版本命令显式接续；版本内容已确认则必须另走新版本流程。 |
| 项目已完整成功 | 只验证事实并报告，不重复建壳、签约、加策略或上架。 |

终端与 `--json` 报告必须按 `key` 列出：资源 ID/完整标识、完成阶段、是否上架、失败/未知原因、下一条安全命令。成功不能掩盖失败；“已建壳”不能表述为“已发行”；“已签约”不能表述为“已支付”或“已授权生效”。

## 6. 验收

1. 人和 AI 能仅依照 Schema、`spec` 输出和错误 JSON Pointer 填写协议；未知字段、重复键和含糊 null 不会被执行器吞掉。
2. 混合普通资源类型、主题/插件的类型特定发行物均可在同一清单中准备；每项仍只发行一个单资源。
3. 任意预检错误不会创建线上壳；名称、类型、文件和同批依赖冲突均能集中报告。
4. 创建阶段全部使用单资源 `Resource.create`；版本阶段全部使用当前 `createVersion` 及依赖签约链，不调用 `Resource.createBatch` 或 `batchSignContracts` 版本提交捷径。
5. 未授权依赖在自动化模式缺少精确 `policyId` 时失败；付费签约不触发支付流程、不假装付款完成。
6. 任一请求结果未知后停止全批，`resume` 只核验和接续，不重发未知写入；每个成功资源保留独立身份与可追溯报告。
7. 任何输入、报告、命令和实现中均不包含合集添加、合集发布或合集隐式回调。

## 7. 实施与 dev 验收矩阵

批量发行的测试不能只验证“建壳成功”。实现后至少要覆盖以下闭环，并把每项的资源 ID、运行记录与读回结果写进 dev 测试报告：

| 场景 | 必须证明的结果 |
|---|---|
| 预检 | 非法字段、重复键、越界真实路径、重复名称、非叶子类型、批内依赖均在零远端写入时失败。 |
| 普通文件与主题/插件 | 一份普通单文件和一份主题/插件目录/zip 都正确使用各自的产物准备规则，每项只创建一份单资源。 |
| 完整首版表单 | 系统属性、属性、可选配置、描述、依赖、封面、标签均进入各自资源的首版或 listing，且不互相串写。 |

| 策略与上架 | 策略追加成功后才允许 `publishOnline:true`；缺策略/策略停用时不上架。策略后端不可用时可安全停在 `publishOnline:false`。 |
| 部分成功与恢复 | 某项明确失败不回滚已确认项；创建/版本/策略写入未知时整批停止，`resume` 只读回并且绝不重复未知 POST。 |
| 输入变更 | 已建壳后更改 JSON 或产物不能被新 run 覆盖；用户只能恢复原 run 或明确切回单资源流程。 |
