# 依赖

对照业务：发行时的依赖授权。终端**不嵌微前端**，把「查资源 → 选版本范围 → 循环检查 → 签约拿到授权」拆成一步步问。只在 `create-version` / `update-version` 菜单 5 / 6。

| 场景 | 能做什么 |
|------|----------|
| 发行版本菜单 5 / 6 | 空表上加、改范围、删；加的时候当场签，且必须拿到授权 |
| 更新版本菜单 5 / 6 | 先回显上一版依赖，再加、改范围、删 |
| 已发版 | **不能**改树。看树 / 补签见 [管理/04](../管理/04-依赖及其授权.md) |

没有独立的 `dep add`。本期**不做支付、不解决上抛**。只接受「对**这一条依赖本身**签一条免费策略就能拿到授权」（合约 `authStatus` 为 1 或 2）。

不问「是否上抛」、不改 `baseUpcastResources`、不替对方签基础上抛。对方有 `baseUpcastResources`：不加，「对方存在基础上抛，本期不支持。」  
签完仍是 128 / 未授权：这条不加，「签约后无法获得授权，本期不支持。」自己的资源当依赖 **也要签**。

提交时：有依赖但未拿到授权 → 不能 `createVersion`，「依赖中存在未获取授权的资源」。`baseUpcastResources` 传 `[]`。

业务事实与微前端接口：[P0-D-依赖管理与签约](../../../../业务梳理/依赖与签约/P0-D-依赖管理与签约.md)。

### 创建版本 vs 更新版本

同一套菜单 5 / 6，起步不同。

| | `create-version` | `update-version` |
|--|------------------|------------------|
| 工作稿起步 | 空表 | 回显源的 `dependencies`。上抛名单**不回显、不写入**（工作稿 `baseUpcastResources` 恒 `[]`） |
| 已有合约 | 几乎没有 | 合约挂在本资源上，上一版签过的通常还在，§1.5 会跳过 |
| 回显后立刻做什么 | — | 见 **§4**（核授权；对方有基础上抛则当不支持；排除项当没有） |
| `licenseeVersion` | 平台若要：`1.0.0` | 平台若要：即将发行的新号。`batchSign` 体没有这个字段就不要造 |
| `--yes` | 稿里未授权的按 §1.5 自动签（仅一条免费才敢） | 回显带来的未授权同样自动签，规则相同 |

对照微前端（`dependencies-declarator` + 嵌套的 `authorization-processor`），**不是** Console 壳自己的表单：

```
添加依赖
  → 抽屉：资源市场 / 我的 / 收藏 / 合集 / 存储
  → 点一条（排除自己；未发行/冻结/下架不能点）
  → 打开授权处理器（默认 versionRange = ^latest）
      查合约、授权链、循环（只传这一条）
      签策略 / 上抛 / 对方的基础上抛也要处理
  → 提交后才写入依赖列表
  → 列表上可改范围（semver.validRange，且能命中对方某一已发号）
```

循环：声明器加载已有列表、处理器打开某条时，都会 `POST .../cycleDependencyCheck`。体往往只有**正在看的这一条**。`data===false` 标 `error=cycle`，不能当正常依赖用。  
CLI 传「工作稿已有 + 新的」更严（同一次会话加多条也能查到）。接口失败不要继续加。

微前端「授权完成」= 未上抛的依赖及其上抛都有 `status===0` 的合约（128 也算；上抛的本层可以不签）。本期 CLI：**不处理上抛**；必须对依赖本身签到 `authStatus` 1 或 2。  
合集、存储对象当依赖：微前端抽屉有，本期 CLI **不加**。

---

## 1. 发行：添加（菜单 5）

一次只加一条。做完写盘，回菜单。想再加再选 5。

```
1 问目标
  → 2 定位到恰好一条普通资源
  → 3 选 versionRange
  → 4 循环依赖检查（不过不能加）
  → 5 对方若有基础上抛：不加
  → 6 签约：已有授权则跳过；否则签免费策略，必须拿到授权
  → 7 写入工作稿（不上抛）
```

中途失败：这条不加，已问的作废，回菜单。不要留下半条依赖。

### 1.1 问目标

「依赖的资源：resourceId 或 username/name」。

| 输入 | |
|------|--|
| 空 | 重新问 |
| 含 `/` | 当 `username/name`（短标识段仍按平台规范化理解） |
| 否则 | 当 `resourceId` |

不能填自己（本资源 `resourceId` 或自己的 `username/name`）：「不能依赖自己」。

### 1.2 定位

`Resource.info`（`GET /v2/resources/{resourceIdOrName}`），CLI 传未预编码的 id 或 `username/name`。

| 结果 | |
|------|--|
| 没有 / 平台错误 | 「找不到该资源」，回菜单 |
| `subjectType!==1` | 不加（合集、其它标的本期不当依赖） |
| 对方没有 `latestVersion` | 不加，「对方还没有发行版本」 |
| 对方未发行 / 冻结 / 下架（`status` 为 `0` / `2` / `4`，或 `(status&2)===2`） | 不加。文案：「对方未发行」/「对方已冻结」/「对方已下架」。与微前端抽屉 `0/2/4` 点不了一致 |
| 对方 `baseUpcastResources` 非空 | 不加，「对方存在基础上抛，本期不支持。」不要去签那些上抛、也不问是否上抛 |
| 恰好一条普通资源（通常 `status===1`，且无基础上抛） | 打印标题、`username/name`、latest，继续 |

### 1.3 版本范围

`Resource.getVersionListByResourceID`（`GET /v2/resources/{对方id}/versions`）。打印对方已发版（新的在前）。

问「版本范围」。hint：须是 semver 可解析范围，例如 `*`、`^1.2.0`、`>=1.0.0`。  
默认建议：`^` + 对方 `latestVersion`（用户能整段改掉）。

非法：重新问。不要默默改成 `*`。  
还要能命中对方**当前某一已发号**（`semver.maxSatisfying(对方版本列表, range)` 非空）。命中不到：重新问，「这个范围对不上对方已发行的版本」。和微前端改范围确认时一样。

同一依赖（同一 `resourceId`）工作稿里已有：走「改范围」而不是再加一条。本步应提示「已在依赖中，将改范围」或让用户去菜单 6。

### 1.4 循环依赖

和微前端、旧脚手架同一条：`Resource.cycleDependencyCheck`（`POST /v2/resources/{本资源id}/versions/cycleDependencyCheck`）。  
`本资源id` = 被授权方（正在发行的这个资源），不要传对方 id。  
**在选完范围之后、签约之前**做。不要像旧代码那样接口失败还继续加。

体：`dependencies` = 工作稿已有的（去掉将要覆盖的同一 `resourceId`）+ 正要加的这一条 `{ resourceId, versionRange }`。  
微前端常只传正在加的那一条；CLI 传全集。

| 平台 | 行为 |
|------|------|
| `data === true` / 通过 | 继续 |
| `data === false` 或文案判循环 | 不加。「添加此依赖会导致循环依赖，无法添加。」 |
| `ret`/`errCode` 失败 | 不加。打印 `msg`。不要当「检查失败仍可加」 |

改范围（菜单 6）也要再跑本节。

### 1.5 签约（必须拿到授权）

不做支付。不列待执行合约、不问「是否立即支付」。

**已签**：`Contract.contracts`（`GET /v2/contracts`）`licenseeId` = 本资源，`subjectIds` = 对方，`identityType=1`。  
有一条 `status===0` 且 `authStatus` 为 **1 或 2**（正式 / 测试授权）：本步通过，不必再签。  
只有 128 或没有合约：要新签。

拉对方策略：`Resource.info`（对方 id，`isLoadPolicyInfo=1`）。  
只保留：`status===1` 且策略文本 **不含** `TransactionEvent`（大小写不敏感）。

| 情况 | |
|------|--|
| 已有授权合约（1 或 2） | 通过，不签 |
| 一条免费 | 默认用它，TTY 仍展示名称让用户确认 |
| 多条免费 | `select` 选一条 |
| 零条 / 只有付费 | **不加**。「没有可直接获得授权的策略，本期不支持。」 |
| 用户取消 | 不加 |

确认后 `Contract.batchCreateContracts`（`POST /v2/contracts/batchSign`）：

| 字段 | 值 |
|------|-----|
| `subjectType` | `1` |
| `licenseeId` | **本资源** `resourceId` |
| `licenseeIdentityType` | `1` |
| `subjects` | `[{ subjectId: 对方 resourceId, policyId }]` |

若平台还要乙方版本：发行版本用 `1.0.0`；更新版本用即将发行的新号（尚未 POST 也可以）。没有这个字段就不要造。

签约失败：不加。  
签完看返回 / 再查合约：`authStatus` 必须是 **1 或 2**。是 **128** 或仍未授权：「签约后无法获得授权，本期不支持。」**不加**。不要引导去支付、不要「先加进稿稍后再付」。

`authExcludedItems`：本期菜单 5 **不写排除项**（排除常用来绕过签不了的）。吃不准就当不支持。

### 1.6 写盘

不问上抛。不写上抛名单。

`N.version.json`：

```
dependencies: [{ resourceId, versionRange }]
baseUpcastResources: []
authExcludedItems: []
```

不写合约 id 进 `N.json`。回菜单。快照上这条标「已签」（`authStatus` 1 或 2）。未拿到授权的不要出现在工作稿里。

## 2. 发行：管理（菜单 6）

列出工作稿依赖：`username/name`（没有就 id）、`versionRange`、是否已签。不要打「是否上抛」。

选一条，再选：

### 2.1 删除

确认后从 `dependencies` 去掉。  
**不**调解约 API（平台本步没有必须解约）。写盘，回菜单。

### 2.2 改范围

问新 `versionRange`（规则同 §1.3）。再跑 §1.4。循环则不改。需要则按 §1.5 再确认授权（已有 1/2 则不必再签）。对方现有基础上抛：不改，「对方存在基础上抛，本期不支持。」写盘只在改成功时。

没有「改上抛」。没有「改成另一个 resourceId」：先删再加。

---

## 3. 提交时带什么（发行 / 更新版本共用）

提交前**再核一遍**（回显带来的、刚加的都算）。不要只信菜单 5 当时的结果：对方可能刚冻结、策略刚下线、后来出现了基础上抛。

1. 工作稿每条依赖再 `Resource.info`。现已是 `0/2/4` 或不存在：失败，点名这条，让人去菜单 6 删。**不要自动删**。
2. 对方现 `baseUpcastResources` 非空：失败，「对方存在基础上抛，本期不支持。」点名。不自动删、不去签那些上抛。
3. 每一条依赖**本身**必须已有 `authStatus` 1 或 2。没有：TTY 按 §1.5 补签；`--yes` 只有**一条**免费才敢自动选。多条免费、没有免费、签完不是 1/2：失败，「签约后无法获得授权，本期不支持。」
4. 工作稿若带回显来的 `authExcludedItems`：**当没有**。提交仍传 `[]`。

`createVersion`（首版和新号同一张表）：

| 字段 | |
|------|--|
| `dependencies` | 工作稿全部 `{ resourceId, versionRange }` |
| `baseUpcastResources` | **`[]`**。不要把壳上或上一版的上抛带上去 |
| `batchSignContracts` | **不带**。签约在 §1.5 / 提交前补签已经完成 |
| `authExcludedItems` | 传 `[]` |

`--yes`：不进会话。提交前按上面 1–4 做。不要自动付费。

---

## 4. 更新版本：回显之后

只在 `update-version` 落完回显稿之后做（发行版本没有上一版，跳过本节）。编排见 [更新版本](../更新版本/01-更新版本.md) §1 / §5。

回显写入：只带回显源的 `dependencies`。`baseUpcastResources` 写 `[]`（不要从壳 `info.baseUpcastResources` 抄过来）。上一版在 Console 勾过的上抛，新号上 CLI **清掉**。

进菜单或 `--yes` 提交前：

| 回显带来的情况 | |
|----------------|--|
| 合约还在，1 或 2，且对方无基础上抛 | 快照标「已签」。不必重签 |
| 只有 128 / 没有合约 / 合约已终止 | 按 §1.5。签不了：快照标未签；提交失败（TTY 可先去菜单 6 删） |
| 对方现已 0/2/4 | **不自动从稿里删**。快照标状态；提交按 §3 失败并点名 |
| 对方有基础上抛（上一版就有，或后来多出来） | 当不支持。不自动删；提交按 §3 失败并点名 |
| 稿里有排除项 | 当没有，见 §3 |
| 范围对不上对方当前已发号 | 不自动改范围。提交不因「对不上」单失败（平台收树）；人改范围时按 §1.3 拦 |

不要在回显时对每条再跑一遍「不能依赖自己 / 合集」门禁而删树。自己的资源当依赖：合约没有则仍要签。

---

## 5. 已发版

已发版不能改依赖树。`version description` 只改描述，不要出现菜单 5 / 6。  
看树、补签：`dep list` / `dep auth`，见 [管理/04](../管理/04-依赖及其授权.md)。要改树走 [更新版本](../更新版本/01-更新版本.md)。
