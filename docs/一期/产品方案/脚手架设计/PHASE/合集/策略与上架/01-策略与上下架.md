## 1. 合集适配器

合集命令只负责解析/校验 `subjectType=4` 的目标；可从本地合集身份或显式选择器取得，但标题绝不用于选择。随后与单资源一样调用 `Resource.info`、`Policy.policyTemplates`、`Policy.policyReCompile`、`Policy.policyTranslation` 与 `Resource.update`。

合集不是 presentable，不能使用 `resourceTypeCodes4Presentable`。当前 Console 合集侧栏没有把 `resourceTypeCode` 传给模板列表，导致其请求空类型；这是现代码缺口，不复制到 CLI。当前两种主体均使用 `{}` 取得完整模板集，并在每一项返回的 `compileType` 字段上区分单资源 `normal` 与合集 `collection`；CLI 必须在响应后筛掉另一主体的模板。后续类型缩小查询的正式契约确认前，CLI 不猜测或透传筛选参数。

创建策略与单资源 payload 完全一致：`Resource.update({resourceId, addPolicies:[{policyName, policyText: encodeURIComponent(compiledText), status:1}]})`。编译类型只来自模板响应，不能按合集写死。

## 2. 上架与下架

`collection online` 是独立状态写入：

1. 重读本人、未冻结的合集；已上架幂等成功。
2. 无已发布合集快照（`latestVersion` 为空）时拒绝，指向 `collection publish`；不自动发布。
3. 没有启用的**合集自身**策略时拒绝，指向 `collection policy template apply`；不能把单品策略当作满足条件。
4. 确认后只写 `Resource.update({resourceId,status:1})`，再读回 `status:1`。

`collection offline` 只写状态 4 并读回。策略创建完成后只提示 `collection online`，绝不自动上架。

合集目录发布和上架是两层事实：`collection publish` 必须从已发布目录接口读回单品；上架还必须读回 `status:1`。目录里有单品而合集 `status:4` 时，不能称为线上可见合集。

## 3. 验收

除公共策略矩阵外，合集必须额外验证：错误主体拒绝、合集模板请求不走 presentable 参数、无已发布快照/无启用合集策略时 online 拒绝、已发布目录 + 启用合集策略时 online 读回成功。已有非交互模板创建与 off/on 的 dev 证据不替代真实 TTY、datetime 或 online 正向测试；缺少对应样本时只将该分支标 `BLOCKED`，不否定已通过的分支。
