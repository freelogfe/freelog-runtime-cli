# 合集功能拓扑与证据驱动测试门禁

状态：**实施与 dev 验收进行中；策略模板非交互主链已于 2026-09-20 在 dev 验证。** 本文仍是功能点、证据与剩余门禁的索引；旧的 B-05 不能再被解释为“整个策略功能尚未实现”。

本文把合集的用户能力拆成有向依赖图，并为每个节点和每条写入边定义可证明的测试事实。它不是“跑过几条 happy path 就算完成”的清单：只有所有声明功能点均有来源证据、自动化断言和真实 dev 读回证据，才可把合集全流程称为通过。

“100%”在本文中有严格含义：**100% 已声明的节点、边、失败分支和不变量均被逐项覆盖并有证据**。没有任何测试方法能证明“绝对不存在所有未知问题”；因此未能从 tools-lib、Console 可执行代码或 dev 响应确定的契约一律标为 `BLOCKED`，不得用猜测实现后再补测试。

## 1. 证据等级与放行规则

| 等级 | 含义 | 可用于什么 | 不可用于什么 |
|---|---|---|---|
| E1 | 正式设计与可信业务梳理一致 | 列功能边界、生成测试用例 | 推断请求 payload |
| E2 | 当前 `packages/tools-lib` 存在 Node 端请求包装 | 锁定方法、URL、已声明 DTO 字段 | 断言服务端实际响应或未声明字段 |
| E3 | Console 当前可执行代码确认调用/映射 | 核对 UI 行为、payload 映射与分支 | 覆盖 Console 自身未处理的异常 |
| E4 | CLI 单元/集成测试断言 | 证明本地实现的确定性行为 | 证明真实平台行为 |
| E5 | dev 真实请求和完整读回 | 证明当前环境端到端契约 | 推广到 prod 或未测资源类型 |

一个**已实现**功能点达到可交付最低门槛必须同时有 E1、E2、E4、E5；若涉及 Console 专有映射，还必须有 E3。纯只读诊断可省 E5，但仍需在 dev 至少验证一次真实响应形状。任何远端写入若不能给出唯一的读回判定，则不能进入 dev 写入阶段。

## 2. 用户能力拓扑

```text
登录态 + 环境
   │
   ├─ 解析/重读本人合集目标 ───────────────┐
   │                                      │
   ├─ 创建合集壳 / 接入已有合集            │
   │                                      ▼
   │                              合集当前事实
   │                       (owner / subjectType / status / RSS)
   │                                      │
   │          ┌───────────────────────────┼─────────────────────────┐
   │          ▼                           ▼                         ▼
   │   服务端目录草稿                 listing / 收录规则         合集表单操作草稿
   │   (单品、排序、授权)                                        (属性/配置/描述/展示/依赖)
   │          │                           │                         │
   │          │                           └──────────┐              │
   │          │                                      │              │
   │          └─────── 目录差异 / 自动模式 ─────────┼──────────────┤
   │                                                 ▼              ▼
   │                                      collection publish（唯一合并点）
   │                                                 │
   │                                    已发布合集快照 + 已发布目录
   │                                                 │
   └──────────────────── 合集自身策略 ──────────────┼──────────────┘
                                                     ▼
                                          online / offline（独立状态）
```

### 2.1 不可跨越的边界

1. 单品目录草稿、listing、收录规则、合集表单、策略、上下架是不同的远端事实；一个命令不得顺带写另一事实。
2. `collection publish` 是唯一把完整表单与可选目录草稿合并为已发布合集快照的写点；它不创建单资源版本，也不隐式上架。
3. 单品上游合同映射、合集直接依赖声明和合集自身策略是不同操作；可以复用身份/目标解析，但不能共用存储字段或发布接口。CLI 没有依赖签约交互。
4. `.freelog/N.json` 只保存主体身份；`subject:"collection"` 不含 `filePath`。表单操作草稿和发布 intent 是可回收事务数据，不能变成第二份线上目录事实。
5. 标题是可变、可重复的展示值，永远不能用作目标、单品、策略或恢复匹配键。

## 8. 通过判定与报告格式

### 8.1 节点状态

每个 C-ID 只能取以下状态之一：

- `NOT_STARTED`：没有代码或测试；
- `DESIGN_READY`：E1/E2（需要时 E3）齐全，尚未实现；
- `LOCAL_PASS`：E4 通过，尚未 dev；
- `DEV_PASS`：E1~E5 齐全；
- `BLOCKED`：缺少 B-ID 对应外部契约；
- `DECISION_REQUIRED`：产品边界尚未定案，不能用实现猜测代替决定；
- `OUT_OF_SCOPE`：一期明确不提供，但已有目标必须有保护性负向测试；
- `FAIL`：存在可重现的设计、实现或平台偏差。

“当前合集全流程通过”唯一条件：C-01～C-24 中所有已纳入一期的节点均为 `DEV_PASS`，或用户明确从一期范围删除某一节点并同步本表、正式设计和交接文档；C-25 维持 `OUT_OF_SCOPE` 并完成 T-52 的保护性测试。RSS 重新排期时，必须恢复其 C/T/B 节点并另行完成 dev 证据，不能沿用当前“合集全流程通过”的表述。任何 `BLOCKED`、`DECISION_REQUIRED`、`NOT_STARTED`、`LOCAL_PASS` 或 `FAIL` 都不能写为当前范围的全流程通过。

### 8.4 安装包可控中断与恢复装置

T-42/43的异常恢复必须另外通过实际安装包与跨进程重启验证，不能用正常发布链或域层注入单测替代。故障仅在隔离本机平台装置注入，不向真实dev/prod故意中断、重发或制造支付/签约。CLI产品不新增测试入口；固定preload只能把SDK原始请求中的固定dev目标和白名单接口转到本机端口，其它方法/路径及外网连接拒绝并留痕。独立loader在加载前替换原生keyring，固定合成身份之外的读写均拒绝；不读取私有账号文件、未知宿主条目或用户工程。

装置先自证：合成凭据只读、原生模块不加载，固定HTTPS→本机HTTP路径可达，非白名单域名/路径/方法及其它网络传输拒绝，缺控制文件/损坏记录失败关闭。prepared/sending终止只发生在同次intent原子rename已完成后；清理故障仅拒绝精确intent的unlink，不能扩大到稿/用户文件。每个子进程有ready/finished或精确fault记录；缺记录、意外signal/timeout不算预期故障。Node实验loader的告警抑制只限装置进程，CLI stderr仍须完整核对。

生产者必须绑定同候选实际installed bin、run和包摘要，禁止workspace dist回退；恢复观察的实际起止必须位于该次聚合报告起止内，不允许把旧阶段改外层run/摘要后当新证据。原始观察由源码固定的语义判定重核后才能登记叶子PASS；无关文件保留使用原始字节比较，不以UTF-8解码后的文本相同代替。装置自测只证明测试设施，不是产品验收、平台真实中断或完整管理矩阵通过。未完成接入/执行仍保留NOT_TESTED及父gap；失败/未决现场不得自动清理。

本项登记为`COLLECTION.RECOVERY.INSTALLED_MATRIX`，生产者固定`verify-collection-recovery.mjs`，对应C09.F01～F12的21种固定场景；每种包含publish、重复publish、默认resume、显式apply四个实际子进程，保留阶段原始文件与完整字节，不接受调用方自选场景。每个场景分别重核请求、完整表单/目录、intent、当前稿、无关本地主本及默认只读；预期故障只允许固定故障点/退出86，任意signal/timeout仍失败。SDK非零errCode的明确拒绝必须通过原包SDK链，不用直接返回失败对象代替。

F12还须有完整createProgram入口的回归，覆盖全局preAction到领域动作的组合，而非只解析独立publish子命令：默认resume有/无yes及apply缺yes时均保持完整事务字节；合法apply继续由领域锁前滚，普通publish和其它祖先路径同名resume不能获得恢复豁免。安装包某次失败在源码修复后仍保持原FAIL，不能把定向绿写回原报告。
