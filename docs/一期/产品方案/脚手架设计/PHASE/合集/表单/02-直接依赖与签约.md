# 合集直接依赖与签约

状态：本轮定稿设计，尚未实现。支付后的平台授权能力仍由浏览器完成；这不改变“能签约即记录依赖”的当前产品边界。

## 审阅重点

先区分三件事：合集自己声明的依赖、单品带来的上游授权、以及单资源版本依赖。它们可以共用选择器和签约交互，但绝不能共用草稿字段或发布接口。签约成功即可继续；不能读取精确授权排除状态时，发布必须停下而不是写空数组。

## 1. 三种“依赖/授权”先分清

| 关系 | 何时处理 | 被授权方 | 最终写入 |
|---|---|---|---|
| 合集直接依赖 | `collection dep add/rm/range` | 合集自身 | 表单 `dependencies`，发布时 `updateCollection.dependencies` |
| 单品上游授权 | `collection item add` | 合集自身 | 服务端目录草稿单品授权字段 |
| 单资源版本依赖 | `version dep …` | 单资源版本 | 单资源工作稿 / `createVersion` |

三者都可复用资源选择、版本范围校验、策略选择和裸签约的通用组件，但不能共用草稿字段、批量授权结果或发布接口。特别是“单品来自线上”不代表它是合集的直接依赖。

## 2. 命令和操作草稿

```text
collection dep list [--resource <collection>]
collection dep add <id:…|name:…> [--range <semver-range>] [--policy <policy-id>] [--yes]
collection dep range <id:…|name:…> --range <semver-range>
collection dep rm <id:…|name:…>
```

所有命令先解析当前账号可维护的 `subjectType=4` 合集，再读取/创建[合集表单](./01-属性-可选配置与展示.md)操作草稿。`add/range/rm` 仅修改其中的 `dependencies`，不调用 `updateCollection`；发布才提交完整依赖清单。未给 `--range` 时默认 `^<目标最新版本>`，并沿用单资源依赖的 `semver.validRange` 与 `maxSatisfying` 校验。CLI 比 Console 当前 `resourceDepAuth` 页面更显式地暴露范围，但不改变最终 `{resourceId,versionRange}` 的平台字段。

## 3. 写入前的真实校验与签约

每次 `dep add` 按此顺序执行，列表缓存不能替代任一步：

1. 重读合集并确认当前账号、环境、`subjectType=4`、非 RSS、非冻结且可维护；目标必须是线上 `subjectType=1`，有已发布版本，且不是合集自身。
2. 校验版本范围命中目标已发布版本；将“现有表单依赖 + 新候选”交给 `Resource.cycleDependencyCheck({resourceId: collectionId,…})`。平台说会成环或返回未知，均不写草稿。
3. 以**合集 ID**为 `licenseeId` 查询目标授权状态：先 `Contract.batchContracts({subjectIds, licenseeId:collectionId, subjectType:1, licenseeIdentityType:1})` 读取现有合约；不得把无 `licenseeId` 的 `Resource.batchAuth`（它代表当前登录身份）当成合集授权结果。
4. 已存在可用授权合约时写草稿；否则只列目标当前启用且可签的策略，非交互需 `--policy`，交互必须让用户选择，绝不取“第一条”。
5. 经确认调用 `Contract.batchCreateContracts({subjects:[{subjectId,policyId,subjectType:1}], subjectType:1, licenseeId:collectionId, licenseeIdentityType:1})`。签约成功即允许写入依赖草稿；付费策略可能回 `authStatus:128`，CLI 显示“请在浏览器完成支付”但不回滚合同、不假装已经付款，也不重复签约。

`Contract.batchContracts` 用于合集身份的授权查询、`batchCreateContracts` 用于显式签约；两者都必须走本仓 `packages/tools-lib`。现有 tools-lib 的 `subjects` TypeScript 声明缺少服务端要求的 `subjectType`，实现时要补正声明和回归测试，不能通过 `any` 永久绕过。

## 4. 上抛与排除项：安全边界

Console 的依赖微前端会返回 `baseUpcastResources`、`authExcludedItems` 和有时的待签策略；合集页把它们带入服务端草稿，最终 `updateCollection` 也支持相关字段。但是它们不是“直接依赖列表”的同义字段，且 Console 代码中存在 `policyID/contractID` 映射不一致的历史痕迹。

因此一期 CLI 的确定规则是：

- 直接依赖仍只声明 `{resourceId,versionRange}`，但操作草稿另保存由授权处理步骤产生的 `baseUpcastResources` 与 `authExcludedItems`；这不是依赖数组的一部分，也不能丢弃；
- `excludedType:'contractId'` 的 `excludedValue` **只能**是实际 `contractID`，不能误填同一对象中的 `policyID`。新签约必须从签约结果保存 contractId；已有合集须由 `Contract.batchContracts({licenseeId: collectionId,…})` 和服务端草稿读回重建；
- 无法重建已有排除项时，允许只读和继续编辑本地表单，但禁止 publish；不得用空数组覆盖；
- 单品上游授权仍按单品设计独立处理，不因本页限制而绕过。

工具库的目录列表接口当前只回单品授权布尔值，不提供完整排除映射；因此 `collection auth show` 必须明确区分“已验证可重建”和“未知”，不能假装列表足以恢复映射。实现前需做一次 dev 契约测试，锁定 `batchContracts` 与服务端草稿对已有排除项的可重建范围。

## 5. 恢复、并发与验收

签约是远端副作用，操作草稿写入失败不允许重新签约：CLI 必须先持久化 `signing` 意图，再签约，随后重新读取合集身份下的合约并写草稿；中断恢复先查合约，只有确认未产生合同才可再次发签约请求。不同 CLI/Console 使表单基线变化时按表单文档冲突处理，不做依赖数组盲合并。

验收：

1. 合集直接依赖不修改目录草稿、不创建版本、不加入单品。
2. 授权查询和签约的被授权方始终是 collection resource ID，而非当前登录用户或来源资源。
3. 免费、付费及已有合约分别得到可解释结果；付费不阻塞记录依赖，也不宣称支付完成。
4. 环、无匹配版本、自己依赖、非单资源、冻结/未发布目标均不写本地或远端依赖。
5. 发布前完整 `dependencies` 只由表单快照生成，未知上抛/排除项不会被捏造。
