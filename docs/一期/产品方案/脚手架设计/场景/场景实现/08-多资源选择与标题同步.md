# 多资源选择与标题同步：命令路径

本页实现 [真实场景 08](../真实场景/08-多资源选择与标题同步.md)。身份只用 `--resource` 选择，产物只用 `--artifact` 指定。

## S61：零状态

```text
freelog-cli status --env dev
→ 当前目录没有资源状态。新资源可直接 create --type <叶子类型> --artifact <路径>，也可先 init 再 create；已有资源请 bind <资源 ID|标识符> --artifact <路径>。
→ exit 1；不调平台、不创建 .freelog
```

## S62：单状态

```text
freelog-cli version show --env dev
→ 静默使用 .freelog/1.json；不显示选择菜单
```

## S63：多状态

```text
freelog-cli update-version --env dev
→ 请选择资源：
  1) 1.json  标题=标题 A  标识=a  ID=...  类型=RT006003  产物=a.mp4  有工作稿
  2) 2.json  标题=标题 B  标识=b  ID=...  类型=RT006003  产物=b.mp4  无工作稿
  0) 退出

freelog-cli update-version --resource artifact:b.mp4 --bump patch --yes --env dev
→ 只操作 2.json / 2.version.json

freelog-cli update-version --bump patch --yes --env dev
→ exit 1；多份状态的非交互调用必须传 --resource
→ 例如：id:<A的ID> | name:<username/a> | artifact:a.mp4 | file:1.json；
         id:<B的ID> | name:<username/b> | artifact:b.mp4 | file:2.json
```

`--resource` 还可为 `id:<resourceId>`、完整 `name:<username/name>` 或 `artifact:<相对文件/目录>`；标题仅在列表显示，即使唯一也不能用于选择。`file:` 保留给 AI、脚本和恢复。

## S64：冲突

```text
freelog-cli status --env dev
→ 发现 1.json 与 2.json 使用同一 resourceId；保留所有本地文件，未调用平台。
→ 请先备份 .freelog；删除一组完整的 N.json + N.version.json，或在空状态重新 bind。
```

孤儿 `N.version.json`、资源 ID / 类型不匹配工作稿、重复标识符或重复产物路径同样停止，不自动修复。

## S65：标题同步

```text
freelog-cli resource sync --env dev
→ 读取所有 env=dev 的已绑定资源并在一个本地事务中更新 title

freelog-cli resource sync --resource id:<resourceId> --env dev
→ 只同步这一份
```

请求失败的状态保留旧标题；命令打印成功/失败摘要并退出非零。`update --title <title>` 成功后应直接回写选中 `N.json.title`，不需要再调用同步命令。

## S66：多资源中新增或接入

```text
# 同一素材目录中已有 video.mp4、cover.jpg，但尚无 .freelog
freelog-cli create --title 视频 --name video --type <视频叶子code> --artifact video.mp4 --yes --env dev
→ 新建 1.json，filePath=video.mp4
freelog-cli create --title 封面图 --name cover --type <图片叶子code> --artifact cover.jpg --yes --env dev
→ 新建 2.json，filePath=cover.jpg；不要求新目录，也不选择或改写 1.json

# 1.json、2.json 已绑定，没有未绑定状态
freelog-cli create --title C --name c --type RT006003 --artifact c.mp4 --yes --env dev
→ 成功后新建 3.json；不要求先选择 1.json 或 2.json

# 有且仅有一份未绑定 3.json
freelog-cli bind alice/c --artifact c.mp4 --env dev
→ 接续 3.json

# 有多份未绑定状态
freelog-cli create --title C --name c --type RT006003 --artifact c.mp4 --yes --env dev
→ exit 1；请传 --resource artifact:<当前文件> 或 file:N.json 等精确选择器，不能按编号或菜单猜测

freelog-cli bind alice/c --resource artifact:c.mp4 --artifact c.mp4 --env dev
→ 只写 3.json；若 alice/c 已在别的 N.json，失败并保留所有状态
```

`create --resource` 只能接续未绑定状态；对已绑定状态必须失败。`bind --force --yes --resource artifact:<当前文件>`（AI、脚本也可用 `file:N.json`）才可替换已绑定目标，并在同一事务删除该编号的工作稿。

## S67：有损工作稿操作

```text
# 有稿、交互终端
freelog-cli version draft discard --resource artifact:b.mp4
→ 打印 2.version.json 的来源、文件、条目与描述摘要
→ 确认「丢弃工作稿？」默认否；取消 → exit 0，2.version.json 保留

# 有稿、非交互
freelog-cli version draft discard --resource artifact:b.mp4 --yes
→ 只删除 2.version.json

freelog-cli version draft pull --resource artifact:b.mp4 --version 1.1.0
→ 先确认线上 1.1.0 存在，再显示旧稿摘要并确认；取消或线上版本不存在 → 旧稿保留

freelog-cli update-version --resource artifact:b.mp4 --reset --bump patch --yes
→ 先验证已有 latest、新号、产物路径；任一失败 → 2.version.json 保留
→ 通过后确认/--yes，删除 2.version.json，按回显源重拉；后续拉取、上传或提交失败 → 不恢复已确认丢弃的旧稿
```

领域层不得接受未经确认的有稿 `discard` 或 `reset` 删除；命令层确认只是用户界面，不能成为唯一防线。
