日期：2026-09-10  
状态：`[~]` 问题记录与实施状态索引。本文件不覆盖现有 ARCHITECTURE、PHASE、场景或代码；与正式设计冲突时，以正式设计为准。

对应实施前规划见：[单资源 CLI 健壮性治理计划](../../../.omx/plans/2026-09-10-单资源CLI健壮性治理计划.md)。

## 1. 本轮已确认的不变量

1. 一个工程可管理多份彼此独立的单资源；一次常规命令只操作其中一份。
2. `.freelog/N.json` 是资源身份缓存，不是版本管理或版本历史。资源成功发布后仍保留它。
3. `.freelog/N.version.json` 是该资源唯一的、尚未提交的当前工作稿；版本 POST 已确认成功后删除它。平台是版本历史的唯一来源。
4. 已绑定资源的 `resourceId`、完整资源标识、类型和环境是身份事实，不能被普通编辑命令悄然改写。`filePath` 是下一次上传的默认本地产物，可以明确修改。
5. 标题是可重复、可过期的展示缓存；它不是资源身份，也不能作为可信的资源选择条件。`resource sync` 是显式刷新标题缓存的入口，不能由“选择资源”隐式触发。
6. `--resource` 只选择资源身份；`--artifact` 只提供本次上传或默认产物路径。主题/插件仅在产物为目录时临时压缩；显式文件（包括 zip）直接上传。

## 3. 目标选择与缓存规则

### 3.1 单资源命令的可信选择器

推荐公开选择器：

| 选择器 | 适用性 | 可信依据 |
|---|---|---|
| `id:<resourceId>` | 日常、脚本、线上操作首选 | 不可变平台资源 ID |
| `name:<username/name>` | 人工可读的稳定身份入口 | 已缓存的完整资源标识，必须精确匹配 |
| `artifact:<工程内规范路径>` | 本地素材/构建目录定位 | 当前身份记录的默认产物路径；文件暂时不存在仍可定位 |
| `file:N.json` | AI、脚本、故障恢复 | 当前工程内的精确本地状态文件 |

标题不在该表中。TTY 列表可以显示标题，但实际选中值必须回填稳定选择器。无选择器时仍保持：零份给 create/bind 指引；一份自动选择；多份 TTY 选择或非交互失败。

### 3.2 标题缓存

- create、bind 和 `update --title` 成功后可回写标题缓存。
- `resource sync [--resource ...]` 是唯一批量/显式刷新入口；它按当前环境读取线上详情，成功项原子回写，失败项保留原值并逐项报告。
- 标题更新失败、标题重名或标题与线上不一致，都不得改变资源选择结果。
- 未来可提供仅本地的标题搜索/过滤来辅助人工发现，但搜索结果必须要求用户以稳定选择器确认目标。

### 3.3 统一执行顺序

```text
参数解析 → 解析工程根 → 短锁 → 验证/恢复可信本地事务
→ 诊断状态 → 固定资源上下文 → 生命周期与权限预检 → 确认
→ 重取锁并复验上下文 → 平台动作 / 本地原子收尾 → 输出恢复信息
```

`create` / `bind` 是新增或接续状态的专属路由；其它单资源命令必须在固定资源上下文后运行。版本提交已建立可核验未决记录；其它远端写操作尚未证明有足够的平台事实可安全恢复，不能把这个目标描述为已实现。

## 4. 已裁决与仍需评估的取舍

1. `title:` 已从公开单资源选择器移除；标题仅用于展示和显式 `resource sync`。
2. 已绑定新状态保存完整 `resourceName`；旧状态缺失时不能用短名猜测完整身份，必须通过明确恢复/重新 bind 处理。
3. `N` 已采用工程内单调不复用；长期脚本使用 `id:`，不是编号文件名。
4. `.pending-operation.json` 与 `resource recover` 已用于版本提交。扩展到 create、listing、策略、上下架、依赖签约前，必须逐项证明平台存在足以区分并核验该操作的事实；没有证明时保留“结果未知、不得自动重发”的边界。
5. 失效附加属性保留在 `orphanedInputAttrs`，通过 `version attr review` 提供逐项处置；未引入不必要的第二种 `reviewItems` 状态格式。
6. 本地损坏采用保守模型：`resource list` 永远只读诊断；任何正常业务命令发现全局身份/稿/事务冲突即停止，避免一个被低估的共享冲突扩大为写入损坏。

## 5. 验收底线

尚未最终验收的 I08 / I13 与整体验证关闭前，不得将完整发布流程标记为已验收。每项改动均须同时具备：

1. 已批准的正式设计、PHASE、场景和使用手册同步；
2. 单元与 CLI 级回归；
3. 对 create、bind、版本提交、策略、上下架、依赖签约等平台写入的 dev 真网证据；
4. `test`、`typecheck`、`build`、发布包验证和 `git diff --check` 的新鲜结果。
