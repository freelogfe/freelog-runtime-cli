# 设计确认后的严格交付证据补强

## 目标与范围

用户参与业务设计验证；工程链路由 AI 负责。本轮补齐可执行的“已登记设计→验收义务”追溯和候选级双路审查记录绑定，不改业务行为，不推断历史设计全部已获批准，不发布/提交/推送，不做新 dev 写入。

现状依据：`scripts/release/core.mjs` 的 checkCandidate 仅核验候选和业务报告；`test/acceptance/catalog.mjs` 含14进程项、7未实现义务及2业务项。现有源码摘要能发现变化，不能证明设计语义或审查真实发生。

## 最小实现

1. 先在质量规范固定边界。新增源码内交付契约，固定现有9项产品义务到正式设计文件与 case ID 的对应，不接受报告自定义清单或 LEGACY 充当业务覆盖。
2. 候选内 delivery.json 记录设计文件摘要、固定映射、作者，以及代码/架构两份原始独立审查文件引用。原始审查自身包含同一候选、source、tarball、契约摘要、scope、审查者、时间、结论和问题处理；作者、两lane不能同一记录身份。
3. checkCandidate 读取业务报告后先核验交付证据，再运行原业务协议；发布前的二次检查同样重读。无 skip 开关，不新增依赖，不以审查报告消除7项 gap。
4. 先补精确失败回归，再实现；有效局部fixture与缺失/映射/摘要/自审/非通过/时效/原始证据变化/路径/未知case负例分开。发布集成需证明拒绝发生在 npm 读写前；增加内存 mutation 防止被别的拒绝救绿。
5. 双路独立复核、本地根 verify、实际候选prepare和只读拒绝检查。维护 README/模板/交接，保留原有脏改动。最终审查证据存在忽略目录，不回写源码造成摘要循环。

## 验收与边界

- 每项负例必须命中自己的错误码，删除对应 guard 后其断言应失败；不能只 assert.throws。
- delivery 局部正例只说明追溯和记录绑定合法，产品 PASS 仍由原 acceptance 协议决定。
- 当前追溯粒度仍是9项目录义务，不是所有字段或场景逐项覆盖；7项完整业务专项继续阻断。
- 本机身份字符串和文件哈希不是身份认证，独立原始结论由真实子agent产生；不能伪造、重写旧结论或自动填 APPROVE。
- 任一实现/测试/文档变化后旧候选及审查失效；实际发布仍需用户明确版本授权。远端CI强制检查、分支保护未核实，不在本地工具中伪造已执行状态。
