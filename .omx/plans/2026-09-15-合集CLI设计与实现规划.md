# 合集 CLI 设计与实现规划

2026-09-15，状态：设计草案已提出，待用户复核；未开始代码实现。

## 需求与来源

用户希望在当前单资源 CLI 基础上设计合集，重点解决本人已发布单资源的成员管理。业务要求实际为“本人已上架单资源”；合集用目录变更发布，不提供 semver 升级流程。

用户补充确认：本地来源也须先走既有单资源发行与上架，再从线上查询添加为合集单品。成员不接受 file:N.json/产物路径，不从本地身份推导可加入资格。具体复用清单及发布后返回查询的体验见主稿 §3.2–§3.4。

产品方案、证据 E1–E12、待验契约 K1–K8、场景 C01–C18 统一见 [合集设计草案](../../docs/一期/产品方案/合集CLI设计草案-2026-09-15.md)，不在此复制第二份业务规则。

## 独立能力与当前修改边界

用户新增明确要求：AI准备标准JSON后，一次连续执行多个/几十个单资源发行，减少逐资源、逐字段CLI往返。[快速发行设计草案](../../docs/一期/产品方案/单资源JSON与快速批次发行设计草案-2026-09-15.md) 是独立单资源能力的设计依据，可为合集提供线上候选，但与合集没有必然关系。

| 独立快速发行任务 | 影响范围 | 完成标准 |
|---|---|---|
| F1 统一发行输入 | 新 spec 数据模型/Schema；`domain/version/form/` 共用校验；类型/模板准备资料；包内文档 | 单资源create/update标准明确，完整属性/配置/依赖，静态与动态错误可定位到JSON路径 |

| F3 多份预检与接续 | 拟新增批次加载/defaults/任务执行与报告服务；pending/recover | 1/10/30份；展开意图快照、按阶段resume校验、与手工命令共用pending；明确与未知失败分开；已完成阶段不重复；记录实际耗时/请求量 |

## 决策与替代方案

- 推荐：本地工作稿完整整理，显式发布时写平台目录草稿并合并。保留现有 N.json 永久身份与分步续作习惯，可完整 diff。
- 替代：每次 item add/remove 立即写平台草稿。优点是 Console 随时可见；代价是本地编辑也有远端写副作用、离线编辑受限、丢稿和跨端冲突更复杂。当前不推荐作为默认流程。
- 不采用直接 live CRUD：添加、删除、排序不能有的暂存有的立即线上生效，破坏统一预览和发布边界。
- 已确认限制：缺少服务端 revision/CAS 时，客户端无法保证跨机器并发原子性；不能把本地锁当成该能力。

## 验证与风险控制

- 先做协议/快照/排序/批次/恢复的单元和接口契约测试，再用本人 dev 资源与合集实测。
- 现有单资源类型树/leaf 校验、filePath 规则、工作稿、策略模板、签约、unknown recovery 都在影响面，提取共享服务后必须回归。
- 每个变更组跑针对性测试、typecheck；落地完成时全 CLI tests、build、verify:package、diff check；文档随包验证。
- dev 必须覆盖真实成员、系统附加属性、自定义属性、文本及下拉配置、依赖、说明、展示配置的首发/更新读回。
- dev 必须把“本地单资源发行→上架→线上本人资源库查询→合集添加”串起来验收，同时覆盖未上架拒绝、线上暂未读到、无本地源资源缓存、合集添加失败后不重复发行。单资源与合集领域服务共享规则，状态和提交adapter分别实现。
- 上一项是合集侧的可选组合场景验收，不是F1–F4快速发行独立交付的通过条件；快速发行不得加入合集参数、pending阶段或afterResources钩子。
- 账号凭据只从本地忽略文件/系统凭据库使用；设计阶段未进行平台写入。
- K1/K2 尚未证明草稿隔离和条件合并，明确限制并发保证；不以大量单测掩盖平台无法证明的性质。
- 根 DESIGN 和业务分册历史 CLI 示例过时，实施不能照搬 manifest/state、session 或 import-dir 模型。
