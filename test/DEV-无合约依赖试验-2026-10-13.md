# dev 无合约依赖试验

## 目标与判断标准

回答：当前资源或合集从未签约目标时，平台是否允许记录并发布依赖声明？不能把本地 JSON 写入、HTTP 成功或个人已有授权当作答案。

若平台确实允许，按用户要求暂时关闭 CLI 自动签约和支付引导交互，改为依赖声明与消费授权分离，签约/支付留给网页。是否移除发布前合约门禁也由实际接口结果决定；测试前不修改产品代码。

## 安全边界与前置

- 仅 dev，primary 账号；新建隔离主题、图片、视频与合集作为乙方，资源池仅用于只读依赖目标。
- 业务 API 经本仓 tools-lib。实验执行时 CLI 会阻止缺合约依赖，因此该阶段只用 CLI 创建壳及 prepare 合法文件，直接调用 tools-lib 发布 API，避免以客户端门禁替代平台证据。
- 不调用签约、付款 API，不传 `batchSignContracts`，不撤销旧合同，不修改池内资源，不上架测试源。
- 查询以真实乙方 ID、单资源身份 1 / 合集身份 4、目标主体 1 为准，不限合同状态。前后均须没有任何双方合同，含搁置/终止，不只没有有效合同。
- 每次发布读回真实版本/合集快照及依赖，再查合同；若平台自动生成合同，单独记录，不能称为无合约成功。
- 所有请求和子进程有超时；POST 结果未知只读诊断，不能盲目重发。临时工程、脱敏报告和新建审计壳有意保留，登录态退出。

## 结果与后续

API 试验已完成：4 个新主体（主题 RT001、图片 RT005001、视频 RT006003、合集 RT003011）各对 6 个目标逐个提交，再提交全部目标组合，共 28 次全部 accepted；rejected/unknown/既有合约跳过/装置失败均为 0。三个单资源均覆盖带依赖的首版 `1.0.0` 和后续更新版；合集创建时已有初始 `1.0.0`，通过 `updateCollection` 完善其快照，而非创建单资源版本。

每次发布前后查询均没有双方合约，实际版本快照的依赖 ID 与范围读回一致。又对 24 个源/目标组合分别扫描合同状态 0、1、2，共 72 项均无合同，排除平台隐藏自动签约。6 个目标包含本人免费、本人付费、他人等待免费及多个他人免费资源；没有他人付费样本，不把结论扩张为所有平台类型或任意策略已验证。

正式证据：系统临时目录 `freelog-runtime-cli-verification/unsigned-dependencies/2026-10-13T06-14-12-726Z/report.json`，状态扫描为同目录 `supplemental-contract-status-scan.json`。源码为 `test/verify-uncontracted-dependencies.mjs`。不调用签约或付款，源保持未上架，登录态已退出。

结论：当前 dev 的依赖声明/发布可以独立于签约进行。按用户决定，移除 CLI 直接依赖的自动签约及提交合约门禁，签约/支付交给网页；不宣称声明成功等同已获消费授权。合集单品上游的 contractId 排除映射未经本试验覆盖，关闭其自动签约但保留只读事实检查与网页处理提示。

## 装置、清理与剩余验证

- 首轮实验误将工程置于仓内 `test/tmp-uncontracted-dependencies`，这是装置边界问题，不是产品失败；检查登录退出后迁移到系统临时目录，未删除其它改动。该仓内目录已不存在，保留迁移证据供审计。
- 28 次均首次明确成功，未发生 POST 超时，因此无依赖对照和未知写恢复分支未触发；不伪称已做网络故障注入。
- 本轮保护了前轮 dirty 状态，未提交/推送/发布 npm。实验脚本是有意保留的可重复证据入口。
- CLI 实现调整后还需回归：无合同 add/range、首版/更新版提交、合集完整表单/纯目录发布，不请求合约/授权、不传签约字段，旧签约选项拒绝，身份/范围/环/属性/配置门禁保留。最终基线与受影响 dev 验收结果在交接文档汇总。
