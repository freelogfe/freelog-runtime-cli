# 发布主题插件流程设计
  
作品调试：

  1.作品线上维护草稿版本，设置数据、依赖，策略等。

  2.开发

    2.1 作品侧： 展品调试与conosle管理侧使用插件直接在作品下面预览作品调试
        2.1.1 打开作品的调试开关，才能够进行调试，调试数据使用的是草稿版本。
        2.1.2 可以将某个正式版本导入到草稿版本进行开发调试。

        调试开关是为了防止非作品拥有者调试该作品。

    2.2 节点侧：节点这边是展品和依赖两种情况
        2.2.1 展品：同样打开展品的调试开关，展品无需上线，展品配置信息使用的是测试数据，
              正式数据与调试数据可以互相覆盖，
              同时需要打开作品的调试开关，进行开发调试。
        2.2.2 依赖：同上。
        2.2.3 调试完成后发布作品后，可以将展品调试数据同步到正式数据。
        
        调试开关是为了防止作品拥有者未经同意调试该展品。

  3.发布作品

    3.1 本地发布时上传本地打包的代码，后端根据打包的文件名和sha1值以及草稿的数据  发布为一个正式版。

  4.调试数据（草稿版本）与正式数据（正式版本）差异： 数据与合约都独立
    4.1 数据差异：草稿的作品文件访问的是本地文件，正式作品文件访问的是线上文件。
    4.2 访问差异：需要打开调试开关，以及本地调试时才可以访问到调试数据。
    4.3 合约差异：在调试数据中可以新添加策略进行调试，每次修改策略后，相关的调试合约自动全部作废，需要重新签约；
                 策略调试完成后可以保存为模板，用于设置授权策略。
                 这里因为策略是挂在作品上面的 而不是版本上面的，

节点调试：单独调试一个展品是很危险的，没有权限控制。

  5.整个节点调试控制：
     5.1 设置节点调试开关，控制节点是否可以调试。
     5.2 调试节点域名需要不同或带调试识别参数， 同时可以设置调试节点的访问密码。
     5.3 节点数据分调试数据和正式数据，正式数据与调试数据可以互相覆盖。

  6.展品调试控制：
     6.1 展品调试开关：同2.2，但展品可以不上线也能进行调试，也就是只要打开了调试开关就可以正常访问。
     6.2 可以批量打开展品调试开关。
     6.3 可以批量进行调试数据和正式数据互相覆盖。

  7.调试环境与正式环境异同： 数据与合约都独立
     7.1 数据差异：除了互相独立，无其他差异。
     7.2 访问差异：调试环境可以访问未上线的打开了调试开关的展品。
     7.3 合约差异：调试环境可以添加策略进行调试，每次修改策略后，相关的调试合约自动全部作废，需要重新签约。
